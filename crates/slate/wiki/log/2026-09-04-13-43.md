# fix LoopToWhile racing ForRangeRecover for unsimplified loops

_2026-09-04 13:43:15_

LoopToWhile (priority 20) was permanently converting for-range-shaped loops
to `while` before ForRangeRecover (priority 13) got a chance. Priority only
orders candidates *within one worklist visit*; it doesn't guarantee
ForRangeRecover sees the loop first overall. ForRangeRecover needs the
increment tail (`i = i + 1`) fully inlined from its raw
`let tmp = i + 1; i = tmp;` shape across several worklist rounds, while
LoopToWhile's head_test only checks the break-guard and fires as soon as
the guard alone is simplified — winning the race and locking the node into
NodeKind::While, which LoopToWhile-only rules (kinds=[Loop]) can never
revisit.

Root-caused with eprintln debug on both rules' matches(): for a repro
`for (int i=0;i<4;i++) pthread_create(...)`, ForRangeRecover's guard check
already passed (`If(cond=!(i<4))`) but is_unit_increment failed because
body.last() was still `i = _vinc` (a pending single-use temp), not
`i = i + 1`.

Fix: loop_to_while.rs gained `tail_pending_inline`, which defers matches()
whenever body.last() is `x = tmp` for a single-use, effect-free temp still
defined inside the loop body — the same one-hop-through-temp check
for_range.rs already does for its bound. General "don't commit to the
lossy fallback while the tail is still converging" guard, not for-range-specific.

Bug was silently baked into checked-in REWRITES FileCheck blocks:
loop_to_while.rs (5c4deeb2) landed while tests/support/filecheck.rs
short-circuited all Rewrites-profile checks (2026-09-04-09-06.md).
re-enable rewrite filechecking (36478a7a) turned checks back on and
regenerated snapshots to match the *buggy* output instead of catching it.
Regenerated 35 fixtures plus fixtures.multi/local_struct_cross_file_collision
back to the for-range form. Full rewrites profile: 93/93, fmt+clippy clean.
