# always trust CIR for char signedness (slate-sdks.2)

_2026-09-05 09:12:21_

Root cause: plain C \`char\` signedness is target-defined (signed on x86/Apple,
unsigned on aarch64/arm/riscv), but four independent places guessed \`signed\`
unconditionally instead of consulting CIR or the target:

1. c_ast.rs::parse_c_type - bare \"char\" spelling always built CType::Char{signed:true}.
2. lowerer.rs record-field paths - CIR struct/union member matching broke on any
   struct with alignment/tail padding, since CIR emits explicit Pad members but the
   matcher required members.len() == record.fields.len(). Added cir_data_members()
   to filter to Data/BitField members before matching (record_analysis.rs too).
3. function_setup.rs::main_arg_bindings - argv's char_ptr was hardcoded to i8.
4. backend/engine/prelude.rs + libc_call.rs - the synthesized __slate_atoi/atol
   helpers' \`s: *const i8\` param was hardcoded, breaking on aarch64 where the
   real argv/char pointers are *const u8.

Fix: CIR is now consulted first everywhere reachable; record-field code panics if
CIR resolves a char field to something other than an 8-bit int (misalignment bug),
but falls through silently when CIR has no data at all (e.g. sizeof-only structs
that clang constant-folds away). Added toolchain::char_is_signed_default() as the
correct target-aware fallback for cases 1, 3, 4 where no CIR type is reachable.

Found by removing the 14-fixture char-signedness skip_reason() blanket in
differential_aarch64.rs and using the resulting failures/panics as a worklist.
Verified: aarch64-lowering, aarch64-rewrites, x86 lowering, x86 rewrites all
pass. gnu_builtin_atomic_flag stays skipped - separate ClangIR limitation
(cir.atomic.test_and_set requires a signed-8-bit pointer operand unconditionally).
