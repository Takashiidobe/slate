# search_lsearch.c moved back to supported: real slate-side fix, not just an upstream workaround

_2026-08-25 16:44:09_

Corrects an earlier version of this entry. chibicc's search_lsearch.c is being re-moved unsupported -> supported with zero source changes; libc_test_functional_supported_tests_match_c passes. Verified by building the actual 87afb4a7^ commit (parent of the commit that punted this fixture) against today's clang-ir crate (one unrelated match-arm patched to compile) and re-running the fixture: it produced a genuine rustc E0308 at that point in history -- `std::mem::transmute::<Option<fn(*mut i8, *mut i8) -> i32>, ...>(Some(strcmp))` where `strcmp`'s real extern decl was `*const i8` (correctly repaired from Clang AST spelling) but slate's own transmute `from` annotation assumed CIR/CType's const-dropped `*mut i8` -- a self-inflicted mismatch caused by issue 217687, and it did miscompile at the time.

The actual fix landed two days later in dc4135d3 ("handle fn ptr to fn ptr transmutes across project", 2026-08-22), src/frontend/lowerer/memory.rs:238-255: when a fn-ptr-to-fn-ptr cir.cast's source is a direct reference to a named global function, transmute through an untyped `*const ()` raw pointer instead of asserting a typed `Option<fn(...)>` source, sidestepping the const/mut disagreement entirely. The record-field `trust_cir` logic from 87afb4a7 (lowerer.rs:487) is unrelated -- this fixture has no struct with a function-pointer field and never exercises it (confirmed by toggling `trust_cir` off: byte-identical output).
