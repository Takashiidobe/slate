# Add GCC 'p' (address) asm constraint

_2026-09-06 20:10:54_

Implemented slate-3f8g.4.15.2: the 'p' inline-asm constraint (operand's
address, materialized in a register). Audited real-world usage via
gh code search (Linux kernel percpu.h, esbmc, chaos kernel) -- always
paired with the %a template modifier, since LLVM's x86 asm printer
requires 'a' to render a 'p'-class operand at all.

Changes:
- constraint_allows_generic_reg now accepts ConstraintAtom::Address,
  so 'p' resolves like generic 'r' (AsmRegConstraint::Generic).
- Added TemplateModifier::Address ('a'); rendered by wrapping the
  substituted register in ()/[] per dialect, since Rust's asm! has no
  address-print modifier -- the register holds the address, so the
  wrapping parens perform the dereference GCC's %a would otherwise do.
- Fixed a latent bug found in the process: asm input operands used
  operand_expr instead of typed_operand_expr, so a pointer-typed input
  that resolved to a bare global (e.g. &global_var, or a struct
  pointer field via "g"/"r") emitted the global's/base's identifier
  instead of its address. This is what made 'p' materialize the wrong
  value, and also fixed gcc.dg torture__pr77648-1 (promoted from
  fixtures.gcc-dg.unsupported).
- Refactored translate_asm_template from a single parse+emit scan into
  parse_asm_template (str -> Vec<TemplatePiece>) + per-operand
  rendering, per user request to keep dialect/modifier decisions out
  of the character scanner.

New fixture: tests/fixtures/asm_address_operand_p.c.
