# sqlite3 CIR memory blowup: root cause found in ASM printer

_2026-08-23 13:02:23_

Captured a real crash backtrace (not just timing) from /tmp/vdbe_449.i: it's
LLVM ERROR: out of memory inside a SINGLE mlir::Operation::print call, cycling
through StructType::print <-> PointerType::print <-> ArrayType/UnionType::print
via CIRDialect::printType, ending in bad_alloc from a std::string reallocation.

Root cause in clang/lib/CIR/Dialect/IR/CIRTypes.cpp: printRecordBody() only
guards literal self-reference cycles via tryStartCyclicPrint (instance-identity
keyed). CIRDialect.cpp registers a short alias for named records
(CIROpAsmDialectInterface::getAlias, !cir.rec\_<name>), but printRecordBody's
per-member printer.printType(member) never consults that alias for repeat,
non-cyclic occurrences - it re-expands the full body every time. sqlite's
Mem/sqlite3_value struct is reachable via many independent, non-cyclic pointer
chains (sqlite3, Vdbe, Parse, sqlite3_context, UnpackedRecord, ...), so each
path re-prints its full body, and total output size grows combinatorially.

This is an ASM-printer bug, not CIRGen - happens while serializing the module,
not building it. Filed under slate-wcf7.2. Minimal-reproducer work continues
via cvise for the upstream report; two prior cvise runs falsely converged
because the interestingness test's signal (timing-threshold, then an
artificially tight ulimit -v cap) was weaker than the real bug - both fixed by
requiring an actual timeout/bad_alloc under a generous (8GB) cap.
