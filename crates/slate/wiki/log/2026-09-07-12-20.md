# ARM32 __int128/VLA-alloca are ClangIR frontend limitations, not slate (slate-3f8g.4.16.14)

_2026-09-07 12:20:23_

Confirmed both failure categories occur at 'clang -emit-cir' itself, before
slate's lowerer runs -- same pattern as slate-sdks.1's aarch64 findings.

1. int128_arith.c, int128_struct.c, f128_intrinsics.c: clang rejects
   __int128 outright for armv7-unknown-linux-gnueabihf ('__int128 is not
   supported on this target'), a plain clang frontend diagnostic.

2. c99.c, local_vla.c, builtin_alloca.c (VLA/alloca): SLATE_CLANG's CIR
   codegen crashes with a module verification error --
   'cir.alloca' op operand #0 must be 64-bit unsigned integer, but got
   '!cir.int<u, 32>' -- CIR's alloca op hardcodes a 64-bit size operand
   requirement regardless of target pointer width, so on a 32-bit target
   the natural i32 VLA-length operand fails verification before any CIR
   pass runs.

Both are SLATE_CLANG (upstream ClangIR) build limitations, not fixable in
slate's own frontend/backend code. Kept skip-listed in
tests/differential_arm.rs (reason already correctly described this before
verification). Bead closed as documented/blocked per its acceptance
criteria's alternate branch.
