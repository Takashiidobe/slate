# bitint switch cases use inline const blocks

_2026-09-02 14:51:40_

Bitint switch cases briefly hoisted every case value to a module-level
`const` item so exact matches could be const *patterns* (`__CASE_B256_5 =>`).
That required threading a `Vec<BitintCaseConst>` out-param from `cir_ops`
through `control_flow` into a `Lowerer` field, plus a name-mangling scheme.

Replaced with `Expr::ConstBlock`: every bitint case is a guard again, and the
bound is written inline as `const { bitint::BInt::<..>::from_decimal_str("..") }`.

Why this is the right shape:

- Range patterns cannot ever cover bitint. rustc restricts `a..=b` in pattern
  position to char and the numeric primitives (E0029); no trait impl on
  `BInt`/`BUint` opens it. So a guard is mandatory for `case a ... b` and the
  const-pattern form only ever covered half the cases anyway.
- `BInt`/`BUint` already impl `PartialOrd`/`Ord`, so `>=`/`<=` in the guard
  need nothing new; a `RangeInclusive::contains` spelling would need the same
  bound and buy nothing.
- A pattern cannot contain a call, which is the only reason a named const item
  was needed. A guard is expression position, so the call can be inline.
- `from_decimal_str` is `const fn` but running it in a guard would be a runtime
  string parse per switch evaluation; `const { }` forces compile-time
  evaluation without a hoisted item.

`Expr::ConstBlock` is a leaf everywhere in the backend (walkers, inline_temps,
pointer/string lattices): nothing may be substituted into it. `merged_guard` in
structure_dispatch stays — guards still cannot be `Or`'d — but lost its
`Pattern::Const` arm.
