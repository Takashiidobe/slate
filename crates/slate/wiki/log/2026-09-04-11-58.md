# plain __builtin_alloca already fully supported; alloca_with_align blocked upstream (slate-04q.47.5)

_2026-09-04 11:58:16_

Checked CIRGenBuiltin.cpp (llvm-project/clang/lib/CIR/CodeGen/CIRGenBuiltin.cpp)
for the whole stack-allocation builtin family:

- alloca/_alloca/__builtin_alloca/__builtin_alloca_uninitialized all route
  through emitBuiltinAlloca to the same cir.alloca op (name="bi_alloca",
  a dyn_alloc_size operand even when the argument is a compile-time
  constant -- CIR never folds __builtin_alloca(16) into a fixed-size array
  alloca the way a real C array declaration would).
- __builtin_alloca_with_align, __builtin_alloca_with_align_uninitialized,
  and __builtin_infer_alloc_token all hit errorBuiltinNYI -- confirmed
  directly with `clang -fclangir -emit-cir` on
  `__builtin_alloca_with_align(16, 128)`: "ClangIR code gen Not Yet
  Implemented: unimplemented X86 library function builtin call". No CIR
  op is ever produced for these; nothing for slate to lower.

Turns out slate already has a mature, conservative Vec<u8>-backed
lowering for bi_alloca (src/frontend/lowerer/storage.rs::lower_alloca):
heap-backed emulation via a local `Vec<u8>` whose `.as_mut_ptr()` becomes
the alloca'd pointer, matching the epic's own stated assumption ("heap-
backed emulation is acceptable... behaviorally equivalent"). It already
handles both constant and runtime sizes uniformly, hoisted/goto-crossing
allocas (resize() on re-entry), va_list allocas, and a separate constant-
size struct-frame path (lower_constant_size_bi_alloca_group) reserved for
cases needing exact adjacent-field layout preservation. No code changes
were needed -- just verification + a fixture.

Added tests/fixtures/builtin_alloca.c covering constant-size,
dynamic-size, and __builtin_alloca_uninitialized; passes differential.
Split the CIR-unsupported alignment variant into slate-04q.47.5.1,
status=blocked, with the exact NYI repro recorded for re-check whenever
the local ClangIR toolchain build advances.
