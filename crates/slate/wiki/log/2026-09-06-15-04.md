# Re-diagnose long_double_aggregate: silent-zero aggregate init, not ABI marshaling

_2026-09-06 15:04:01_

slate-i3nv.5.2 was originally filed as a Rust<->C extern ABI struct-marshaling
bug (a field-shift). Re-investigated per user request and that framing was
wrong -- retitled/re-described the bd issue.

Root cause, confirmed via temporary debug prints in
src/frontend/lowerer.rs's render*const_value_expr (added, verified, reverted;
no net diff): the wildcard arm '* if matches!(ty, Type::LongDouble)' (~line 2935) intercepts ALL long-double values ahead of the direct
'Attr::CirFloat => fp_literal_expr_for_type(...)' arm (~line 2998). It only
knows how to produce a value from facts.pop_front() (the AST-probing
mechanism); when facts is empty it gives up and returns None, discarding a
perfectly good already-parsed CIR constant. Confirmed via debug output that
for 'struct ld_pair p = {0x1...p0L, 0x1...p0L};', each field's attr really is
Attr::CirFloat{ty: LongDouble, value: "1.00000000000000000011"} (correct,
full precision) but facts is empty for aggregate-initializer sub-elements,
so both fields silently default to LongDouble([0;10]) -- no todo!(), no
error, wrong answer at runtime.

Distinct from slate-i3nv.5.1: that literal has no AST FloatingLiteral node at
all (compiler-synthesized, blocked on an upstream ClangIR/MLIR f80-printer
gap). This one has a real source literal that Clang's own AST does record --
the gap is purely in Slate's own facts-plumbing not reaching into
InitListExpr sub-elements, so it's fixable without waiting on upstream.
Updated slate-i3nv.5.2 with full repro, root cause, and two candidate fixes
(walk InitListExpr children when building facts; or fall back to
fp_literal_expr_for_type on CIR's own Attr::CirFloat when facts is empty).
Not fixed in this session -- investigation only.
