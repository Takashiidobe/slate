# asm: correct g/imr and ebx docs against real CIR/clang/rustc evidence

_2026-09-06 09:11:13_

Extended wiki/concepts/inline-asm-support.md with findings from a design
discussion (no code changes) about a proposed g/imr and memory-operand
lattice, verified against real tools before writing anything down.

CIR ground truth (dumped via SLATE_CLANG -Xclang -fclangir -emit-cir):
g canonicalizes to imr on x86 before CIR exists. Inputs get a plain SSA
value (memory option already resolved away by Clang). Outputs get an
address + (maybe_memory) marker, deferring reg-vs-mem to LLVM's InlineAsm
lowering. Conclusion: picking `reg` whenever a constraint offers `r` is
sound by construction (the constraint was compiler-checked against the
template), not a heuristic -- no NP-hard register-pressure subsystem
needed. Output-side g/imr currently hard-errors (parse_output_reg_constraint
chokes on the `*imr` token) despite being listed as Supported; corrected.

Rejected consulting LLVM's regalloc for the maybe_memory case: isolating
an asm statement loses the real register-pressure signal that would make
the answer meaningful, and even a perfect answer doesn't unlock a Rust
representation (no memory-operand class either way).

Designed (not implemented) a scoped memory-operand path: CIR already
computes the operand's address for `m`, so a single-reference slot with no
address modifier can bind as in(reg) + deref-wrapped template text
(`(%0)` AT&T, `[{0}] dword ptr` Intel) instead of hard-erroring.

Corrected an ebx attribution error before it went in the doc: tested real
SLATE_CLANG accepts "=b" fine under -fPIC and -m32 -fPIC (no restriction).
zstd's cpu.h (~/c-corpus/zstd/lib/common/cpu.h:89) shows the actual native
restriction is GCC's, 32-bit -fPIC only (`!defined(__clang__)` branch,
"gcc reserves ebx for use of its pic register"); Clang's default branch
uses "=b" directly. Confirmed the real restriction slate works around is
rustc's own asm! macro, unconditional across every config ("rbx is used
internally by LLVM"), unrelated to either C compiler.
