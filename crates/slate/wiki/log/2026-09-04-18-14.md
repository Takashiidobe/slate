# MSVC ABI probes: dllimport/dllexport blocked upstream; data accessors + link names already work; cross-target env-pollution bug

_2026-09-04 18:14:17_

slate-wlpp.5 (calling conventions, imports, exports):

Verified two acceptance-criteria items already work correctly for x86_64
MSVC with no code changes: an imported data accessor
(__attribute__((dllimport)) extern int g_counter;) lowers to
`unsafe extern "C" { static mut g_counter: i32; }`, and an explicit
assembler/link name (extern int f(int) asm("actual_symbol");) lowers to a
call on the real symbol name directly. New fixture: tests/fixtures/msvc/
imported_data_and_link_names.c, added to differential.rs's
msvc_translation_ready() allowlist (from the wlpp.4 session) alongside
llp64/errno_stream_redirects.

dllimport/dllexport significance is NOT verifiable today, and it's an
upstream ClangIR gap, not a Slate bug. Two things compound:
1. Slate's MSVC profile lowers through x86_64-unknown-uefi with
   -fno-ms-extensions (toolchain.rs clang_target(), the wlpp.7 workaround).
   That disables __declspec parsing outright ("__declspec attributes are not
   enabled"), so __declspec(dllimport)/(dllexport) -- how real UCRT/Windows
   SDK headers spell these -- can't even parse.
2. Enabling -fms-extensions to get __declspec back reintroduces a *different*
   NYI: `isInvokeDest: no exceptions or ignore exception`, on ANY function
   call (not calls specifically to __declspec'd symbols), reproduced bare
   with $SLATE_CLANG -fclangir -emit-cir on x86_64-unknown-linux-gnu,
   x86_64-unknown-uefi, and x86_64-pc-windows-msvc alike -- a
   translation-unit with zero calls compiles fine under -fms-extensions, the
   first call trips it. Confirmed independent of slate-wlpp.7's MSABI bug.
3. Even the GNU attribute spelling (__attribute__((dllimport/dllexport)),
   which does parse without -fms-extensions) produces zero CIR-level signal
   on a non-Windows-environment target -- diffed generic CIR for a
   dllimport/dllexport probe against a plain-extern-linkage equivalent:
   byte-identical modulo ordinary external/private linkage. UEFI's
   TargetInfo doesn't implement hasDLLImportExport, so there's nothing for
   Slate to consume even if it wanted to.

Filed slate-wlpp.12 for the isInvokeDest gap and added a `bd dep add
slate-wlpp.5 slate-wlpp.12` blocking edge (same pattern as the existing
slate-wlpp.7 dependency).

Separately, found and fixed a real cross-target test-harness bug while
generating the new fixture's FileCheck blocks: tests/support/mod.rs's
ensure_c23_clang_args() permanently sets the process-wide SLATE_CLANG_ARGS
env var to `-std=c23` (via a `Once`) the first time ANY default-flavor
fixture translates in-process. tests/differential.rs's translate_cross_target
spawns a fresh `slate` subprocess that inherits whatever SLATE_CLANG_ARGS
happens to be in the test process at that moment -- so a cross-target
fixture's dialect was silently at the mercy of unrelated fixture execution
order/parallelism. My new fixture needs `asm("name")` (a GNU extension,
rejected under strict c23), which is what surfaced it: passed in isolation
(SLATE_DIFF_FIXTURE=...), failed intermittently in the full suite. Fixed by
always passing an explicit SLATE_CLANG_ARGS to translate_cross_target's
subprocess (empty by default) instead of leaving it to inherit ambient
process env, via a new cross_target_clang_arg_overrides(name) function
mirroring the existing fixture_clang_arg_overrides pattern. Verified stable
across 3 repeated full-suite runs after the fix.

lowering, rewrites, and libc profiles all green; fmt/clippy clean.
