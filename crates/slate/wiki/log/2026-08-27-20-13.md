# SCC-ordered call-graph worklist for string_params (slate-y0qs.4)

_2026-08-27 20:13:26_

Built src/backend/interproc/{mod.rs,string_params.rs}: a generic call-graph
+ Tarjan SCC + dirty-queue worklist engine (mod.rs), and the first fact
family wired to it (string_params: char* param -> &str lifting). Runs as
a whole-Program pass in engine::apply() before the per-function arena
worklist, per rewrite-engine-v2.md's "different problem" carve-out.

Ported the eligibility fixpoint from the dead facts::string_params.rs
(salsa-free: plain function/var names, no BindingId/FunctionId) and the
rewrite half from git show 366d9f8b~1:src/backend/query/rules/string_params.rs.
Worklist discipline: active param set starts optimistic (all candidate
params), only shrinks (monotone, guarantees termination), and on change
enqueues both direct callers and direct callees (eligibility is genuinely
bidirectional -- own reads/writes plus callers' arg liftability plus
callees' param activity).

Two scope narrowings vs the old algorithm, documented in the module doc:
libc string-call eligibility only checks the tracked arg's own slot (not
every pointer arg of the call); "liftable source" recognizes only the
common `let buf: [i8;N]=[0;N]; buf=[..,0];` literal-array shape instead of
a full string_buffer provenance fact.

Real complication: this phase runs before ZeroInit (per the wiki's explicit
ordering), so CIR's `let x = null; x = y;` idiom hasn't folded into `let x
= y;` yet -- alias-chasing had to see through both shapes itself
(find_zero_decl_then_assign_aliases), and the "established" write from that
idiom has to be excused from both the write-disqualification check and the
read-classification walk.

Getting tests/fixtures/string_param_lift.c to actually *compile* post-lift
required going beyond a literal port: promote the whole tracked alias
chain (not just param-name-direct aliases) to &str, insert `.as_ptr()`
before raw-pointer casts of promoted locals, and substitute known literal
array content as an inline &str literal at call sites (`forward_num("42")`)
instead of reusing a still-raw-pointer temp. Without this the signature
flip type-checked but the body didn't -- a real regression caught by
`cargo nextest r --release --profile rewrites` (which stashing confirmed
was 100% green pre-change).

Validation: rewrites 110/110 (1 unrelated flaky dep-info cache test,
confirmed passes standalone), lowering 10/10, libc 19/19. fmt/clippy clean.
libexpat (21 TUs, compile_commands.json): 10.52s before this slice's phase
was wired in, 10.53s after -- negligible marginal cost (interproc finds no
lift candidates in libexpat's real code under this filter). Whole-pipeline
wall time is already ~6.4x below the 67.4s y0qs.3 baseline, mostly from the
already-landed arena/worklist engine, not this slice specifically.

Scoped out (real gaps, not silently dropped): ptr_len family (bucket-2,
explicitly out of scope for .4); full string_buffer-style provenance
(would let more call-site sources lift than the literal-array special
case); indirect/fn-pointer calls (excluded from the graph, same as the old
code).
