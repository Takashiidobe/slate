# Project/library crate generation drops #![feature(f128)] for cross-file long-double shims

_2026-09-05 15:25:02_

Two related gaps in project/library-mode crate generation caused generated
crates to fail with E0658 "the type f128 is unstable" even though single-file
translate handles the same code correctly:

1. Each per-file Lowerer tracks its own uses_f128/uses_c_variadic/etc. flags
   and inserts #![feature(...)] into that file's own CrateAttrs via
   insert_crate_feature. That's correct for single-file translate (the file
   is the crate root) but wrong in project/library mode: if a *sibling*
   module (e.g. parse.c, not the file defining main) is the one that
   triggers the flag, the attribute lands on a non-root file, which rustc
   silently ignores, while the actual crate root (main.rs/lib.rs) never gets
   it.

2. lower_shared_types() (src/frontend/lowerer.rs) builds the shared `types.rs`
   module by hand and never sets uses_f128 at all, even when it pulls in
   f80_shim_decls()'s __slate_f128_nexttoward (f128 params/return) via the
   shared_types_use_long_double branch. Contrast with the per-file Lowerer,
   which explicitly checks f80_shim_decls() params for f128 before adding
   the same decls (lowerer.rs:1580-1587).

Fix:
- lower_shared_types now checks the f128-ness of f80_shim_decls() the same
  way the per-file Lowerer does, and calls insert_crate_feature so
  types.rs's own CrateAttrs at least carries the fact.
- Added ProjectModules::drain_module_features()/install_crate_features() in
  main.rs: after all per-module programs (including shared types.rs) are
  built, drain any Feature attrs a module inserted into its own CrateAttrs
  and re-home the union onto the actual crate root (src/main.rs, or the
  lib_rs string for --lib). Wired into all four project/library pipelines
  (translate-project, translate-project --compile-commands, --lib,
  --lib --compile-commands).

Verified: project_strtold and shared_long_double (translate-project) and the
library_crate_links_generated_c_abi_shim_for_long_double_libc_call fixture
now compile cleanly; full cross_tu suite only shows the two pre-existing
stale-FileCheck-snapshot failures (generated_cross_tu_filecheck,
generated_library_filecheck), confirmed present on baseline via git stash,
unrelated to feature attrs.

Fixes slate-59ie.
