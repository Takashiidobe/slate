# C++ translation pain points scoped ahead of CIR C++ support

_2026-08-25 09:51:47_

Pre-implementation scoping pass for eventual C++ support (CIR is C-only
today; C++ support expected within the year). Probed
~/llvm-project/build-cir/bin/clang -emit-cir and -ast-dump on small snippets
to ground the discussion empirically rather than speculate. Full writeup:
wiki/concepts/cxx-translation-pain-points.md.

Key findings:
- Templates lower to plain monomorphized cir.funcs (verified: add<int> ->
  cir.add, add<double> -> cir.fadd, separately mangled) — mostly "more
  functions," not a new lowering primitive.
- The C AST<->CIR join (source location -> one node) breaks for templates;
  fix is joining on the instantiation FunctionDecl's `instantiated_from` +
  TemplateArgument list against the CIR mangled symbol instead.
- Constexpr template metaprogramming (compile-time Fib) fully folds away
  before CIR — a non-issue, const fn covers it if ever needed.
- SFINAE: CIR shows only the winning instantiation, never the predicate.
  AST recovers it. Single-capability predicates (has-member) port to a
  hand-authored trait, even on stable Rust (autoref trick). Arbitrary
  expression-validity / priority-tag fallback chains have no Rust target at
  any stability level, nightly specialization included (it ranks impl
  specificity, not expression well-formedness) — real unsupported boundary.
- Move semantics need Option<T>/moved-flag scaffolding, not real Rust move,
  since C++ moved-from objects stay alive and destructible.
- RAII/exceptions, multiple/virtual inheritance, and static-init-order
  (SIOF) each need new pass machinery or an explicit unsupported boundary,
  not just more fixups.
- std lib support (string/vector/map/iostream) is libc-shim.md-shaped, just
  much bigger — a scale problem, not a design problem.
