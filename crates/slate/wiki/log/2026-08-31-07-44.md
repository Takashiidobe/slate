# Implement FreeBSD stdio, locale, and text-conversion ABI

_2026-08-31 07:44:15_

Implemented slate-sfzn.10.3. Real FreeBSD 15.1-RELEASE struct __sFILE
layout added in libc-shim/bits/freebsd/stdio.h (312 bytes, __mbstate_t at
offset 176, verified byte-for-byte against the oracle sysroot via
`clang -Xclang -fdump-record-layouts` on both my shim header and the real
sys/*.h — every field offset matched, including FreeBSD's __up pointer
field where Darwin instead has an __sFILEX* _extra field, and the trailing
_fl_mutex/_fl_owner/_fl_count/_orientation/_mbstate/_flags2 fields Darwin's
FILE lacks entirely).

fpos_t is a direct __off_t alias on FreeBSD (no wrapper struct like
Darwin's __fpos_t), stdin/stdout/stderr route through
__stdinp/__stdoutp/__stderrp exactly like Darwin.

locale.h: LC_* category numbering (0-6) matches Darwin's exactly, but
LC_*_MASK bit assignment does not — FreeBSD orders
COLLATE,CTYPE,MONETARY,NUMERIC,TIME,MESSAGES while Darwin orders
COLLATE,CTYPE,MESSAGES,MONETARY,NUMERIC,TIME. Gave FreeBSD its own
LC_*_MASK block rather than reusing Darwin's. freelocale() returns void
on FreeBSD (int on Darwin) — left FreeBSD on the existing default branch.
lconv's int_p/n_cs_precedes field order matches Darwin's, not the
generic/glibc branch's order.

langinfo.h: FreeBSD's nl_item numbering (CODESET=0..D_MD_ORDER=57) is
numerically identical to Darwin's, but Darwin gates YESSTR/NOSTR/
D_MD_ORDER behind __DARWIN_C_LEVEL macros that don't exist on FreeBSD, so
gave FreeBSD its own unconditional block instead of reusing Darwin's.

xlocale.h: FreeBSD only gets localeconv_l (matches its real xlocale.h
surface); skipped Darwin's LC_C_LOCALE/_c_locale globals, which have no
FreeBSD equivalent, and skipped the wider _l-suffixed function family
(strtol_l etc.) that FreeBSD's xlocale.h pulls in conditionally per
already-included header — out of scope for this ticket's stdio/locale
surface.

wchar.h/wctype.h: added __SLATE_LIBC_FREEBSD to the existing
POSIX/BIONIC/DARWIN visibility conditions for locale_t and the _l-suffixed
wide-char functions (no ABI divergence there, just visibility).

Added libc-shim/freebsd-stdio-locale-headers.txt (mirrors
macos-stdio-locale-headers.txt) and
freebsd_stdio_locale_header_manifest_compiles_for_x86_64_and_aarch64 in
tests/header_compilation.rs, with oracle-backed _Static_assert checks
(FILE size/offset, LC_* values/masks, langinfo values) for both
architectures.

Verified end-to-end: `slate translate` on a stdio-using fixture for both
x86_64/aarch64-unknown-freebsd produces a `#[repr(C)]` struct __sFILE
matching the real layout field-for-field; `cargo check --target
{x86_64,aarch64}-unknown-freebsd` against the generated Rust (with the
`libc` crate) succeeds on both. cargo fmt/clippy clean; nextest --profile
libc 24/24, --profile lowering 10/10.

Deliberately out of scope: iconv.h (mentioned in the ticket description
but not in the basic-stdio-locale manifest; no divergent iconv_t shape
found worth modeling yet), the wider xlocale _l-suffix surface, uchar.h
(already libc-agnostic, no change needed).
