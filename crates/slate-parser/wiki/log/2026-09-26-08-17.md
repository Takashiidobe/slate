# answer __has_attribute from attribute_support

_2026-09-26 08:17:05_

`__has_attribute` read a hand-copied clang tablegen list in pp/has_checks.rs that
ignored flavor and target, so gcc headers saw clang-only attributes and
`__has_attribute(dllimport)` was 1 on ELF. It now calls
`attribute_support::has_attribute(name, flavor, target)`.

The previous commit (dyd.46) regressed unmodeled-but-real attributes such as
`nonstring`: they parse as `Attribute::Unknown`, which then warned
-Wunknown-attributes although clang knows them. Registration now has a
fallback for names slate does not model: `src/attribute_support/registered.rs`,
generated by `tools/generate_attribute_lists.py`, which asks each installed
compiler`s own `__has_attribute` over every identifier in its binaries (clang
on 6 triples, gcc on x86_64/aarch64). sema warns on an `Unknown` only when
`spelling_registered` says the flavor does not know it either. The generated
clang list matches the old tablegen list except for ObjC-only names; it
replaces KNOWN_ATTRIBUTES.

Verified slate`s `__has_attribute` against clang (x86_64/aarch64/armv7 linux,
x86_64 windows) and gcc (x86_64, aarch64) over all modeled names: all match
except clang`s Windows-only `guard`, which the target-blind generated list
admits everywhere (accepted as permissive). Found and fixed on the way:
clang does not register `preserve_none` on arm32 (new `NotArm32` gate); gcc`s
`__has_attribute` also counts standard attributes with no GNU spelling
(`nodiscard`, `maybe_unused`, `_Noreturn`, `unsequenced`, `reproducible`);
and `__has_attribute(const)` / `(restrict)` were #if errors because keyword
arguments were rejected.

The three `sema/unknown_attributes_*.c` fixtures gained `__has_attribute`
probes and a `nonstring` declaration. Filed slate-parser-dyd.66 for
`__has_c_attribute`, which is still always 0.
