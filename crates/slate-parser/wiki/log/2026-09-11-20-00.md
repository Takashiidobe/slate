# Fix concretize_guard excluding a guard's own defining entry

_2026-09-11 20:00:51_

User asked "does this handle arbitrary nesting levels?" after wf8.1.19's
generalization landed. Hand-traced a 3-level self-nested guard case
(A > B > C, each defining itself then a final macro Z) and confirmed Z
itself resolves correctly at any depth -- but noticed concretize_guard's
rewrite filter (`definition.order > guard_order`, strict) excludes the
guard macro's OWN defining entry (order == guard_order exactly). Verified
the gap concretely: `#ifndef A / #define A 99 / #endif / int v = A;`
left `A` as an unresolved Identifier instead of expanding to `99`.

Fix in src/pp.rs concretize_guard(): switched the threshold from the
guard's own min order (`guard_order`, strict `>`) to `order_from` (the
macro_order captured before this branch's body was parsed, already used
for the pre-existing-guard bail-out), with `>=` on both the bail-out
check and the rewrite loop. This is a strict superset of the guarded
region including the guard's own #define, so its own condition now also
collapses correctly, with no effect on any of the previously-verified
cases (guard-then-value macro-uses only ever reference the guard's
result via later code, never affected by whether the guard's own
internal bookkeeping is fully simplified) -- reran every case verified
for wf8.1.19 (triple-nested self-guards, -D-divergent macro nested
inside a self-guard, real clang stdbool.h chain) plus the new
guard-uses-itself-as-a-value case, all still correct.

Extended tests/fixtures/header-guard.c with a guard whose own name is
then used as a value (`SENTINEL`, resolves to 7) and
tests/fixtures/nested-header-guard.c with a 3-level self-nested guard
chain (`TRIPLE_NESTED`, resolves to 3). Full cargo test and clippy pass.
