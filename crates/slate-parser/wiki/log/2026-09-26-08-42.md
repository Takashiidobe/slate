# Gate __declspec names per flavor and target

_2026-09-26 08:42:10_

slate-parser-dyd.65. The parser applied every modeled name under __declspec, so under the clang
flavor __declspec(packed) shrank a struct (5 vs clang's 8), mode(DI) widened int to
i64, aligned/weak/visibility/section/used changed the symbol, dllimport/dllexport set
dll_storage on ELF, and vector_size errored where clang accepts.

Measured clang 22 (-fdeclspec, linux/windows-msvc/windows-gnu): __declspec honors only
align, allocate, allocator, code_seg, cpu_dispatch, cpu_specific, deprecated, naked,
no_init_all, noalias, noinline, noreturn, nothrow, property, restrict, safebuffers,
selectany, thread, uuid, plus dllimport, dllexport, empty_bases, guard, layout_version,
novtable on Windows only. It never unwraps __name__. Everything else gets
'__declspec attribute X is not supported' [-Wignored-attributes] and is dropped.

attribute_support::declspec_registered holds that table (CLANG_DECLSPECS). gcc uses
gnu_registered, since mingw gcc defines __declspec(x) as __attribute__((x)) and gcc
rejects __declspec elsewhere. msvc accepts every modeled name: cl rejects unknown
ones (C2485), so being permissive there never changes a compiled result. An
unregistered name parses to the new Attribute::IgnoredDeclspec, and sema warns with
clang's wording.

Not modeled: clang without -fdeclspec on non-Windows rejects __declspec outright
(slate accepts, which is permissive), and a declspec on a struct tag does not warn
because tag attributes skip check_attributes. The result is still correct there.
