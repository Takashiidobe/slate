# _Bool atomic fetch arithmetic computes in the storage byte

_2026-09-20 14:56:41_

Atomic fetch arithmetic on a `_Bool` object was rejected with `atomic
arithmetic on non-integer`, because `fetch_computation` matches
`Type::Numeric(Integer)` and `Type::Bool` is a separate IR type. Clang
accepts it and emits `atomicrmw add ptr, i8` -- the operation runs in the
object's storage byte, which is the only way a `_Bool` can come to hold a
byte outside {0, 1}.

`arithmetic_object` now retypes a `_Bool` place to `unsigned char` before the
fetch, the same reinterpretation `flag_object` already does for a `void *`
flag, so the place keeps its `ptr<bool>` spelling while the operation is
`update<u8, ...>`. That shape is established precedent, not new.

The first attempt was wrong in a way worth recording: retyping the place also
retyped the operand conversion, so `__atomic_fetch_add(&b, x, 5)` converted
`x` straight to `u8`. Clang converts it to `_Bool` first (`icmp ne 0` then
`zext`), because the builtin's value parameter has the object's *declared*
type, so `x == 2` gives clang 1 and gave us 2. `FetchObject` now carries the
declared type alongside the retyped place, and the operand converts through
it: `from_bool<u8>(ne<i32>(x, 0))`.

The result converts back to `bool`, so the expression keeps its C type. This
is the one remaining divergence: clang materializes the `_Bool` by
truncating to the low bit, while the conversion back asks `!= 0`. They agree
on every byte in {0, 1}, so they can only differ on an object that already
holds a trap representation, whose use is undefined.

Only the arithmetic fetches need the storage view. `load`, `store`,
`exchange`, `test_and_set` and `clear` already worked and cannot put a
`_Bool` out of range, so they stay `bool` operations.

Verified against clang 22.1.8 for all ten fetch operations, both fetch forms,
the `__sync_`, `__c11_` and `__scoped_atomic_` families. Covered by a new
`flags` function in `tests/fixtures/sema/ir_atomic_extensions.c`.
