# Pin MSVC sysroots to the cl.exe oracle via xwin as a library

_2026-09-27 23:29:39_

slate-parser-v74.3 (fixed in ../slate-sysroots, uncommitted there for the user to commit).

Root cause was not just an unpinned xwin. xwin 0.10 (lib.rs get UCRT) takes the UCRT from the standalone Microsoft.Windows.UniversalCRT.HeadersLibsSources.Msi package whenever the manifest has one. In the VS 2022 manifest (17) that is UCRT 10.0.26624, older than the CRT: no corecrt_math.h, tgmath.h, stdalign.h or stdnoreturn.h, and no _UCRT_DISABLE_CLANG_WARNINGS, which breaks threads.h. The VS 2026 manifest (18) has no standalone package, and xwin then looks for the SDK's own 'Installers/Universal CRT...' payload with '/', while 10.0.26100 lists it with '\', so it fails. --crt-version/--sdk-version alone can't fix either case.

Changes in slate-sysroots:
- xwin is a library dependency; the xwin binary and XWIN env var are gone. The license prompt is on stdin, skipped with XWIN_ACCEPT_LICENSE.
- The package manifest is normalized before pruning: the standalone UCRT package is dropped and payload names use '/'.
- Pins: manifest 18, CRT 14.51 + SDK 10.0.26100; thumbv7a-pc-windows-msvc (new target, slate-parser-78x3.7) gets CRT 14.44.17.14 + SDK 10.0.22621, the last with ARM32. Older toolsets need the full 14.44.17.14 component version.
- SYSROOT-MANIFEST.txt records versions; doctor has a 'Universal CRT as new as the MSVC CRT' check.

Result: x86_64 UCRT is byte-identical to the msvc-wine oracle's; CRT headers are the same 14.51 build (crtversion.h matches; the rest differ only in CRLF, trailing newlines and msvc-wine's lowercased include paths). ARM32 libs are coff-arm and clang --target=thumbv7-pc-windows-msvc accepts windows.h/threads.h/tgmath.h. All four MSVC sysroots reinstalled; 4369 slate-parser tests pass.
Follow-up: slate-parser-v74.5 (_MSC_FULL_VER snapshot 36256 vs cl.exe 36257).
