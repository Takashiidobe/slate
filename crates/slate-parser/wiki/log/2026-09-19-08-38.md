# _Atomic layout promotion matches clang

_2026-09-19 08:38:07_

slate-parser-lh7.2.20: layout used the unqualified type, so
`_Atomic struct { char a[3]; }` was 3/1 instead of clang's 4/4.

clang's rule (ASTContext, Type::Atomic), confirmed against the local clang
for every supported triple: take the value type's layout, treat a zero size
as one byte, and if it fits in `getMaxAtomicPromoteWidth` round the size up
to a power of two and raise the alignment to match. Widths measured:
16 bytes on x86_64 and AArch64 (linux and msvc), 8 on i386 and armv7 — so
`_Atomic struct { char a[9]; }` is 16/16 on x86_64 but stays 9/1 on i386,
and `_Atomic long long` is 8-aligned on i386 where plain `long long` is 4.

The qualifier never attaches to an array type (C11 6.7.3p3), so an array of
atomic elements promotes each element: `_Atomic struct odd3 a[3]` is 12, not
16. `TypeResolver::qualified_storage(ty, atomic)` therefore threads the flag
down through array layers and promotes at the value type.

No `Type::Atomic` variant: lh7.2.10 deliberately models `_Atomic` as an
access property, and the flag is already available everywhere layout is
computed — `c.qualifiers` for a type name, `Field::access` for a member,
`Place::access` for `sizeof obj`. `unevaluated_type`, `Ordinary::Object` and
`assertion_operand_type` now carry that access alongside the type.

Not covered: a global's own promoted size is invisible in the dump (the IR
prints no size for globals), and record ABI classification does not model
atomic aggregates — it does not model plain aggregates either yet.
