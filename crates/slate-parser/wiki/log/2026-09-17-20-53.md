# Bit-precise integers follow C23 conversion rules

_2026-09-17 20:53:29_

slate-parser-3pt. The bead named one bug; there were three, all reachable
from the same C23 rule.

1. `Context::promote` promoted anything narrower than int, including
   `_BitInt(N)`. C23 6.3.1.1 exempts bit-precise types from the integer
   promotions, so `a8 + a8` was becoming i32 instead of i8b, and `~a8`,
   `-a8`, `+a8`, `a8 << 1` likewise.
2. The same rule applies to the default argument promotions. The variadic
   branch in `Lowerer::expr`'s call lowering widened `_BitInt(8)` to i32;
   clang passes `i8 signext`. Fixed the same way.
3. `Context::convert` emitted nothing when width and signedness matched but
   bit-precision differed, so the operand kept its old type while the
   operation was typed from the target. `a32 + i` printed
   `add<i32b>(read<i32b>, read<i32>)` — an operation whose own operands
   disagreed with it. Now emits an exact `reinterpret`, since `i32b` and
   `i32` share a value representation and only the type changes.

`usual_arithmetic` needed no change: its equal-width tie-breaks
(`sa && sb`, `pa && pb`) already encode C23's rank rule that a bit-precise
type ranks below a standard type of the same width. That only became
observable once (1) and (3) were fixed.

Oracles: 24 expressions checked against clang 22.1.8 and gcc 16.2.1, which
agree with each other and now with us on all of them. MSVC 19.51 (checked
via the Compiler Explorer API, /TC /std:clatest) does not implement \_BitInt
at all — it parses the keyword as an identifier — so there is no MSVC
behavior to match here. GCC needs no API: 16.2.1 is installed locally and
supports \_BitInt.
