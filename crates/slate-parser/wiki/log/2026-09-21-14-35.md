# Scope the asm IR redesign to the operand model

_2026-09-21 14:35:41_

Reviewed `todo/ir-asm-design.md` and `todo/msvc-asm-design.md` against the
current `ir::InlineAsm`, and rejected the docs' central proposal: parsing GNU
asm template bodies into a typed instruction IR.

Reason: Rust `asm!` is itself a template-with-placeholders format. Translating
`"movl 8(%[base],%[index],4), %[out]"` to `"movl 8({base},{index},4), {out:e}"`
is a substitution at the operand-reference sites. Lowering to
`mov.i32 mem{base,index,scale,disp}` and re-rendering AT&T returns the same
string while acquiring a per-target assembler plus a large `Opaque` hatch that
directives, prefixes, SIMD and non-x86 targets all fall into.
`AsmPiece::{Text, Operand}` is already the right body shape.

What is actually missing is the operand model around the body. Filed
`slate-parser-25m.11`-`.18`: target and dialect on the node; one GCC-numbered
operand list with a normalized direction; constraint letters resolved to
register classes; operand width; alternative selection; computed Rust options;
naked as a function kind; and the decision itself.

Two corrections to the docs, both landmines if left:

- The early-clobber mapping is inverted. GCC's plain `"=r"` lets the allocator
  reuse an input's register, which is Rust's *late* form: `"=r"`->`lateout`,
  `"=&r"`->`out`, `"+r"`->`inlateout`, `"+&r"`->`inout`.
- Operand width is mandatory, not cosmetic. AT&T `%0` for an `int` prints
  `%eax`; Rust `{0}` for `in(reg)` always prints the full-width register, so
  without a width-derived `:e`/`:x`/`:r` modifier the emitted asm silently uses
  the wrong register size.

Instruction reading stays scoped to the MSVC `__asm` frontend, where no
constraints exist and effects must be inferred — and even there it is
identifier resolution plus a flags table, not a typed instruction IR. The
MASM/`ml64` PROC/directive/unwind layer is out of scope: a standalone
assembler file format, not C. Both docs rewritten to match.
