# lex alignof as the C23 keyword

_2026-09-21 11:20:01_

C23 6.4.1 makes `alignof` a keyword spelling of `_Alignof`, but the lexer's
keyword table mapped only `_Alignof`, `__alignof` and `__alignof__`, so
`alignof(int)` lexed as an identifier and reached name resolution as
`unresolved ordinary name alignof`. The corpus sweep hid this behind
c23_language.c's leading `#warning` (slate-parser-dyd.13).

Fix follows the existing `bool` gate: new `StandardFeatures::keyword_alignof`
(`c23_keyword`, so Standard in c23/gnu23 and Rejected elsewhere) and a
`"alignof" if self.features.keyword_alignof.is_accepted()` arm in
`src/lexer.rs` producing `Token::Alignof`. Before C23 the spelling stays an
identifier, which is what lets `<stdalign.h>` define the macro.

`alignas` needed nothing: the parser already matches it as an identifier
alongside `_Alignas` in attributes.rs and stmt.rs, ungated, and that
pre-existing looseness was left alone.

c23_language.c:184's `alignof(int)` now parses as `AlignOf { ty: int }`
instead of `Call { callee: Identifier("alignof") }`; fixture regenerated.
ast-spec.md records which alignof spellings are always available and which
one is gated.

Closes slate-parser-dyd.41.
