# typeof() supports general expression operands (wf8.2.1)

_2026-09-12 19:48:08_

DeclaratorParser::parse_typeof_operand only handled a bare identifier/int-literal/string-literal as typeof's expression operand. Fixed by giving DeclaratorParser a typedef_names: &HashSet<String> field (populated at all ~7 construction sites from the caller's typedef_names) and routing the operand's already-extracted, depth-scanned token span through const_expr::Parser::parse_expression, wrapped as Expr::Const, mirroring how Parser::parse_expression handles the top-level statement grammar. This changes the rendered shape of previously-supported single-token operands too (TypeOf(Expression(Identifier(x))) -> TypeOf(Expression(Const(Identifier(x)))))), so regenerated FileCheck expectations for every fixture using typeof/typeof_unqual/__auto_type: c23_language.c, c23_typeof_unqual.c, gnu_auto_type.c, typeof-types.c, gcc-dg/c23-nullptr-5.c, and the two target fixtures gcc-dg/c23-tag-alias-7.c and gcc-dg/c23-tag-composite-10.c (typeof(*(1 ? &x : &y))). Verified via full before/after fixture diff (temporary catch_unwind instrumentation in tests/filecheck.rs, reverted) that only these fixtures changed status and nothing regressed.
