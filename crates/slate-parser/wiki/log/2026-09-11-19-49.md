# Support extern "C" { ... } linkage-specification blocks (wf8.1.17)

_2026-09-11 19:49:14_

Parser hit `extern "C" { ... }` as if starting a normal declaration and
failed with "expected declaration type, found StringLit(\"C\")". Clang
resource headers (stdatomic.h etc.) wrap their C++ interop sections in
this exact idiom, and since #ifdef conditions stay symbolic for the
polyvariant AST, both branches (with and without the \_\_cplusplus wrap)
must parse as valid C regardless of the real compile mode.

Fix in src/parser.rs: parse*top_level_item's PPNode::Code arm now detects
the exact token prefix [Extern, StringLit(*), LBrace] and dispatches to a
new parse_linkage_spec_block(), which finds the matching closing brace
across subsequent PPNodes (same brace-depth-counting style as
parse_tag_definition) and recursively parses the interior nodes via the
normal parse_decls() -- extern "C" is a no-op wrapper for a C-only
frontend, so its contents are just flattened into the surrounding decl
list.

Verified: minimal repro (extern "C" { int x; }), multi-declaration bodies
mixing plain declarations and multi-line function definitions, and a
trailing declaration after the closing brace. Added
tests/fixtures/linkage-spec.c with generated FileCheck output. Full
cargo test suite and clippy pass (pre-existing if_same_then_else warning
in pp.rs is unrelated).

Found but did NOT fix, filed separately as slate-parser-qwy: struct/union/
enum bodies written entirely on one physical line (e.g.
`struct Point { int x; int y; };`) already fail to parse today, with or
without extern "C" wrapping -- parse_tag_definition never checks for a
same-line closing brace the way parse_function's matching_brace() does
for function bodies.
