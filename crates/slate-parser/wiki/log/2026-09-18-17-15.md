# Enum underlying and enumerator types follow clang per standard

_2026-09-18 17:15:49_

slate-parser-47s.5: checked clang c89..c23/gnu: an enumerator outside int, a fixed underlying type and a trailing enumerator comma are all only extension warnings before C23 (-Wc23-extensions / -Wc99-extensions), never errors, so nothing is rejected (matches feature-availability-not-target-gated). What differs is typing, now fixed in sema/types.rs. Underlying (no fixed type): any negative -> int if all fit int else long; none negative -> unsigned int if all fit u32 else unsigned long. This is mode independent and corrects enum { A, B } from i32 to u32 (clang/gcc use unsigned int). Enumerator type: int when no fixed type and all values fit int; otherwise the underlying type pre-C23 and the enum type itself in C23 (StandardFeatures::enumerators_have_enum_type), decided per enum not per enumerator (clang types Q0=-1 as long when a sibling is out of int). C23 enumerator refs then cross enum_to_int. Known gap: clang keeps a C23 enumerator at unsigned int when its literal type equals the underlying (enum P { P0 = 0x80000000 }); we use the enum type. Enum values above i64 (0xFFFF...ull) remain unsupported. Fixtures: ir_enum_typing_c89.c and _c23.c; regenerated 5 enum fixtures (underlying i32 -> u32). ir-spec.md updated.
