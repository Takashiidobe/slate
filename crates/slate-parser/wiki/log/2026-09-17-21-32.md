# StandardFeatures replaces ad-hoc LanguageStandard predicates

_2026-09-17 21:32:41_

`slate-parser-47s.1`. New `src/standard_features.rs` holds `StandardFeatures`,
derived from `LanguageStandard`, plus an `Availability` tri-state
(`Standard` / `Extension` / `Rejected`). Lexer, parser, `const_expr`, and
sema now read named fields instead of calling `is_c23_or_later()` and
friends; those three predicates are deleted from `LanguageStandard`, which
keeps only `stdc_version` (the `__STDC_VERSION__` macro value still needs
the raw standard).

Two shape decisions worth keeping:

**`Availability` vs `bool` per field.** A field is `Availability` when the
question is "may source use this construct" — something a future `-pedantic`
can diagnose: the four C23 keyword spellings and `implicit_int`. It is a
plain `bool` when the rule is a semantics fork with no diagnostic:
`control_statement_scopes`, `auto_type_inference`,
`empty_parens_are_prototype`, `main_implicit_return_zero`. Pre-C23 `auto x =
1;` is the clearest case — it isn't rejected, it parses as implicit int with
storage `auto`, so it's a fork, not an acceptance question.

**No `CompilerFlavor` parameter yet**, against what the bead's acceptance
criteria said. Nothing migrated here varies by flavor. `47s.3` adds it with
`keyword_typeof`, which is a keyword in the gnu modes and c23 but not in
strict c99/c11/c17 — flavor and gnu-ness, not version. `Availability::
Extension` likewise has no constructor until then; every feature here is
`Standard` or `Rejected`.

Verification: `cargo nextest run --release` passes with two fixtures moved
aside (`gcc-dg/pr85388-4.c`, `gcc-dg/split-4.c`). Those two fail identically
on the unmodified tree — stale absolute tag ids that shift with the local
system-header snapshot, filed as `slate-parser-45s`.
