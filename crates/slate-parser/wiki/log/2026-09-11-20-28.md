# wf8.1.18: lexer/parser fixes surfaced by string.h bisection

_2026-09-11 20:28:14_

Investigating slate-parser-wf8.1.18 (string.h/stdlib.h parse failure under libc-shim + clang resource headers) via bisection turned up three unrelated, pre-existing parser bugs, none matching the originally-filed symptom:

1. src/lexer.rs: **inline/**inline** (clang/glibc GNU spellings of inline) weren't aliased to Keyword::Inline, unlike **restrict/**restrict** which already had aliases. Fixed by extending the match arm.

2. src/parser.rs parse_function: function _definitions_ (with a body) returning a pointer type failed with 'expected function name', because the hand-rolled return-type/name-finding logic never consumed '_' tokens between the base type and the function name (ordinary non-function declarations get this via Declarator::Pointer, but FunctionDecl.ret_type has no separate declarator field). Fixed by adding a loop that folds each leading '_' into ret_type as CType::Pointer before locating the name. No existing fixture ever caught this.

3. src/parser.rs parse_function: signatures were assumed to fit in nodes[0], but each physical source line is its own PPNode::Code, so a wrapped parameter list (e.g. 'int add(int a,\n int b) { ... }') failed with 'expected )'. Note: this is unrelated to the pp.rs splice_continuations() backslash-newline mechanism, since there's no backslash here -- ordinary C allows bare newlines inside parens. Fixed by adding signature_node_span()/join_node_text() helpers that join leading PPNodes by paren-balance before lexing the signature.

Bisecting stdlib.h further (past these three fixes) found a fourth, separate gap: compiler builtin type macros like **UINTPTR_TYPE** aren't seeded, so declarations using them fall through to expression parsing. This is out of scope for wf8.1.18 and filed separately as slate-parser-g6b.

Added fixtures: tests/fixtures/inline-keyword-aliases.c, tests/fixtures/pointer-return-type.c, tests/fixtures/multiline-function-signature.c. Full cargo test and clippy pass.
