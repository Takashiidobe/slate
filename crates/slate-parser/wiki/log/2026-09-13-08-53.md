# Move float literal bit extraction from const_expr.rs to Token

_2026-09-13 08:53:25_

FloatValue::LongDouble was still a String -- unlike Half/Single/Double/Quad, which
are already typed (u16/f32/f64/u128 bits) -- and all the digits-to-bits conversion
lived only in const_expr.rs's FloatLiteral::parse, with no Token-level equivalent
of Token::integer_value()/integer_value_i128() (lexer.rs) for floats at all.

Added Token::float_value_f16/f32/f64/f80/f128 (lexer.rs), each backed by a private
Token::apfloat_bits<F: rustc_apfloat::Float>() helper -- same shape as
integer_value_i128: operates on a Token::FloatLit's raw spelling, returns None if
not a float token or unparseable. float_value_f80 uses rustc_apfloat's
ieee::X87DoubleExtended (BITS=80), matching how this target already treats
sizeof(long double) == 16 (padded 80-bit extended) elsewhere in the codebase.

const_expr.rs::FloatLiteral::parse keeps owning suffix-detection and the
imaginary-marker double-strip (that interplay is const-expr-level, not something
Token should know about) but now builds a throwaway `Token::FloatLit(digits)` and
calls the new methods instead of a private apfloat_bits free function -- same
pattern parse_primary already uses for integers
(`Token::IntLit(value.clone()).integer_value()`).

FloatValue::LongDouble(String) -> LongDouble(u128) (bits, #[debug(format="{:#x}")]
like Quad). Display's LongDouble arm changed from `{digits}L` to `f80:{bits:#x}`
to match Half/Quad's tagged-hex style instead of echoing original spelling.

Regenerated 24 fixtures referencing LongDouble(...) via update_filecheck.py.
Decimal32/64/128 (\_Decimal\*, GNU/C23 decimal FP) were NOT touched -- rustc_apfloat
has no decimal-floating-point support, so those stay string-based; only the binary
IEEE formats (now including x87 extended) got typed.
