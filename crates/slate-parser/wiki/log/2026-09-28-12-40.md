# Type oversized integer literals the way gcc does

_2026-09-28 12:40:25_

slate-parser-cxg.6, cluster B (format/unnamed-1.c, format/ms_unnamed-1.c, pr79788-1.c, pr79788-2.c).

gcc's rule, measured with gcc -S on x86_64 and -m32: cpplib evaluates a literal in intmax_t precision, so a literal wider than 64 bits is truncated ('integer constant is too large for its type'); the normal candidate list then runs on the truncated value (99999999999999999999 is long); a signed-only literal that still fits nothing gets gcc's widest literal type (__int128 on 64-bit targets, long long otherwise), keeping its bits ('integer constant is so large that it is unsigned'). So 18446744073709551615 and 9223372036854775808LL are __int128 on x86_64, and 18446744073709551615 is long long -1 on i686. Slate followed clang (unsigned long long fallback, reject past u64), which changed values under the gcc flavor, e.g. -18446744073709551615.

select_integer_candidate now returns IntegerLiteralSelection {rank, signed, value: ir::Number, truncated, widest_fallback}; the wrapped i686 case uses Number::SignedInteger. Truncation applies in every flavor (clang and cl reject, gcc warns: accept per reject-only-on-consensus) under a new Warning::IntegerLiteralTooLarge (slate-named, gcc has no -W for it). The widest fallback is gcc-only via StandardFeatures::widest_integer_literal_fallback.

Root cause of the fallback not firing at first: sema built StandardFeatures::new(standard) in four places, dropping the flavor layer the preprocessor added. Added StandardFeatures::for_compiler(standard, flavor, target) and used it in pp and all sema sites; removed pp's microsoft_extensions_enabled and with_microsoft_extensions.

Fixture changes: c99-intconst-2.c now lowers 9223372036854775808LL as i128 (gcc agrees); error/clang literal_diagnostics_all_contexts.c now shows the truncation warning in each context. New gcc/linux/{x86_64,i686}/integer_literal_widest_fallback.c; format.h copied beside format__unnamed-1.c.
