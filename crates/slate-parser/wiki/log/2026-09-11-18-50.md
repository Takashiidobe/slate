# sizeof(type-name) support in const_expr parser

_2026-09-11 18:50:08_

Fixed slate-parser-wf8.1.11: const_expr::Parser::parse_unary's sizeof branch only ever parsed sizeof(<expr>) via parse_comma(), so sizeof(unsigned long) etc. hit ExpectedRParen and hard-panicked at parser.rs:1483's array-bound evaluation (unwrap_or_else(panic!)).

Fix: mirror the existing _Alignof handling — try try_parse_type_name first (matching starts_type_name), and only fall back to expression parsing if that fails. Added ConstExpr::SizeOfType{ty, declarator} plus declarator_size/ctype_size in const_expr.rs to actually compute byte sizes for primitive int/float/pointer/array types (LP64 assumptions: long=8, pointer=8, etc.), so array bounds like bits[128 / sizeof(unsigned long)] evaluate to a real value instead of erroring. sema.rs's is_integer_constant_expression updated for the new variant.

Regenerated tests/fixtures/attribute-expressions.c CHECK lines via tools/update_filecheck.py since sizeof(int) now parses as SizeOfType instead of SizeOf(Identifier("int")) — the new form is the correct one.

Repro'd against tests/upstream/fixtures/add.c via #include <stdio.h> -> libc-shim headers -> bits/types.h's __sigset_t. That panic is now gone; hit a new, unrelated blocker (anonymous struct/union bodies as member types) immediately after, filed as slate-parser-wf8.1.12.
