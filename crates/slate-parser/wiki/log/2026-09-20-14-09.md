# Floating atomic fetch min/max lower to minnum/maxnum

_2026-09-20 14:09:24_

`__atomic_fetch_min/max`, `__atomic_min/max_fetch` and the `__c11_` forms
on `float`/`double` were rejected with `atomic arithmetic on non-integer`.
Clang emits `atomicrmw fmin`/`fmax` for them (verified with clang 22), which
is NaN-ignoring: `fmin(old, NaN)` is `old`. The existing integer lowering is
`conditional(lt(old, v), old, v)`, which answers NaN when `v` is NaN, so it
could not be reused.

Added `ArithOp::MinNum`/`MaxNum` (printed `minnum`/`maxnum`) and lowered the
floating fetches to `minnum<T, rounding=..., exceptions=...>(old<T>, v)` with
the ambient floating semantics. Integer min/max keep the compare-and-select
form, which is exact for them.

Named `minnum`/`maxnum` rather than `min`/`max` because clang's
`__atomic_fetch_fminimum`/`fmaximum` family is NaN-propagating and orders
`-0` below `+0`; it will need separate ops, and `min` would have had to be
renamed then. That family is still unsupported (slate-parser-lh7.2.37).

`__sync_fetch_and_min/max` stay integer-only — clang rejects a `float *`
there.

The two exhaustive `(NumericType, ArithOp)` matches in `sema/numeric.rs`
gained arms for the new ops; both are unreachable, since no `BinaryOp` maps
to them.

Covered by a new `extrema` function in
`tests/fixtures/sema/ir_atomic_extensions.c`, which also keeps an integer
`__atomic_fetch_min` to show the compare-and-select path is unchanged.
