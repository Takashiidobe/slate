# \_\_builtin_complex works; multi-line macro invocations now expand (wf8.2.3)

_2026-09-12 20:07:08_

gcc-dg/complex**builtin-complex-1.c's failure wasn't about **builtin_complex at all (that already parsed fine as a generic call via const_expr's postfix-call support) -- it was a real, previously-unknown preprocessor bug: expand_macros ran per physical source line, so a function-like macro invocation whose argument list spans multiple lines (extremely common, e.g. VERIFY(...)/ALL_CHECKS(...) wrapping in this fixture) was never expanded; the unexpanded macro name then parsed as an ordinary call, which broke once an unexpanded argument was a type-name like 'long double' rather than a valid expression. Fixed via merge_open_lines in src/pp/syntax.rs: joins consecutive non-directive logical lines whose net paren/bracket depth is still positive, so macro expansion sees the whole invocation. Two correctness traps found and fixed along the way (both documented in wiki/concepts/pp-logical-line-merging.md): must never merge across a #directive line (c11.c selects a printf argument via #ifdef mid-call), and must defer a continuation line's trailing comment to its own entry after the merged line rather than bundling it into the head, or several guality**\* fixtures' comment/Unreachable-wrapping placement shifts. Verified via full before/after fixture diff (temporary catch_unwind instrumentation in tests/filecheck.rs, reverted) that only complex**builtin-complex-1.c, c23-bool-1.c, c23-tag-alias-7.c, and c23-tag-composite-10.c changed status, plus regenerated 5 guality\_\_pr45003/pr58791 FileCheck goldens whose comment position shifted (more correct, not less: comment now follows its own asm statement instead of the following return). Nothing else regressed.
