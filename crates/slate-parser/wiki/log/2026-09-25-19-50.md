# C23 tag redefinition members: per-flavor C-type rule replaces the ir::Type pre-filter

_2026-09-25 19:50:42_

slate-parser-ntb: removed same_tag_content, the ir::Type field pre-filter on C23 same-scope tag redefinitions. The bead proposed dropping it and letting CTypes::compatible decide, but measuring showed the pre-filter was load-bearing: clang 22 and gcc 16 both reject redefinitions whose members are only compatible (int (*)[] vs int (*)[3]; void (*)() vs void (*)(int)), so compatible alone would accept code neither compiler does. The real split is narrow: clang treats an enum and its underlying integer type as equivalent at any depth (direct, pointer, array element, function parameter, fixed underlying types), with qualifiers still required equal; gcc requires the same type (typedefs transparent). Since CompilerFlavor already reaches TypeResolver, this is now correct per compiler: same_field_types takes the member comparison; the redefinition path passes CTypes::same_or_enum_underlying (new, clang flavor) or CTypes::same (gcc, MSVC); cross-scope join_compatible_tag passes CTypes::compatible. The 14-case probe matrix matches clang and gcc in both flavors except cross-scope int (*)[] vs int (*)[3] under clang, where clang rejects and slate accepts (gcc accepts; permissive, accepted). Also measured: enum E : long redefined as enum E : long long is accepted because same_tag_shape compares enum underlying as ir::Type (both i64); both compilers reject; permissive, recorded in wiki and not filed. Fixtures: tests/fixtures/sema/c23_tag_redefinition_enum_underlying.c (clang flavor, plus INCOMPLETE_ARRAY and QUALIFIED error configurations) and gcc_c23_tag_redefinition_enum_underlying.c (gcc flavor, DIRECT and POINTER error configurations); each configuration checked against the matching real compiler. Updated wiki/concepts/c-type-layer.md. Verified with cargo clippy --allow-dirty --fix, cargo fmt, cargo nextest run --release (pass).
