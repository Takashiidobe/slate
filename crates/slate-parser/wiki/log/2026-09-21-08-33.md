# __atomic_* on _Atomic objects follows GCC, not clang

_2026-09-21 08:33:13_

Closed lh7.2.42 as not-a-bug after checking GCC.

The bead claimed slate-parser wrongly accepts the GNU `__atomic_*`
builtins on an `_Atomic`-qualified object, since clang rejects
`__atomic_fetch_add(&ai, 1, 5)` for `_Atomic int ai` with "address
argument to atomic operation must be a pointer to integer, pointer or
supported floating point type".

GCC 16.2.1 accepts it, silently -- no diagnostic even under
`-Wall -Wextra -pedantic -std=c23` -- and lowers it identically to the
unqualified form (same `lock xaddl %eax, ai(%rip)`). GCC also accepts
`__atomic_store` on an oversized `_Atomic` struct, which clang rejects
as non-trivially-copyable. So this is clang-specific strictness, not
invalid C.

Decision: match GCC, i.e. keep the current permissive behavior. The
pipeline's job is ingesting real-world C, and most of that is built
with GCC; a clang-only check would only narrow what we can take in,
for a diagnostic nothing consumes. Our existing lowering was checked
against GCC semantics for both the scalar and the struct case and is
correct (`update<..., atomic=seq_cst>` and
`write<..., atomic=seq_cst>` respectively).

If a clang personality is ever added, the check belongs there and
nowhere else. The implementation hook is that `AtomicBuiltin`
(src/sema/atomic.rs) carries `scoped` but not the prefix it was parsed
from, so `atomic_object` cannot currently tell the `__atomic_*` family
from the `__c11_atomic_*` one.
