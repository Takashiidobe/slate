# C23 [[attribute]] placement in declarators and file-scope attribute declarations

_2026-09-29 17:50:19_

slate-parser-cxg.4. The declarator suffix loop read `[[` as an array bound, so `int a [[x]]`,
`void f [[x]] (void)`, and `int f(void) [[x]]` failed. `[[...]]` after the identifier or an
array/function suffix now parses (parse_c23_attribute_groups, C23 syntax only) into
`Declarator::Attributed`; GNU attributes there still end the declarator.

Decision (with the user): treat C23 type-position attributes roughly like GNU `__attribute__`,
i.e. as declaration attributes. Modeling each position was measured first (gcc 16.2, clang 22.1):
both drop declaration-only attributes after a suffix or type specifier with "ignored" (clang errors
on some), and honor type ones (format, nonnull, access, reproducible, unsequenced, aligned,
conventions). The only payoff was the warnings and not applying dropped attributes, which is the
accepted permissive case. Recorded in attributes.md#c23-placement.

`DeclarationSpecifiers::attributes_with(declarator, trailing)` replaces `function::attributes` and
the ad-hoc specifier+trailing chains for objects, typedefs, parameters, fields, and reachability;
it skips nested calling conventions (derive applies them to the type; including them put
CallingConvention in c_attributes of `int (__fastcall *table[2])(int)`). field_request also reads
the nested layers.

Also: file-scope `[[x]];` is `DeclKind::Attribute` (gcc warns ignored, clang silent);
`[[fallthrough]];` outside a switch is accepted under gcc (only a pedwarn); gcc `__has_cpp_attribute`
= `__has_c_attribute`, falling back to `__has_attribute` for unscoped names; gcc `auto` accepts a
grouped or attributed identifier. Migrated 11 gcc.dg fixtures. c23-auto-1.c still needs bit-field
deduction (cxg.55); c23-attr-{reproducible,unsequenced}-5.c need __builtin_has_attribute (cxg.44).
