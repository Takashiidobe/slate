# MSVC _Atomic layout: lock word instead of power-of-two promotion

_2026-09-21 09:09:16_

slate-parser-rol. --flavor=msvc was on clang's atomic promotion rule, which
is wrong for MSVC's /experimental:c11atomics. Measured cl.exe 19.51 on
x86_64-pc-windows-msvc and modelled the result.

The rule: a value already at a lock-free width (1, 2, 4, 8) keeps its size
and is aligned to it; anything else gets a leading four-byte lock, laying out
like struct { int lock; T value; }. So char a[3] is 8/4 (clang 4/4, gcc 3/1),
char a[16] is 20/4, struct { double d; int i; } (16/8) is 24/8. The lock
leads the object, so it reaches enclosing member offsets too.

Only size and alignment are modelled, no hidden field: C forbids reaching a
member of an atomic aggregate, so interior offsets are not observable.

Surprise worth recording: MSVC's over-alignment in the lock-free branch is
spelling-dependent. _Atomic struct S (size 4, align 1) is 4/4, but _Atomic T
and _Atomic(T) through a typedef of that same struct are 4/1. The lock branch
agrees across all three spellings. Not reproduced — layout() cannot see the
spelling, and an 8-byte lock-free atomic at align 1 cannot be accessed
atomically, so the elaborated-specifier answer is used everywhere.

TypeResolver::promotes_atomic_layout (a bool) became atomic_layout, a
three-way dispatch on CompilerFlavor delegating to TargetInfo::atomic_storage
or the new msvc_atomic_storage. Fixture
tests/fixtures/sema/x86_64-pc-windows-msvc/ir_atomic_layout.c; every layout
number in it was cross-checked against cl.exe. ir-spec.md and
c-type-layer.md updated.
