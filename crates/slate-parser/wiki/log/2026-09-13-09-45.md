# wf8.4: port fixtures 251-500, triage 15 failures into 5 bug tickets

_2026-09-13 09:45:37_

Ported the next 250 gcc-torture fixtures (alphabetically sorted,
tests/upstream/fixtures.gcc-torture 251-500) into tests/fixtures/gcc-torture/
under a new task slate-parser-wf8.4 (child of wf8, sibling of the now-closed
wf8.3). 235 parsed cleanly and were ported directly via
tools/update_filecheck.py. Learned the hard way: `while read -r f; do
python3 ...; done < file.txt` deadlocks/desyncs when the inner command's
subprocess inherits stdin from the same fd the while-loop is reading its
line source from -- use `mapfile -t arr < file.txt; for f in "${arr[@]}"`
(or redirect the inner command's stdin from /dev/null) instead. Also:
xargs -P for a batch of independent subprocess-spawning CLI invocations
(here, update_filecheck.py runs slate-parser + FileCheck per fixture) is
~50x faster than a serial loop -- 235 fixtures went from minutes to 4.7s.

The remaining 15 failures were triaged (not fixed) into 5 precisely-scoped
bug tickets under slate-parser-wf8.4, each with a minimal repro and a named
root-cause location, so a fresh agent can act on each directly:

- wf8.4.1 (3 fixtures): a deliberate recursive self-include idiom
  (`#ifndef T ... #include self ... #else T(...) #endif`, used to generate
  code combinatorially) gets flagged as `IncludeCycle` because
  `pp::mod::include_guard`'s guard-recognition heuristic only matches the
  narrow single-branch `#ifndef X / #define X` header-guard shape. Even a
  looser heuristic wouldn't be enough here -- the existing skip-on-guard
  behavior (return empty) is semantically wrong for this idiom (it needs
  to actually re-parse the `#else` branch, not produce nothing).
- wf8.4.2 (1 fixture): `parse_top_level_item`'s function-vs-declaration
  dispatch assumes at most one top-level construct per PPNode, so a macro
  expansion producing `struct S sS; struct S retmeS(...) { ... }` (a
  declaration followed by a function def, both from one `##`-pasting
  macro invocation) gets misparsed as a single malformed function.
- wf8.4.3 (8 fixtures, the biggest win): `__builtin_va_arg` was never
  given const_expr.rs special-case handling like offsetof/bit_cast/generic
  get, so it falls through to generic Call-argument parsing and chokes on
  the type-name second argument. `va_arg(ap, T)` in <stdarg.h> expands to
  exactly this, so this one ticket covers both the 20041214-1 and all 7
  931004-*.c fixtures.
- wf8.4.4 (2 fixtures): parse_tag_definition's trailing-declarator/
  initializer/semicolon scan (both the same-line-close fast path and the
  multi-line-close fallback) only ever looks at the single PPNode holding
  the closing `}`, never scans forward across further nodes -- so a
  multi-line array initializer, or an `#ifdef`-split `__attribute__` +
  terminating `;`, gets silently dropped and the leftover nodes get
  misparsed as bogus new top-level items. Also flagged in passing:
  build_tag_alias_decl (from wf8.3.7) still hardcodes `initializer: None`.
- wf8.4.5 (1 fixture, likely more later): `__const` (GNU/glibc header
  alias for `const`) isn't in the lexer's keyword table (unlike the
  existing `__restrict`/`__complex` aliases), so it's silently accepted
  as a bogus named type via parse_base_type's unguarded
  `Token::Ident(name) => CType::Named(name)` catch-all.

No src/ changes in this session -- purely porting + triage, per explicit
instruction not to fix these now.
