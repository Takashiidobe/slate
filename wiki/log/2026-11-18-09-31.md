# slate-yar4.44 length_lattice rewrite_signature_expr: lifted &[T] call inside struct/array literal, closure, atomic, loop head kept raw (ptr, len) args

_2026-11-18 09:31:10_

- bead: slate-yar4.44
- kind: bug
- area: crates/slate/src/backend/interproc/length_lattice.rs

Outcome: the length-lattice signature rewriter now walks every Expr and Stmt child in the same pre-order as `collect_calls`, so calls to a lifted `&[T]` function inside aggregates, closures, atomics, loop heads, and match guards are bridged and proofs stay paired with their call sites.

Symptom: `signature_call_sites` collects one `CallProof` per call with `Expr::collect_calls` / `stmt_collect_calls` (every variant, pre-order). `rewrite_signature_expr` was a hand-written match ending in `_ => {}`, so it skipped StructLit, ArrayLit/VecLit, closures, atomics, CopyNonoverlapping/PtrCopy/WriteBytes, etc. A skipped call kept the raw `(ptr, len)` args against the lifted signature (E0061), and its proof stayed in the per-(caller, callee) VecDeque, so a later call popped the wrong proof.

Reproducer:
    static int sum(int *v, int n) { ... }
    struct pair p = {sum(values, 3), sum(values, 3)};
    int arr[2] = {sum(values, 3), sum(values, 3)};

Cause: `rewrite_signature_expr` / `rewrite_signature_stmt` in crates/slate/src/backend/interproc/length_lattice.rs diverged from `collect_calls`. The rewriter also popped proofs after it recursed into args (post-order), not pre-order. On the stmt side it skipped `For::iter`, `While::cond`, and `Pattern::Guarded` conds, and it visited LetIf as then_body, else_body, then_value, else_value instead of then_body, then_value, else_body, else_value.

Fix: `pop_call_proofs` pops a call's proofs before it recurses. `expr_children_mut` lists children in `collect_calls` order. `bridge_call_args` rewrites the args after the recursion. The stmt walker now matches `stmt_collect_calls`.

Regression test: crates/slate/tests/fixtures/length_lift_call_in_aggregate.c (struct literal, array literal, while condition, ternary).

Limits: `sum(values, 2)` on a 3-element array blocks the lift for the whole function. That is a separate analysis limit, not a walker bug.
