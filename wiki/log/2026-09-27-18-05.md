# Hoist tied asm input effects in source order

_2026-09-27 18:05:27_

Fixed slate-parser-25m.20. A tied input ("0"(expr)) is folded into its output's operand slot. effects_statements hoisted input effects in operand order, so a tied input's side effects ran before untied inputs written ahead of it in source.

clang and gcc both evaluate asm inputs in source order after the outputs. Checked with asm(... : "r"(a++), "1"(a *= 10), "0"(a -= 3), "r"(a <<= 1)): clang -emit-llvm and gcc -S both do ++, *10, -3, <<1.

Fix: InOut's input is now Option<AsmTiedInput { value, operand }>, where operand is the source operand number that the fold otherwise loses. InlineAsm::inputs_in_source_order merges the tied inputs (sorted by source number) with the untied inputs, which are still in list order after the outputs. The input pass in effects_statements walks that order. The printer is unchanged: the source number is observable through hoisting order, so the IR grammar did not change.

Fixture: tied_order in tests/fixtures/sema/ir_asm.c. ir-spec's Inline asm section no longer lists this as a known deviation.
