# Atomic fetch fminimum/fmaximum lower to NaN-propagating extrema

_2026-09-20 14:18:24_

Added `ArithOp::Minimum`/`Maximum`/`MinimumNum`/`MaximumNum` (printed
`minimum`, `maximum`, `minimum_num`, `maximum_num`, matching both the C
builtin spellings and LLVM's intrinsic names) and lowered
`__atomic_fetch_fminimum`/`fmaximum`/`fminimum_num`/`fmaximum_num` to them
with the ambient floating semantics. Unlike `fmin`/`fmax` (lh7.2.33), these
propagate NaN and order `-0` below `+0`, so no compare-and-select form
expresses them.

The four builtins exist only in the `__atomic_fetch_<op>` spelling: clang has
no `__atomic_fminimum_fetch`, no `__c11_atomic_fetch_fminimum` and no
`__sync_` form. Replaced the two ad-hoc negative filters in `sync_builtin`
with one `FetchOp::spelled_as(FetchSpelling)` gate covering all five parse
sites, so each family only accepts the operations it actually spells. It is
exhaustive over `FetchOp`, so a new operation has to say where it is spelled.
A rejected spelling is not an atomic builtin at all and falls through to
ordinary name resolution, which reports `unresolved ordinary name` -- clang
says "call to undeclared function".

A floating extremum on a non-floating object is `ResolveError::Invalid`
rather than `Unsupported`; it is ill-formed input, not a gap.

CAVEAT: the locally installed clang 22.1.8 does not have these builtins at
all -- `src/sema/clang_builtins.rs` is generated from something newer. The
semantics come from LLVM's LangRef, not from a local oracle diff.

Covered by a new `propagating` function in
`tests/fixtures/sema/ir_atomic_extensions.c`.
