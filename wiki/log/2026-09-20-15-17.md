# FileCheck scratch files use tempfile RAII instead of manual removal

_2026-09-20 15:17:56_

The explicit `remove_file`/`remove_dir` calls in `tests/filecheck.rs` were
skipped on any panic between creating a scratch file and removing it -- and
a failing fixture panics, so the normal development case was the leaking
case. Thousands of tiny leftover directories under `target/filecheck` are a
btrfs *metadata* problem rather than a bytes problem, which is what exhausted
the disk: `df` showed 54G free while `Device unallocated` was 1.05MiB and
metadata was 94.91% full.

Replaced all four scratch paths with `tempfile`:

- The FileCheck input directories are now `tempfile::tempdir()`, which also
  moves the churn off `/home` to the system temp dir (tmpfs here), so btrfs
  never sees it. The self-include directory already used `std::env::temp_dir`,
  so this follows existing convention in the file.
- The stripped copy of a fixture is a `Scratch`, a drop guard. It stays beside
  the original as a `NamedTempFile`, since relative includes resolve against
  the fixture's directory; a self-including fixture instead gets a `TempDir`
  with the copy under the fixture's exact name, so the include finds itself.

On a genuine FileCheck failure the work directory is now kept via
`TempDir::keep()` and its path named in the panic message. Previously the
input was deleted before the assert, so there was nothing left to inspect;
now cleanup still happens on success and on unexpected panics.

`slot` existed only to make scratch names unique across parallel jobs, which
`tempfile` does itself, so it is gone from `FixtureJob` and both runners.
That drops `run_error_fixture` to seven parameters and its
`expect(clippy::too_many_arguments)` with it.

Verified by breaking a fixture: the failure names the kept input, the file is
readable afterwards, and the beside-fixture copy is still cleaned up while
unwinding. A passing run leaves nothing in `tests/`, `/tmp` or
`target/filecheck`.
