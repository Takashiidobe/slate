# slate-parser-bcpcomma gcc: __builtin_constant_p of a comma expression folded to 1

_2026-11-18 09:51:58_

- bead: slate-parser-bcpcomma
- kind: bug
- area: crates/slate-parser/src/sema/types.rs
- area: crates/slate-parser/src/sema/expression.rs
- flavor: gcc

Outcome: under --flavor=gcc, `__builtin_constant_p` of a comma expression (parenthesized or not) is 0, matching gcc; clang flavor still folds it to 1.

Symptom: `int a = __builtin_constant_p((0, 1));` gave 1 under --flavor=gcc; gcc 16 gives 0 (file scope, -O0 and -O2).

Reproducer:
```c
int comma_int = __builtin_constant_p((0, 1));
int comma_string = __builtin_constant_p((0, "abc"));
```

Cause: two evaluation sites treat a folded comma as constant: `TypeResolver::builtin_constant_p` (sema/types.rs) and the `__builtin_constant_p` lowering in sema/expression.rs, which ORs in `is_folded(&lowered)` before asking `builtin_constant_p`. Only the string-literal path had the clang-only comma rule.

Fix: `TypeResolver::gcc_comma_operand` (peels parens, checks for a Comma under the gcc flavor); `builtin_constant_p` and the lowering site both return false when it holds.

Regression test: crates/slate-parser/tests/fixtures/gcc/linux/x86_64/builtin_constant_p_comma.c.

Limits: gcc at -O2 inside a function folds `(0, 1)` to 1 (the optimizer); slate-parser has no optimization-level model, so it follows gcc's file-scope/-O0 answer. A comma nested deeper in the operand (e.g. `(0, 1) + 1`) is not covered.
