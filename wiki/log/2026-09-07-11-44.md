# AArch64 asm y constraint: correct wiki claim, close .6

_2026-09-07 11:44:56_

slate-3f8g.4.16.6 was already functionally done (w->vreg, x->vreg_low16,
fixture passing) but the wiki's y rationale was factually wrong: it
claimed y is for "scalable SVE vectors", conflating it with ARM32's
iWMMXt y/z letters. Verified against gcc/config/aarch64/constraints.md
(y = FP_LO8_REGS, V0-V7, an ordinary NEON subset) and real CIR codegen
(SLATE_CLANG accepts "y" on a plain float32x4_t add, no SVE type
involved).

The real blocker is narrower and more interesting: Rust's AArch64 asm!
only has vreg (V0-V31) and vreg_low16 (V0-V15), no vreg_low8 equivalent
to V0-V7. Unlike x86's g/imr widening (sound - any register works when a
register alternative was offered), y narrows the other way: the
instruction's encoding hard-requires a 3-bit register field, so binding
vreg_low16 could let the allocator pick an unencodable V8-V15 register -
unsound, not just imprecise. Confirmed 'y' already hits
Constraint::Unsupported cleanly (fail-loud "unsupported inline asm output
constraint", not silently wrong codegen) via a direct translate check.

No code changes needed - corrected wiki/concepts/inline-asm-support.md's
AArch64 FP/SIMD section with the accurate GCC source and the real Rust
register-class gap. Closed slate-3f8g.4.16.6.
