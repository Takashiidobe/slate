# worklist engine: measured libexpat timing, extended scoping to call_args/var_aliases

_2026-08-27 13:38_

Follow-up to [2026-08-27-13-23](2026-08-27-13-23.md). Measured real effect of
the item-scoped rescan (`TouchedItems`/`add_rule_scoped`/
`to_fixpoint_program_with_facts_scoped`) on libexpat (21 TUs,
`~/c-corpus/libexpat/expat/build/compile_commands.json`), same machine, same
`SLATE_FIXUP_TIMING=1` `translate-project --lib` invocation used for
`slate-y0qs.1`'s original profiling:

| state                                                    | wall time                             |
| -------------------------------------------------------- | ------------------------------------- |
| baseline `4281c7e2` (unscoped, before any y0qs.3 work)   | 67.4s                                 |
| + `ZeroInit`/`EarlyInlineTemps`/`LateInlineTemps` scoped | 65.1s                                 |
| + `CallArgs`/`VarAliases` scoped (this entry)            | 65.6s-66.1s (2 more runs, noise band) |

~3-4% faster overall so far, not yet the order-of-magnitude the epic targets --
expected, since only 6 of ~65 passes are scoped. Per-round timing logs confirm
the mechanism works as designed: e.g. one TU's `ZeroInit` round 4 rescanned
only 3 items (`scoped=3`) instead of the whole program, and round cost dropped
58ms -> 21ms round-over-round. The wall-clock ceiling is because most of the
slow-pass list from `slate-y0qs.1` (`Stdio`, `OptionBoxLocals`,
`HeapOwnership`, `BufferCursor`) don't run in a fixpoint loop at all -- they
call `plan.apply` once per `apply_with_logger` invocation, so there's no
second round for scoping to skip. Scoping only pays off for passes already
looping to a fixpoint (`to_fixpoint_program_with_facts` or a manual `loop {}`
tied to `report.changed`).

Extended to `CallArgs` (was already `to_fixpoint_program_with_facts`, same
`Binding` domain as the earlier four) and `VarAliases` (converted its manual
`loop { plan.apply(...); incremental.set_program(...); }` to
`to_fixpoint_program_with_facts_scoped`, which calls `set_program` at the top
of each round instead of the bottom -- verified this preserves the invariant
later steps depend on: `incremental` reflects `program` exactly when the loop
exits, same as the existing `to_fixpoint_program_with_facts`-based passes).

Verified no regression: full `rewrites` profile still fails exactly the same
9/118 test binaries as the pre-y0qs.3 baseline (`gcc_torture_supported_tests_match_c`,
`stdlib_coverage`, `c_testsuite_supported_tests_match_c`,
`generated_differential`, `chibicc_supported_tests_match_c`,
`directive_translated_fixtures_compile_for_current_host`,
`line_directive_preserves_cfg_item_joins_and_presumed_values`,
`generated_directive_filecheck`, `gcc_torture_unsupported_tests_still_fail`)
-- all pre-existing per `slate-mmiy` and unrelated causes (macOS cross-target
libc, gcc-torture promotion bookkeeping), none introduced by this change.

Next real lever for libexpat wall time specifically: either (a) find/convert
more of the currently-single-shot passes into fixpoint loops where a second
pass is genuinely possible (most already aren't, by design -- see
[passes.md](../concepts/passes.md)'s note on hand-placed re-runs instead of a
global fixpoint), or (b) the actual per-site worklist/dispatch-table from
[rewrite-worklist-engine.md](../concepts/rewrite-worklist-engine.md), which
also removes round 1's full walk cost, not just rounds 2+.
