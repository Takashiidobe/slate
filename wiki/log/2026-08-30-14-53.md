# asm: ebx save/restore workaround for cpuid-style outputs

_2026-08-30 14:53:14_

Fixed slate-a28e.14 (zstd ZSTD_cpuid: "cannot use register `bx`: rbx is used
internally by LLVM and cannot be used as an operand for inline asm"). Real
zstd binds ebx directly ("=b"(f7b)) as a cpuid output; rustc unconditionally
forbids explicit ebx/rbx asm operands regardless of register class, so the
straightforward FixedLetter('b') -> Explicit("ebx") lowering from slate-a28e.12
compiles but is rejected by rustc.

Fix: detect when a resolved output/input register lands on the ebx family
(al/bl/bx/ebx/rbx spellings) and, instead of binding it directly, pick a spare
fixed-letter scratch register (preferring D/S then a/c/d, whichever isn't
already used by another operand in the same asm block) and rewrite the
template to manually save/restore ebx: "push %rbx" before the body, "pop %rbx"
after, with a "mov" copying the real value in/out of the scratch register
immediately adjacent to the push/pop. This mirrors the exact workaround real
C code uses in cpu.h's clang-bug branch, but here it's needed unconditionally
since Rust bans the explicit ebx operand outright, not just under a compiler
bug.

Rejected an earlier draft that bound the scratch operand via the generic
"reg" register class and referenced it positionally as {N} in the template:
rustc's asm! macro forbids positional/generic-class operands from following
any explicit-register operand in the operand list, and reordering the operand
Vec would have desynced the numeric {N} indices baked into the rest of the
template by translate_asm_template. Switched to a second explicit-register
operand instead, with the mov instructions written as fully literal
register-to-register text (no {N} placeholder at all, since rustc also
forbids referencing explicit-register operands from the template). Also
caught mid-implementation: AT&T syntax requires "%"-prefixed register names
for hand-written literal mnemonics (unlike the auto-generated {N:e}
substitutions, which insert the "%" automatically) -- "mov ebx, edi" without
prefixes is genuinely ambiguous to LLVM's asm parser; fixed by branching on
the block's dialect (Att vs Intel) for both prefix and operand order.

New fixture: tests/fixtures/asm_ebx_output_cpuid.c (cpuid leaf 7, "=b"(f7b)
output, matching zstd's non-PIC x86_64 branch). Verified: differential +
FileCheck on lowering/rewrites, full rewrites suite (90/90), full lowering
suite (10/10), standalone rustc compile + runtime match against C, and zstd
corpus re-check -- both cpuid-related error classes gone, only the two
unrelated pre-existing bugs remain (addr_of_mut FSE_repeat/u32 mismatch,
*const/*mut ZSTD_parameters mismatch in zdict.rs).
