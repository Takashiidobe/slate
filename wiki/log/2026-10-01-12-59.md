# Multiple-include optimization for include-guarded headers

_2026-10-01 12:59:50_

slate-p58o.7.15. slate-parser re-read and re-lexed every guarded header on every #include (only #pragma once skipped). A chibicc TU opened 284 headers / 1.65MB for 109 distinct / 524KB.

- process() tracks GuardScan per file: the first directive must be #ifndef X or #if !defined X / !defined(X) whose branch is taken; it closes at the matching #endif; any code or directive outside it, or #elif/#else at its level, marks the file unguarded. Comments outside are allowed.
- A closed guard is recorded as include_guards[FileId] = X. resolve_and_parse_include interns the path first and returns nothing, without reading or lexing, while X is defined.
- Requiring the guard branch to be taken matters: gcc-torture vprintf-1.c includes itself under #ifndef test ... #else, and on the nested include the #else branch is what opens depth 1.
- Unlike the guard recognizer removed 2026-09-28 (cycle detection via macro_state dumps), this costs one hash lookup per include.

Remaining repeats are headers meant to be re-entered (bits/wordsize.h, libc-header-start.h, stddef.h/__stddef_*.h with __need_*): 284 -> 214 opens.
pp output byte-identical on all chibicc TUs, sqlite3.c, and quickjs.c; translated chibicc Rust identical.
Timing: strings.c pp 28.8 -> 20.9ms; parse.c ir 72.3 -> 64.3ms; sqlite3.c unchanged; chibicc translate-project 129 -> 114ms.
New fixture pp-multiple-include.c (#undef of the guard then re-include, code after #endif, #if !defined form); it fails if the skip ignores whether the guard is defined.
Tests: parser 7506/7506, slate 10/10.
