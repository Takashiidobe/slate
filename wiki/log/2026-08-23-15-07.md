# dlopen companion .so support for libc-test functional harness

_2026-08-23 15:07:57_

tls_align_dlopen/tls_init_dlopen were "admitted" only because dlopen() failed
identically on native and Slate sides (no companion .so vendored) -- not real
dlopen coverage. tools/filter-libc-test.sh now detects *_dso.c companion
libraries via their .mk (empty $(N).BINS, set $(N).LIBS), builds each as a
real .so, stages it at the dlopen()-hardcoded "src/functional/<dso>.so" path
during the native admission probe, and copies the built .so into the vendored
output under its own name (tls_init_dso.so, not tls_init_dlopen.so -- must
match the literal path the fixture's dlopen() call requests). tls_init_dlopen
flips from run-crashed:139 to admitted: the crash was an upstream test bug
(unconditional f() call after a failed dlsym), sidestepped once dlopen
actually succeeds.

tests/support/mod.rs gained RunConfig.extra_files: Vec<PathBuf>, staged into
<run_dir>/src/functional/<basename> before every case run (both C and Rust
sides use the same run_dir). libc_test_functional_suite.rs wires this up by
convention: for a "<stem>_dlopen" fixture, look for a sibling
"<stem>_dso.so"; no .mk to consult at test time, so the name-derivation
convention is duplicated (deliberately) between the shell vendoring script
and the Rust suite.

Out of scope: functional/dlopen.c needs t_pathrel (argv0-relative path
helper) from common/, not vendored -- separate, bigger lift than a
companion .so.
