# Add GCC memory ('m'/'+m'/'=m') asm constraint

_2026-09-06 20:31:10_

Implemented slate-3f8g.4.15.2 sibling slate-3f8g.4.15.3: memory-operand
address rewrite for m/+m/=m in inline asm.

CIR encodes any memory-class-only alternative set (never mixed with a
register alternative, which stays by-value per constraint_allows_generic_reg)
with LLVM's `*` address-indirection marker: `*m` for inputs, `=*m` for
outputs, and `+m` splits into a `=*m`/`*m` pair, all carrying the operand's
address (cir.ptr) rather than its value -- confirmed via CIR dump for all
three C-level forms.

Changes (src/frontend/lowerer/asm.rs, intrinsics.rs):
- strip_memory_marker() recognizes the `*` marker (after optional `=`/`&`,
  since a `+m`/`=m` operand that lands in the "input" constraint bucket --
  when there's no separate register output ahead of it -- still carries its
  literal `=` text) and a new Constraint::Memory variant carries it through.
- render_operand_reference wraps a plain (unmodified) reference to a Memory
  slot in AT&T `({0})` or Intel `dword ptr [{0}]` -- the pointee's bit width,
  not the address's, since the CIR operand type is the pointer.
- translate_asm_template hard-errors (returns None) if a Memory slot is
  referenced more than once, or with any modifier -- no rewrite designed for
  that yet, matching the bd task's stated scope.
- intrinsics.rs treats Memory like Reg for tied-output bookkeeping (no-op)
  and always emits AsmOperand::In { reg: Class("reg"), address }, regardless
  of C-level direction: the address never changes, so the underlying memory
  read/write happens through the register via the template's own
  instruction, not through Rust's out/inout operand machinery. For "+m",
  since the tied write-back half has no numeric backreference (unlike "+r"'s
  "0"), it is *not* deduplicated with the output half -- it becomes a second,
  unreferenced `in(reg)` holding the same address (redundant but correct;
  differential-tested and confirmed to still produce matching output).

New fixture: tests/fixtures/asm_memory_operand.c (m, +m, =m). Considered an
Intel-dialect case via the existing .intel_syntax-wrapper trick used by
asm_dialect_switch.c, but memory-operand %N substitution is AT&T regardless
of the embedded directive (it's controlled by the compiler's global -masm
flag, not by an inline asm block's own syntax markers), so the real
reference C compiler rejected it; the Intel `ptr`-prefix branch was instead
verified manually via `SLATE_CLANG_ARGS=-masm=intel cargo run -- translate`.
