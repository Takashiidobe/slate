# slate-5exy.12 VLA layout: fixed dimensions wrapping runtime dimensions

_2026-11-23 15:19:58_

- bead: slate-5exy.12
- kind: parser
- area: crates/slate-parser/src/sema/types.rs
- area: crates/slate/tests/fixtures

Outcome: Fixed and runtime dimensions can alternate in VLA objects and
pointees. CodeMetal array_decl_3 translates and matches the native C exit code.

**Reproducer**

```c
int get(int m, int (*p)[6][m]) { return p[1][2][m-1]; }
```

Before, adding a fixed middle dimension caused an unsupported scalar storage
layout error for the inner VLA. The IR now retains the pointee as
`array<vla<i32, %m>, 6>` and uses it as the element of `ptr_offset`.

**Cause and fix**

`TypeResolver::require_pointer_element` descended through runtime bounds and
asked for a static layout at a fixed bound. It now descends through fixed
bounds with runtime-sized elements as well. Alignment queries follow those
same layers. The fixed-size large-array alignment heuristic skips objects with
runtime sizes. The existing runtime `sizeof` and Rust stride and allocation
lowering already account for both kinds of extent.

**Regression**

`variable_length_array_mixed_extents.c` checks the parser's nested type, alignment,
`sizeof` and pointer offsets. `vla_mixed_extents.c` checks parameter decay, local
storage, a fixed outer dimension, captured bounds, indexing, pointer increment
and difference. Both native C and generated Rust exit 0.

The original CodeMetal case exits 1 in both languages because its check compares
the same row with an added `i`. Removing the extra `+ i` in a scratch copy makes
both exit 0, including with the benchmark's four-dimensional VLA.

Promoted chibicc `vla`, gcc.dg `pr114831-2.c` and `vla-4.c`, and gcc-torture
`pr22061-4.c` after their end-to-end checks passed. See slate-parser-dyd.56.3
for the remaining GNU record member case.
