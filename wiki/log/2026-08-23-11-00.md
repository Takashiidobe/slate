# clang-cir emit-cir superlinear memory blowup on sqlite3.c amalgamation

_2026-08-23 11:00:17_

Tried translating sqlite3's amalgamated build (~/sqlite/bld/sqlite3.c, 140456 lines) through slate for slate-wcf7. Blocked before slate even runs: 'clang -fclangir -emit-cir' itself blows up memory. Bisected at function-boundary prefixes (ulimit -v 10GB safety cap): 19698 lines succeeds in 7.2s/330MB RSS; 59998 lines (3x) aborts via llvm::report_bad_alloc_error in ~80s; 79802/99968 lines same; full 140451 lines times out at 90s with RSS still climbing past 4.9GB (uncapped run hit 16.8GB+ before being killed manually, with system swap already under pressure). perf showed ~25-30% of cycles in glibc allocator-internal code -- looks like allocation-count/fragmentation driven (virtual address space exhaustion via ulimit -v, not raw RSS) rather than one big buffer. '-ast-dump=json -fsyntax-only' on the full file is fine (0.86s) -- this is specific to CIRGen/-emit-cir, not Sema/parsing.

Ruled out the local llvm-project fork as the cause: built ~/llvm-project-ref (clean tree at the merge-base, no fork commits) with identical flags and reran the same bisection -- identical abort points and timings to the patched fork. So this is an inherent upstream ClangIR scaling issue on large macro-heavy single-TU C files (sqlite3.c amalgamation is exactly that shape), not something the fork introduced, and not fixable in slate. Filed as slate-wcf7.2 under the sqlite epic slate-wcf7. User plans to report this upstream to the ClangIR project. Practical path for the sqlite epic: translate sqlite's individual src/*.c files instead of the single amalgamation, since those stay well under this cliff.
