# Gate literal prefixes on standard mode; u8 element type follows C23

_2026-09-18 06:57:21_

`u8"..."` has `char` elements in C11/C17 and `unsigned char` in C23, which
added `char8_t`. `sema::types::string_literal_type` now takes `StandardFeatures`
and reads `u8_literals_are_unsigned` instead of hardcoding unsigned for every
non-plain encoding. `TypeResolver`'s lone `empty_parens_are_prototype` bool
became a full `features: StandardFeatures` field, since a second standard-mode
question in the same struct would otherwise need a second ad-hoc bool.

The literal prefixes themselves are now gated in `Lexer::literal_prefix_len`:
`u`/`U`/`u8"` require C11, `u8'` requires C23, `L` is always available. A
rejected prefix is not diagnosed; it simply is not recognized, so `u8'a'` lexes
as identifier `u8` followed by `'a'`. That is exactly what clang and gcc do --
both report "undeclared identifier 'u8'" for `u8'a'` under c11/c17/gnu17 and for
`u"a"`/`u8"a"` under c89/gnu89, with no GNU-mode leniency in either compiler.
slate-parser reports a parse error at the same token instead.

Verified against clang: `_Generic(u8"a"[0], unsigned char: ...)` picks `char`
in c11/c17 and `unsigned char` in c23.

Two gaps found and filed, not fixed here: encoded character constants still do
not lower as values (slate-parser-0tu), and `const char *p = u8"a"` under c23
is a hard conversion error where clang only warns under -Wpointer-sign
(slate-parser-j4b) -- that strictness is pre-existing and applies to any
pointer-sign mismatch.

Fixtures: `sema/std_mode_u8_string_literal.c` pins the element type across
c11/c17/c23; `error/std_mode_literal_prefixes.c` pins the prefix gating.
