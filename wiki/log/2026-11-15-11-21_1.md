Outcome: translated linux shards can be swapped into vmlinux.a and relinked with
the kernel's own make; all 59 vmlinux shards link into vmlinux.o, and the
remaining link/modpost blockers are filed as slate-f2zu.14.34.13-.18.

Gap and why it mattered: the linux corpus run stopped at `cargo build` per
shard; nothing checked that the objects link with the kernel's linker script,
objtool and modpost.

Implementation (tools/corpus/kernel_link.py; e2e.py runs it as the `link` stage
after `build` for `relink_vmlinux` recipes, or standalone:
`python3 tools/corpus/kernel_link.py ~/slate-translated/slate-linux [shard ...]`):

- Tree: `~/c-corpus/linux/build-slate`, a copy of build-<mode> (sibling, so
  srctree stays `..` and kbuild rebuilds nothing), settled with one native
  `make vmlinux`; the original thin archive is kept as `vmlinux.a.native`.
- Per shard (units whose `.o` is a vmlinux.a member): extract libslate_crate.a;
  `ld -r` the crate objects with an archive of the core/compiler_builtins
  members, so only needed runtime members come in. Before that, runtime members
  get `--localize-symbols` for every name native vmlinux.a defines, so
  compiler_builtins' hidden memcmp/bcmp/strlen neither bind Rust calls nor make
  a translated export hidden (modpost: "local symbol 'strlen' was exported").
- `objcopy --keep-global-symbols=<globals of the native members>` makes
  everything else local: every shard bundles core and has the same `slate_crate`
  crate hash, so its Rust symbols would collide across shards. `.eh_frame` is
  removed (one compiler_builtins member has CFI; the kernel uses ORC).
- The thin vmlinux.a puts the shard object at its first native member's position
  and drops the rest; then `make O=build-slate CC= HOSTCC= vmlinux`. Writing a
  newer vmlinux.a keeps kbuild's `vmlinux_a` copy rule from replacing it.
- link.md: link/modpost errors clustered, objtool warnings, and per shard the
  native exports the translation lacks.
- e2e.py re-translation is incremental: shard dirs and `cargo-target` are kept;
  translate-project writes `<shard>/next/crate`, `sync_tree` copies only changed
  files into `crate/` and removes stale ones, so unchanged files keep their
  mtimes.

Findings, all 59 shards, translations from before slate-f2zu.14.34.10/.12:

- vmlinux.o: 5 `multiple definition` from weak defaults translated strong (fixed
  by .10 already).
- `.gcc_except_table`/`.eh_frame` orphan sections from `extern "C-unwind"` under
  panic=abort: .14.
- `__compiletime_assert_N` undefined: `__builtin_constant_p(local)` folds to 0:
  .13.
- missing exports: `__x64_sys_fork` etc. (static alias target pruned): .15;
  `crypto_aes_sbox` (data alias): .16.
- 116875 objtool "'naked' return found in MITIGATION_RETHUNK build": pp_diff
  drops `-mfunction-return=thunk-extern` and the other `-m<opt>=<v>` flags: .17.
- 156 modpost section mismatches, exported `__init` functions in `.text`: .18.

Limits: shards only partly in vmlinux.a (init, \_packed) export only the
in-vmlinux units' symbols; an owner chosen by SymbolOwners in an out-of-vmlinux
unit (init/version-timestamp.c) is not handled yet. Initcall order inside a
shard follows Rust CGU order, not link order.
