# Evaluate __has_* queries outside #if, with per-compiler operand expansion

_2026-10-05 12:01:54_

slate-parser-6x05.38.33: kernel/trace/trace.c uses __has_attribute(btf_type_tag) in an ordinary if, which reached sema as an unresolved name. gcc and clang both evaluate __has_* queries anywhere in the text (only __has_include/__has_include_next/__has_embed are directive-only). expand_token now hands a name that is not a macro to expand_has_check: if the flavor defines it as a query (is_defined_operator) and ( follows, it collects the raw invocation and evaluates it with expand_has_checks, the #if evaluator. A user #define of the name still wins.

Measuring this showed slate's #if path was wrong for macro operands: it never expanded them, but both compilers expand the operand of __has_attribute/__has_c_attribute/__has_cpp_attribute (and __has_declspec_attribute in clang), and gcc also expands the operand of __has_builtin/__has_feature/__has_extension. clang leaves those unexpanded, as well as __has_warning and __is_identifier. A new helper, expands_has_operand(name, flavor), encodes this. expand_condition no longer protects those operators, so they go through expand_token and expand_has_check like running text.

Verified with -E output of clang and gcc on text and #if probes: identical except clang spelling 202003L (same value) and malformed inputs both compilers reject. Fixtures: {clang,gcc}/linux/x86_64/has-operators-in-text.c. Wiki: preprocessor.md Conditionals.
