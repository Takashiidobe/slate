# computed-goto: fix local block-address array dispatch

_2026-08-30 21:33:03_

slate-os0h.3.1.50: fixed 920501-5 (void *j[] = {&&x,&&y,&&z}; goto *j[i];).

Two bugs stacked:
1. Indirect-goto dispatch resolution (block_addr_element_ptrs) only fired
   for GetElement bases that were a genuine Val::Global. A local array
   initialized via ptr::copy from a synthetic module-scope const never
   matched. Fixed by tracking that provenance through the copy: new
   local_block_addr_arrays field on FunctionLowerer, populated in
   lower_copy (storage.rs), consumed by lower_get_element (memory.rs).
2. Once dispatch resolves symbolically (state index into a literal array),
   the original ptr::copy is dead code but still referenced an
   __const_x_j Rust item that's never emitted for block-addr-labeled
   synthetic constants (is_c_global is false for them) -> E0425. Fixed by
   skipping the ptr::copy emission entirely once local_block_addr_arrays
   captures the copy, since the array's real bytes are never read again.

20071210-1 stays open under the same bug: label addresses there cross a
function-call boundary as an opaque void** return value, get sliced into
a fresh array by the caller, then re-enter as an incoming parameter of a
second call to the same function. The current design is intraprocedural
and has no way to recognize an incoming void** parameter as aliasing a
previously-seen block-address global. Needs either real interprocedural
points-to tracking or encoding &&label as a literal decodable integer
value instead of an opaque pointer. Notes with full detail are on the bd
issue.
