Outcome: -m16 is an IR fact (`code16;` in the target header), translate-project writes `.cargo/config.toml` selecting the unit's Rust target (i686 for -m32/-m16, plus `-Ctarget-feature=+16bit-mode,-32bit-mode` for -m16), mixed-target projects are rejected, and the linux harness shards units by -m16/-m32.

Gap and why it mattered: the arch_x86_boot shard mixed 20 -m16 TUs with 14 x86_64 TUs in one crate checked for the host, so i386 lowering's legal explicit `bx` asm operands failed with "cannot use register bx: rbx is used internally by LLVM". slate-parser already retargeted -m16/-m32 to i686 (slate-parser-6x05.38.1), but -m16 was indistinguishable from -m32 in the IR, and slate never told cargo which target a crate was for.

How C does -m16: gcc compiles as -m32 and prints `.code16gcc` at the top of the .s, so gas adds 0x66/0x67 prefixes (pre-4.9 code used `-include code16gcc.h` with `__asm__(".code16gcc")`). clang cannot rely on a top-level directive (the integrated assembler encodes functions by their subtarget), so -m16 sets LLVM's `+16bit-mode,-32bit-mode` (the CODE16 triple). rustc passes the same features through `-Ctarget-feature` on i686; output is byte-for-byte the clang -m16 encoding, inline asm included. rustc warns the feature is unknown/unstable (rust-lang/rust#162235); the hard error is meant for stable, nightly keeps it. No custom target spec or build-std.

Before: `--target=x86_64-linux-gnu -m16` printed `target "i686-unknown-linux-gnu"` identical to -m32; translate-project wrote no target config.

After:
    target "i686-unknown-linux-gnu" { ... stack_alignment = 16; code16; long_double = f80; ... }
    .cargo/config.toml:
    [build]
    target = "i686-unknown-linux-gnu"
    [target.i686-unknown-linux-gnu]
    rustflags = ["-Ctarget-feature=+16bit-mode,-32bit-mode"]

Implementation:
- slate-parser: `TargetInfo::code16`, set in `CompilerArgParser::parse` from `ArchMode::Code16`; printed by `DisplayModule`. Spec: ir-grammar target rule, ir/calls-abi Targets.
- slate main.rs: `project_target` (all units must share triple and code16, else "units A and B translate for different targets"), `write_cargo_config` (no file for the host target; removes a stale one).
- tools/corpus/e2e.py `shard_units`: shards per last -m16/-m32/-mx32 flag (names end in the mode).

Fixture: crates/slate/tests/fixtures.arch-mode/ with differential.rs `arch_mode_projects_select_their_rust_target` (-m32 and -m16 configs, cargo build of both; 64-bit writes no config; mixed -m16/64-bit errors). Parser: clang/ and gcc/linux/x86_64/arch_mode_flags.c M16 now checks `code16;`. Manual objdump -m i8086 of the -m16 crate shows 66/67-prefixed code.

Limits: precompiled core/std stay 32-bit, so 16-bit code calling into them is wrong at link time (setup.elf must resolve memcpy etc. to the kernel's own real-mode routines). Harness passing CARGO_TARGET_I686_..._RUSTFLAGS would override the config rustflags. -mx32 still rejected (slate-parser-6x05.38.7). Kernel recheck deferred until slate-f2zu.14 is empty.
