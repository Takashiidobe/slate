# lower __bf16 as its own float format

_2026-09-21 11:07:38_

`__bf16` previously hit the `Unsupported("floating type")` arm in `sema/types.rs`
`base()`. It now lowers to a new `ir::FloatType::BF16` (size 2, align 2, 8 exact
integer bits) rather than aliasing `F16`.

The reason for a separate format is `FloatType::widens_from`, which used the
enum's derived `Ord`. bf16 is a truncated f32: 8 mantissa bits with f32's 8
exponent bits, against f16's 11 and 5. Neither holds every value of the other,
so no declaration order is correct. `widens_from` now compares
`exact_integer_bits` and a new `exponent_bits` instead, which reproduces the
previous answer for every existing pair and makes bf16/f16 incomparable in both
directions — a conversion either way prints `float_narrow`.

Semantics were taken from clang 22.1.8 by AST dump, and all match: `bf16+f16`
is `f16` (bf16's rank sits below f16 in `float_rank`, as in clang's
`FloatingRank`), `bf16+float` is `float`, `bf16+int` is `bf16`, `__bf16` is not
default-argument-promoted, `__builtin_classify_type` is 8, aarch64 passes a
four-bf16 struct as an HFA. `_Complex __bf16` is rejected by both.

Touched sites beyond the type map: `format_apfloat` dispatch in `ir/mod.rs` (so
bf16 constants print as decimals, not `bits=0x…`), `fold.rs float_to_integer`,
the `target_info.rs` storage table, and `float_rank`. Fixtures
`tests/fixtures/sema/ir_bfloat16.c` and `ir_bfloat16_invalid.c`.

Three follow-ups filed: the `bf16` literal suffix (GCC's `__BFLT16_MAX__` spells
it and `FLOAT_SUFFIXES` mismatches it as `f16`), the module `storage` header's
partial type list, and the `_Complex __bf16` diagnostic quality.
