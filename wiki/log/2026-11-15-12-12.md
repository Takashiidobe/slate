# slate-f2zu.14.34.17 -mfunction-return=thunk-extern: pp_diff.kept_args dropped -m<opt>=<value>; now maps to -Zfunction-return=thunk-extern

_2026-11-15 12:12:40_

- bead: slate-f2zu.14.34.17
- kind: feature
- area: crates/slate-parser/src/compiler_args.rs
- area: crates/slate/src/project/build_target.rs
- area: crates/slate-parser/tools/pp_diff.py
- area: tools/corpus/e2e.py
- target: linux

Outcome: `-mfunction-return=thunk-extern` now reaches slate and becomes `-Zfunction-return=thunk-extern` in the translated crate's rustflags. The corpus tooling also stops dropping every `-m<opt>=<value>` flag and `-mllvm <value>`, so kernel shards build returns as `jmp __x86_return_thunk` the way the native build does.

Gap and why it mattered: `pp_diff.kept_args` (shared by tools/corpus/e2e.py) kept `-m` flags only when they had no `=`, apart from `-march=`, `-mcmodel=` and `-mregparm=`. It also dropped `-mllvm` and its value. In the linux compile database that removed `-mfunction-return=thunk-extern` (2944 units), `-mstack-alignment=`, `-mtune=generic`, `-mstack-protector-guard-reg=gs`, `-mstack-protector-guard-symbol=__ref_stack_chk_guard` and `-mllvm -max-store-memset=N`. The parser also accepted `-mfunction-return=` only as a codegen-only flag that it then ignored, so even a direct translation lost it. Result: objtool reported 116875 "'naked' return found in MITIGATION_RETHUNK build" after the relink.

Before (`translate-project` with the kernel flags plus `-mfunction-return=thunk-extern`), `.cargo/config.toml` rustflags:
```
"-Crelocation-model=static", "-Zcf-protection=branch", "-Zretpoline-external-thunk", "-Zindirect-branch-cs-prefix", "-Ctarget-feature=-x87"
```
After: the same list plus `"-Zfunction-return=thunk-extern"`. The IR target block prints `machine [..., function_return=thunk_extern];`.

Implementation:
- slate-parser: new `Opt::FunctionReturn` (gcc and clang flavors). `thunk-extern` sets `CodegenOptions::function_return_thunk_extern`. `keep`, `thunk` and `thunk-inline` clear it, and any other value is rejected. The flag is no longer a `CodegenOnlyFlag`. `MachineCodegen` carries it, so units that differ in it are different build targets, and module_print shows it.
- slate: `build_target::shared_flags` maps it to `-Zfunction-return=thunk-extern`.
- pp_diff.py: `TARGET_FEATURE` takes an optional `=value`, and `-mllvm` moves from DROP_SEPARATE to KEEP_SEPARATE. Every flag these patterns keep now reaches the parser, so a flag without a policy fails the unit instead of being ignored.
- e2e.py `shard_units`: a new `return` codegen family. The 7 kernel units built without the flag go to their own shard, because `MachineCodegen` now differs.

Tests:
- crates/slate-parser/tests/fixtures/clang/linux/x86_64/driver_flag_effects.c (adds the flag to ARGS).
- `freestanding_projects_build_for_bare_metal_targets` in crates/slate/tests/differential.rs (KERNEL_FLAGS plus the expected rustflag). `freestanding_main_links_as_an_ordinary_symbol` links with the same flags, so tests/fixtures.arch-mode/seven.S now defines `__x86_return_thunk` next to `__x86_indirect_thunk_r11`.

Limits: gcc's `thunk` and `thunk-inline` have no rustc equivalent and are treated as `keep`. Flags that pp_diff now keeps but the parser does not know (seen: `-mabi=`, `-mtls-dialect=`, `-mbranch-protection=`, `-mcpu=`, and `-mpreferred-stack-boundary=` under the clang flavor) now fail translation of any unit that uses them.
