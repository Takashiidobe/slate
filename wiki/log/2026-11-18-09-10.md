# slate-3f8g.4.43 asm Symbol class: x86 'i'(&sym) rejected under PIC/PIE like clang/gcc (i686 PIE default, x86_64 -fPIC preemptible)

_2026-11-18 09:10:58_

- bead: slate-3f8g.4.43
- kind: parser
- area: crates/slate-parser/src/sema/asm.rs
- area: crates/slate-parser/src/sema/module.rs
- target: i686
- target: x86_64

Outcome: slate-parser rejects x86 asm symbol immediates ("i"(&g), "s", the sym part of "g"/"X") exactly where clang/gcc do under PIC/PIE, so "ri"/"g" fall back to a register and "i" gets a rejected: fact instead of Rust that fails to link.

## Diagnostic / IR fact that was wrong

`AsmOperandClass::Symbol` was available for any static-storage object or
function in every PIC mode. Both compilers reject a symbol immediate when its
address is not a link-time constant: on i686 unless `-fno-pic` (the Linux
default is PIE), on x86_64 for preemptible symbols under `-fpic` and for
undefined functions (clang: also `extern` variables) under PIE. slate then
emitted `sym` operands that rust-lld refused (`R_386_32` / `R_X86_64_32S`
"recompile with -fPIC").

## Before / After

```c
int g;
void f(void) { asm("# %0" : : "i"(&g)); asm("# %0" : : "ri"(&g)); }
```

i686-unknown-linux-gnu, default flags. Before: `in 0 "i" ... -> sym`, and
`"ri"` also picked `sym`. After: `"i"` prints `rejected: 0 (operand 0:
not-constant)` and `"ri"` selects `-> reg`, matching clang ("invalid operand
for inline asm constraint 'i'") and gcc ("impossible constraint").

## Fix

- `Lowerer::link_time_address` (sema/asm.rs) filters `Source.symbol`. PIC mode
  is `Module.machine.pic`, else PIE on Linux/Android/Darwin, else off.
- `-fno-pic` allows all; i686 under PIC allows none; x86_64 allows internal,
  hidden/internal visibility, protected (not gcc), and under PIE symbols
  defined in the unit or, for gcc, `extern` variables.
- New `Lowerer::defined_symbols`: a pre-pass over `unit.decls` (function
  definitions, initialized or tentative object definitions) via
  `NameResolution.declarations`, because a definition after the asm counts and
  `Entities::definition` is only set as items are lowered.
- clang keeps accepting `s` under PIC; gcc gates it like `i`.
- clang on x86_64 accepts any symbol with a nonzero offset in every mode
  (`&arr[1]`, `(char *)&g + 3`): llvm checks for a GOT stub only on a bare
  global. `fixtures.library/asm_symbols` (`"i"(&native_value[1])` on an
  `extern` array) depends on it.
- An `alias` declaration counts as a definition
  (`fixtures.release/data_alias_units`, `"i"(crypto_sbox)`).

Verified against a 29-case x 4-mode x 2-flavor x 2-target clang/gcc matrix
with zero mismatches.

## Fixtures

`crates/slate-parser/tests/fixtures/{clang,gcc}/linux/i686/ir_asm_symbols_pic.c`,
`clang/linux/x86_64/ir_asm_symbols_{pie,fpic}.c`,
`gcc/linux/x86_64/ir_asm_symbols_{pic,pie}.c`. The existing
`clang/linux/{i686,x86_64}/ir_asm_symbols.c` now pass `-fno-pic` to keep
testing symbol selection.

Limits: mingw/darwin `extern` rejection is not modeled. The build half of
the bead (hosted `-fno-pic` crates with `-Crelocation-model=static`, lifting the
i686 `%a` barrier) was dropped by decision: only legacy hosted code needs it.
