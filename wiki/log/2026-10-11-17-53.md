# __builtin_ms_va_list and the ms va builtins

_2026-10-11 17:53:37_

slate-parser-v74.1.12.

slate-parser:
- __builtin_ms_va_list is a target builtin type: char* on x86_64/aarch64, unknown type name elsewhere.
- __builtin_ms_va_start/_end/_copy share the va_builtin path. Elsewhere they are rejected (only available on x86-64 and aarch64).
- IR: VaStart/VaArg/VaEnd/VaCopy carry ir::VaConvention {Target, Win64}, printed va_arg<T, win64> and va_start<win64>(..); Target prints as before.
  - Win64 when a Microsoft list is used on a target whose native va_list is not char* (Linux/BSD x86_64 and aarch64); Windows and Darwin stay Target.
  - va_arg on any modifiable char* lvalue is Win64 on those targets, as in clang BuildVAArgExpr.
- clang/msvc flavors check va_start as clang's checkVAStartABI does:
  - ms_va_start only in Win64 functions (any non-sysv_abi function on Windows);
  - native va_start not in an ms_abi function off Windows nor a sysv_abi function on Windows;
  - neither in a function with fixed args (new for the native builtin too).
  The enclosing-function info (FunctionNames) now carries the convention and variadic-ness. gcc accepts all of these, so the gcc flavor skips the checks.

slate:
- Win64 va_arg on x86_64 lowers to the __slate_win64_va::arg support helper: 8-byte slots; types over 8 bytes or of non-power-of-two size are read through a pointer.
- Win64 va_copy is a pointer copy and va_end a no-op.
- Win64 va_start (only possible in variadic ms_abi definitions, already rejected) and long double / aarch64 Win64 va_arg are barriers.
- Library fixture ms_abi_calls gains ms_list_sum, which consumes a native ms_abi variadic's list (va_copy, long, double, 24-byte and 3-byte structs, int). Dropping the by-reference rule makes it fail.

Fixtures: clang/{linux/x86_64,linux/aarch64,windows/x86_64}/ms_va_list.c, gcc/linux/x86_64/va_start_unchecked_contexts.c, 10 error fixtures; migrated clang-test CodeGen/ms_abi.c (windows/x86_64) and ms_abi_aarch64.c (windows/aarch64).
