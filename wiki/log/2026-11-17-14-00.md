# slate-yar4.46 AsmNames: Intel-syntax register names (ds, eax) became sym operands when a C global shared the name

_2026-11-17 14:00:21_

- bead: slate-yar4.46
- kind: bug
- area: crates/slate/src/frontend/lowerer/asm.rs
- target: x86_64

Outcome: in Intel-syntax inline asm (-masm=intel or an inline `.intel_syntax`), x86 register names such as `ds`, `eax` and `rax` stay registers even when a unit-local C global has the same name, instead of becoming `sym` operands.

Symptom: `mov ax, ds` with a C global `unsigned short ds` lowered to `mov ax, {1}` with `sym ds`, which reads the global instead of the segment register (or fails to assemble: `invalid operand for instruction`).

Reproducer:

```c
unsigned short ds = 0x1234;
unsigned eax = 100;
static unsigned long read_ds(void) {
  unsigned long r;
  __asm__ volatile(".intel_syntax noprefix\n\tmov ax, ds\n\tmovzx %V0, ax\n\t.att_syntax prefix"
                   : "=r"(r) : : "rax");
  return r;
}
```

Cause: `AsmNames::text` (crates/slate/src/frontend/lowerer/asm.rs) rewrites template words that name a unit-local function or static into sym operands, and skips only %-prefixed words. Intel syntax has no % on registers.

Fix:
- `AsmNames` tracks `intel`. It starts from `asm.dialect == Intel` and switches on `.intel_syntax`/`.att_syntax` words in the template.
- In Intel mode, `intel_register` excludes a word from symbol rewriting when it is a segment register (cs ds es fs gs ss), rip/eip/ip, or a name `slate_parser::target::x86::decode_register` knows. The GCC pseudo-registers argp, flags, fpcr, fpsr, dirflag and frame (numbers 16..=21) are not excluded.
- Other symbols still become sym operands in Intel mode: `DWORD PTR counter[rip]` keeps `sym counter`.

Regression test: crates/slate/tests/fixtures/x86_64/asm_intel_register_names.c (globals ds, eax and counter; it failed to build before).

See: slate-f2zu.14.34.9 (the AT&T `%%ds` case).
