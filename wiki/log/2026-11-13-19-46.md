# slate-yar4.39 asm register_modifier: %h on x86_64 "q"/"r" operand narrowed to reg_abcd instead of barrier

_2026-11-13 19:46:32_

- bead: slate-yar4.39
- kind: bug
- area: crates/slate/src/frontend/lowerer/asm.rs
- target: x86_64

Outcome: x86 inline asm operands with a general register class (x86_64 "q", any "r") that the template prints with %h now lower to reg_abcd, so the high-byte view always has an %ah/%ch/%dh name.

Symptom: `__asm__("xchgb %b0, %h0" : "+q"(x))` on x86_64 stopped at `statement asm: high-byte view needs an abcd register`.

Reproducer:
```c
unsigned f(unsigned x) { __asm__("xorb $1, %h0" : "+q"(x)); return x; }
```

Cause: sema maps x86_64 "q" (and "r") to AsmRegisterClass::Reg, correctly; register_modifier in crates/slate/src/frontend/lowerer/asm.rs only allows the HighByte view on RegAbcd. Natively it works only by allocator luck: clang -O0 picks %eax (prints %ah), clang -O1 picks %esi and errors "invalid operand in inline asm".

Fix: high_byte_narrowed (asm.rs) clones the InlineAsm and retypes every Reg operand referenced with view HighByte to RegAbcd before lower_asm builds the template and operand list (x86 only). Rust then emits inlateout(reg_abcd) and {0:h}.

Regression test: crates/slate/tests/fixtures/x86_64/asm_high_byte_general_register.c ("+q" xchgb %b0/%h0, "r" input read via %h1, two "q" operands mixing %h/%b/%w). The native side compiles only at -O0, which is what the differential harness uses.

See: slate-dghn.58.3
