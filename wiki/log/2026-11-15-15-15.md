# slate-f2zu.14.34.24 e2e.py shard_units: init/version-timestamp.c in init shard duplicated init_uts_ns/linux_banner at vmlinux link

_2026-11-15 15:15:46_

- bead: slate-f2zu.14.34.24
- kind: bug
- area: tools/corpus/e2e.py

Outcome: e2e.py no longer puts kernel units whose objects are not vmlinux.a
members into vmlinux shards, so init/version-timestamp.c's strong
init_uts_ns/linux_banner stop reaching vmlinux.o alongside link-vmlinux.sh's
native version-timestamp.o.

Symptom: vmlinux link: multiple definition of init_uts_ns and linux_banner
(init/version-timestamp.o vs vmlinux.o).

Cause: shard_units grouped every non-module, non--S unit by directory.
init/version-timestamp.c landed in the init shard with init/version.c;
SymbolOwners kept its strong definitions over version.c's \_\_weak ones, and
kernel_link.py swapped the init shard in because version.o is a vmlinux.a
member. link-vmlinux.sh links version-timestamp.o separately, so two strong
copies reached the final link.

Fix: shard_units reads `ar t vmlinux.a` in each unit's build directory (archive
named relatively so thin-archive members print build-relative). A unit is linked
when its object (path relative to the build dir for generated sources, else
relative to the project dir) is a member. Non-members (version-timestamp.c,
.vmlinux.export.c, arch/x86/boot, realmode, vdso, efi libstub, scripts/mod) are
split into `unlinked*` shards, which swap() skips because none of their objects
are in the index.

Regression test: none (harness); verified by shard listing: init shard no longer
contains version-timestamp.c.

Limits: generated sources under build-clang/ (defkeymap.c, \*.asn1.c,
capflags.c) are members, but kernel_link.swap maps units to objects by
project-relative path (build-clang/...o), so they still never get swapped in.
Pre-existing.
