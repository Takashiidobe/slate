# slate-f2zu.14.40.5 kernel_link/e2e shard_units: non-contiguous shards moved initcall/__param/__setup entries ahead of interleaved objects; split shards into link-order runs

_2026-11-16 11:49:24_

- bead: slate-f2zu.14.40.5
- kind: bug
- area: tools/corpus/e2e.py
- area: tools/corpus/kernel_link.py
- corpus: linux

Outcome: linux shards are split into link-order runs, so swapping each shard object into vmlinux.a at its first member's position no longer moves initcall, __param or __setup entries ahead of entries from interleaved objects.

Symptom: kernel_link.py `swap()` replaces a shard's vmlinux.a members with one object at min(member positions). shard_units groups by directory and packs leftovers into `_packed`, so 22 of 84 shards interleave with other shards or native objects (`_packed` spans members 49..2884). Every later member's table entries ran before everything in between.

Cause (verified by simulation over build-clang/vmlinux.a and readelf of the native objects): with the 84-shard layout, 15 iterated sections end up in a different object order than native: .initcall6.init (281 entries misplaced), __param (175), .init.setup (156), .initcall4.init (100), .initcall7.init (78), .initcall5.init (59), .initcall1.init (41), ...

Fix (tools/corpus):
- kernel_link.py `ORDERED_SECTIONS` (initcalls, .con_initcall, .init.setup, __param, __modver, .apicdrivers, .x86_cpu_dev.init, lsm_info, __earlycon_table, init/fini arrays, kunit suites) and `ordered_sections(build_dir, members)`, which reads them with one `readelf -SW` per 400 objects.
- e2e.py `link_order_runs` (end of `shard_units`): walks each vmlinux.a shard in link order and starts a new run `<shard>_r<N>` when the next unit shares an ordered section with an object between the run's first member and it that belongs to a different shard or to native code. A run's object, placed at its first member, then never passes a conflicting entry. Order inside a run is the crate's (slate-f2zu.14.40.4 for global_asm, .6 for link_section statics). Shards with units outside vmlinux.a are left whole.
- 84 shards become 133 crates (11 shards split, e.g. arch_x86__packed into 7, drivers__packed and _packed into 10).

Check: same simulation after the split: 0 sections out of order.

Limits: not yet retranslated, relinked or booted; planned after slate-f2zu.14.40.6. Weak-vs-weak "first definition wins" and other non-section link-order effects are not modeled.

See: slate-f2zu.14.40.4, slate-f2zu.14.40.6, slate-f2zu.14.34.6 (kernel_link.py)
