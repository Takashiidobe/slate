# local vector-init macro-constant bug (slate-os0h.3.1.59) no longer reproduces

_2026-09-04 11:20:45_

slate-os0h.3.1.59 claimed a LOCAL v4si va = {INT_MAX, 1, INT_MIN, 0}
lowered to `let mut va: [i32;4] = i32::MAX as [i32; 4]`, dropping every
element after the first. Reproduction attempts (bare repro, repro with an
earlier INT_MAX use in the same function, and the actual
saturating_arith.c fixture with the literal workaround reverted back to
INT_MAX/INT_MIN) all lower correctly today to
`[2147483647, 1, -2147483648, 0]` and pass the rewrites differential test.

next_macro_const_expr (src/frontend/lowerer/storage.rs) matches macro
consts by value against a per-function FIFO queue (macro_consts), and each
vector-init element is its own cir.const with its own scalar (i32)
result_ty — cir.vec.create only assembles the ArrayLit afterward — so
there's no shared vector-typed result_ty for the cast to attach to. Most
likely fixed as a side effect of the const/copy and load/store/const
migration to the worklist rewrite engine (2509b926, 2d04f5e8) sometime
after this bug was filed (2026-08-17).

Reverted the workaround: tests/fixtures/saturating_arith.c now uses
INT_MAX/INT_MIN directly in the va initializer; regenerated FileCheck
blocks are byte-identical to the literal version. Closed slate-os0h.3.1.59
as fixed/verified rather than re-deriving a no-longer-needed patch.
