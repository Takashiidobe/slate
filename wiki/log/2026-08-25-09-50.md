# raw setjmp lowering is optimization-unsafe

_2026-08-25 09:50:17_

Investigated whether raw (rewrite-free) setjmp/longjmp lowering is safe under
optimization, since rustc can't mark the extern setjmp declaration
returns_twice.

Found: mutating a non-volatile local between setjmp and the longjmp that
reenters it diverges under optimization in _both_ clang -O2 and Rust
--release (r=99 x=0 vs r=99 x=5 at -O0) — this is inherited C UB, not
Rust-specific. Same code with `volatile int x` stays correct in C at any
opt level, and slate's existing write_volatile/read_volatile lowering for
`volatile` locals stays correct under --release too. So raw lowering's only
real exposure is the common-but-UB volatile-less idiom.

Confirms the SetjmpRecovery catch_unwind rewrite isn't just idiomization —
it's what makes the translation optimization-safe, since panic/unwind is a
construct LLVM's EH machinery understands natively. The differential harness
can't catch this class of regression today since both sides always compile
unoptimized (tests/support/mod.rs pins C at -O0, Rust goes through debug
`cargo build`).

Also confirmed there's no way to reach LLVM's `returns_twice` attribute from
ordinary Rust: it's a function attribute, not an intrinsic, so
link_llvm_intrinsics can't reach it; #[ffi_returns_twice] (which did this)
was removed, and the internal_features lint blocks the rustc_attrs mechanism
it used outside the compiler/std sysroot. Full writeup:
wiki/concepts/setjmp-longjmp-lowering.md.
