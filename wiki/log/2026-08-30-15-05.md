# enum-typed struct-field pointer args now cast to the CIR-erased param type

_2026-08-30 15:05:12_

Fixed slate-a28e.13 (zstd: addr_of_mut!(...litlength_repeatMode) passed where
*mut u32 expected, E0308 x3 in zstd_compress.rs). Root cause: CIR erases enum
types to their underlying integer representation universally, so a callee's
declared FSE_repeat* parameter gets lowered to *mut u32 (matching how the
callee's own body already treats it, e.g. `*arg97 = _v3` where _v3 is a plain
u32). But the CALL-SITE expression for `&entropy->litlength_repeatMode`
naturally infers as *mut FSE_repeat in Rust, since it's a real field access on
a struct whose field is a genuine Rust enum (the enum-ness survives at the
record/struct-field level, unlike CIR's own type tracking which already
erased it). Nothing reconciled the two.

call_arg_expr (values.rs) already had a narrow version of this fix for plain
enum-typed local slots (checking self.slot_types), inserting a Cast to the
CIR-derived rust_type. Extended the same lookup to also check member_ptrs
(struct field access via addr_of_mut) and element_ptrs (array/index access),
mirroring the pattern store_function_pointer_value already used to resolve a
pointer operand's real field type across those three sources. No changes to
cast_void_ptr_call_args or the callee-signature side needed -- this is purely
a caller-side gap in the existing pointer-enum-cast branch.

New fixture: tests/fixtures/enum_field_ptr_call_arg.c, using @lowering-fn-begin
/@rewrite-fn-begin around the whole `run` definition (not statement-level
markers) since a statement-only marker ending right at the function's closing
brace tripped tools/update_filecheck.py into emitting a bogus stray "1 => {"
DAG check not present in the actual generated output -- capturing the full
function sidesteps that boundary issue entirely, per Takashi's suggestion.

Verified: differential + FileCheck on lowering/rewrites, full rewrites suite
(90/90), full lowering suite (10/10), zstd corpus re-check -- all three
addr_of_mut/FSE_repeat mismatches gone, only the unrelated pre-existing
*const/*mut ZSTD_parameters mismatch in zdict.rs remains (different bug,
untracked).
