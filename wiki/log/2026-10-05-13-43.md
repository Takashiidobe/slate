# Corpus e2e for CMake libraries: cJSON and libyaml (slate-dghn.27, .28)

_2026-10-05 13:43:16_

tools/corpus/e2e.py gains a CMakeLibrary recipe kind for CMake/ninja projects whose product is a library (no bench stage). Native TUs come from ninja -t query <library> (symlinked .so resolved first), matched to compile_commands entries by output. The library is translated with translate-project --crate-type staticlib.

Test stage: every CTest executable plus the recipe's tools is rebuilt into test-tree/. Default: relink from the native link command (ninja -t commands), the library swapped for the translated archive, plus Rust's native libs. A ctest case passes on exit 0 and stdout identical to native. Differential entries run a tool over input globs, with the same argv[0] for both builds (libyaml's run-* print argv[0]), and must match exit code and stdout.

cJSON needs translate_tests: its unity tests #include "../cJSON.c", so a relink would test only native code (the first run reported 19/19 with 18 of them never touching Rust). Each test executable (objects plus in-build archives like libunity.a) is translated as its own binary crate and linked against the translated cdylib in place of libcjson.so, keeping the native rule that a test's own definitions win. Generated crates are all named slate_crate, so each binary is copied out of the shared cargo target dir right after its build.

Results: cJSON 1 TU, 19/19 ctest, stdout identical. libyaml 8 TUs, 3/3 ctest, 100/100 differential runs (10 tools x examples/*.yaml + regression-inputs/*). Both added to the README's e2e list. Also fixed e2e.py building -p slate (now slate-c2rust); redis still passes native/barriers.

Filed slate-dghn.29 (Lua: computed goto, visibility attributes, and _setjmp/_longjmp, which lowering-barriers does not report) and slate-dghn.30 (zlib, CMake library mode).
