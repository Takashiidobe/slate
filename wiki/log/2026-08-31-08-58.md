# FreeBSD qsort_r matches glibc's shape, no shim changes needed (slate-sfzn.10.9)

_2026-08-31 08:58:47_

Ticket slate-sfzn.10.9 assumed FreeBSD's qsort_r diverges from glibc's
comparator-callback argument order (context pointer in a different
position) even though both share the name qsort_r, and planned a
FreeBSD-specific function-pointer typedef to model it.

Checked against the FreeBSD 15.1 oracle
(target/freebsd-oracle/sysroots/{amd64,arm64}/usr/include/stdlib.h):
FreeBSD 14 changed qsort_r's prototype to comply with POSIX. The 15.1
declaration is `void qsort_r(void*, size_t, size_t, int (*)(const void*,
const void*, void*), void*)` - identical to glibc's shape and to what
libc-shim/include/stdlib.h already declares. The historical BSD order
(thunk before compar; comparator takes thunk first) is kept only as a
versioned compat symbol (qsort_r@FBSD_1.0 / __qsort_r_compat) for
pre-existing binaries; new code always gets the POSIX-shaped declaration.

Also verified strlcpy/strlcat (string.h) and reallocarray/arc4random/
arc4random_buf/arc4random_uniform (stdlib.h) against both oracle arches:
all match the shared shim's existing declarations and __BSD_VISIBLE
gating exactly. string.h/stdlib.h were already in
freebsd-basic-headers.txt (10.2) and pass the header-compile suite.

Result: no libc-shim code changes. Verified end-to-end via `slate
translate` + `cargo check --target {x86_64,aarch64}-unknown-freebsd` for
a fixture using strlcpy/strlcat/reallocarray/qsort_r (context-carrying
comparator)/arc4random family - both architectures check clean, zero
warnings. qsort_s (C11 Annex K) left out of scope: would need
rsize_t/errno_t/constraint_handler_t machinery not modeled for any libc
profile, and isn't required by the ticket's acceptance criteria.

Updated wiki/concepts/freebsd-libc-oracle.md with a new section; bd notes
on slate-sfzn.10.9 updated to correct the outdated design premise before
closing.
