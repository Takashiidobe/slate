# slate-3amj.34 clang -fpascal-strings: leading \p in a plain string literal becomes a length byte

_2026-11-18 18:10:12_

- bead: slate-3amj.34
- kind: feature
- area: crates/slate-parser/src/const_expr.rs
- area: crates/slate-parser/src/compiler_args.rs
- flavor: clang

Outcome: clang `-fpascal-strings` / `-mpascal-strings` now turn a leading `\p` in a plain string literal into a length byte, and define `__PASCAL_STRINGS__`.

## Gap and why it mattered
The flag was parse-and-ignored (or rejected), so `"\pHello"` kept a bogus `\p` escape and had no length prefix. Classic Mac-style code relies on `s[0]` being the length.

## Before
```c
/* -fpascal-strings */
sizeof("\pHello")   // wrong, no length byte
```

## After
`sizeof("\pHello") == 7`, `"\pHello"[0] == 5`, `"\p"[0] == 0`; `__PASCAL_STRINGS__` is 1.

## Implementation
`Opt::PascalStrings` / `Opt::MPascalStrings` (clang only) set `SourceGraphs.pascal_strings`, threaded like `Opt::Blocks` into `StandardFeatures.pascal_strings`. `pp/mod.rs` defines `__PASCAL_STRINGS__=1` beside `__BLOCKS__`. `parse_primary` in const_expr.rs strips `\p` from the first piece of a plain literal and prefixes a 3-digit octal escape with the total unit count.

## Fixture
crates/slate/tests/fixtures/flag_pascal_strings.c, promoted from fixtures.unsupported/. parser (9306) and slate (43) profiles green.

Limits: lengths over 255 are truncated to a byte instead of diagnosed; `\p` is only recognised at the start of the first concatenated piece; no parser-side fixture for the macro.
