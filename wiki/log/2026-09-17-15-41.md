# String literals carry execution-charset units

_2026-09-17 15:41:47_

`decode_escapes` flattened everything to codepoints, so every consumer that used
`code_units.len()` mis-sized any literal holding non-ASCII text: `sizeof("Ω")`
and `sizeof("Ω")` gave 2 where clang gives 3, and `int probe[sizeof("Ω")]`
lowered to `array<i32, 2>`. Static assertion validation turned that from a quiet
wrong answer into a hard error on valid C, which is what forced the fix.

Re-encoding the codepoints blindly would have traded the bug for another one:
`"\xff"` is a single byte, but as a codepoint it re-encodes to two. The
distinction only exists at decode time, so `Lexer::decode_source_units` now
tags each unit as `SourceUnit::Character` (a source character or a `\u`/`\U`
name, still to be encoded) or `SourceUnit::CodeUnit` (a `\x`/octal escape, or a
raw byte recovered from invalid UTF-8 source — used verbatim).
`decode_escapes` keeps its old signature on top of it, so char literals are
untouched.

`StringLiteral::execution_units` re-walks `pieces` — the raw spelling is already
on the AST node — and encodes per literal encoding: UTF-8 for plain/u8, UTF-16
with surrogate pairs for u and for L on a 16-bit wchar target, UTF-32
otherwise. The AST field keeps its shape, so no fixture churn.

`sema::types::string_literal_type` is now the single routine giving a literal
its array type, used by both `TypeResolver::assertion_operand_type` and
`Lowerer::unevaluated_type`, which previously disagreed — the latter rejected
encoded literals outright. String constant lowering feeds the same units into
`ValueKind::Bytes`, so `"Ω!"` now emits [206, 169, 33, 0]. Lowering an encoded
literal as a _value_ is still unsupported; only `sizeof` of one works.

Checked against clang: tests/fixtures/sema/string_literal_sizes.c passes
`clang -std=c23 -fsyntax-only`. Note `const char s[] = "ab";` still fails IR
lowering ("incompatible or unsupported conversion") — pre-existing, unrelated,
and why the fixture uses pointers.
