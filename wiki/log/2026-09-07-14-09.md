# Fix rustc abi_unadjusted removal: unadjusted -> llvm-intrinsic ABI

_2026-09-07 14:09:38_

Closed slate-3f8g.4.16.19. rust-lang/rust#161398 removed the abi_unadjusted
feature gate and folded it into link_llvm_intrinsics, but also renamed the
extern-block ABI string itself: "unadjusted" is no longer valid, replaced
by "llvm-intrinsic" (confirmed via `rustc --print=calling-conventions` and
a minimal repro compiled + run under #![feature(link_llvm_intrinsics)]).

Fix: single ABI-string emission site in src/frontend/lowerer.rs
(llvm_intrinsic_shims extern block) changed from "unadjusted" to
"llvm-intrinsic". Dropped the now-dead Feature::AbiUnadjusted entirely
(enum variant + spelling arm in src/backend/rust_ast.rs, plus both
insertion call sites in src/frontend/lowerer.rs and
src/frontend/lowerer/module_index.rs) -- Feature::LinkLlvmIntrinsics alone
gates this now.

Despite the ticket title, this wasn't ARM32-only: x86_64 fixtures
gnu_builtin_debugtrap, target_stack_builtin_ops, x86_instruction_intrinsics,
x86_simd_vector_intrinsics, and gcc-dg's long-double__pr19402-2 all hit the
same rustc-version regression. Regenerated FileCheck blocks for the 4
fixtures with embedded LOWERING/REWRITES assertions via
`tools/update_filecheck.py --profile both`.

Verified end to end: full `cargo nextest r --release --profile lowering`
green (12/12 tests), plus arm-lowering and arm-rewrites profiles green
against the real arm-none-linux-gnueabihf cross toolchain -- needed
sourcing .env's SLATE_ARM_LINKER/SLATE_ARM_SYSROOT and additionally
setting CC_armv7_unknown_linux_gnueabihf/AR_armv7_unknown_linux_gnueabihf
so cc-rs (used by build-dependency C shims like bitfields/aligned) picks
up the same cross compiler instead of guessing "arm-linux-gnueabihf-gcc"
from the target triple, which isn't the installed toolchain's prefix
(arm-none-linux-gnueabihf).
