# Lower character constants of every encoding

_2026-09-18 07:04:36_

`sema` no longer rejects encoded or multicharacter character constants. One
helper, `sema::types::character_constant`, now produces both the type and the
value, and is used by the value path in `sema/expression.rs` and by the constant
path in `sema/types.rs` -- those two had drifted, the latter typing `u'a'` as
`int` so `sizeof(u'a')` was 4.

Values are computed from execution-charset units, not code points, so escapes
and characters behave differently: `CharLiteral` gained `execution_units`, built
on the same `decode_source_units` split that `StringLiteral` already used.
`'\xff'` stays one byte (`CodeUnit`, truncated) while `'X'` above ASCII is
encoded, which is what makes `'\xff'` == -1 but `'AB'` == 0x4142.

Types and values verified against clang -std=c23: `u8'a'` unsigned char,
`u'a'` unsigned short, `U'a'` unsigned int, `L'a'` and plain int; `'\xff'` -1
(char is signed here), `'ab'` 24930, `'abcde'` 1650680933 (packed, wrapped into
int), `L'\xff'` 255 (escapes are not re-encoded).

That `'\xff'` was previously 255 instead of -1 was a pre-existing bug in the same
arm, unpinned by any fixture.

`sema/validate.rs` grew the multiple-character diagnostic for encoded constants,
matching clang's two spellings, so the too-large and too-many cases are both
diagnosed there rather than falling through to a vaguer lowering error.

Filed, not fixed: `#if '\xff' < 0` still disagrees with clang because the
preprocessor's evaluator has no target (slate-parser-l26), and plain `'Ω'`
packs UTF-8 bytes like gcc where clang rejects it (slate-parser-4zk).

Fixtures: `sema/character_constants.c`, `error/character_constant_diagnostics.c`.
