# slate-parser-6x05.38.6 X87Excess: clang -mno-sse x87 excess precision (FLT_EVAL_METHOD 2) now modeled

_2026-11-18 08:26:38_

- bead: slate-parser-6x05.38.6
- kind: bug
- area: crates/slate-parser/src/sema/numeric.rs
- area: crates/slate-parser/src/target/x86_isa.rs
- flavor: clang
- target: i686

Outcome: clang flavor with x87 float/double math (i686 -mno-sse, or double under -mno-sse2) now widens to f80 like native clang instead of translating with FLT_EVAL_METHOD 0 semantics.

Symptom: clang -m32 -mno-sse predefined FLT_EVAL_METHOD 2, but the IR rounded each operation to its own type.

Reproducer:

```c
volatile double a = 1e308, b = 10;
double r = a * b / b;   /* native clang -m32 -mno-sse: 1e+308; slate: inf */
```

Cause: `X87Excess::for_dialect` (crates/slate-parser/src/sema/numeric.rs) returned None unless the flavor was gcc, and `X86Isa::x87_formats` always applied gcc's i686 default of -mfpmath=387.

Fix: by user decision (option A), clang now enables `X87Excess` with `X87Rounding::Fast` every time. It ignores -fexcess-precision, -ffloat-store, ISO vs GNU -std, and gcc's 32-bit fast-math opt-out, because clang applies none of them to float/double. MSVC stays off. `x87_formats(family, gcc)` now takes the flavor, so clang's i686 default (SSE2) stays method 0 while -mno-sse2 puts only double on x87. That matches native clang, which reports FLT_EVAL_METHOD 0 under -mno-sse2 but still widens double.

Regression tests:
- crates/slate/tests/fixtures/i686/flag_mno_sse_excess.c (clang i686 differential, adapted from gcc/x86_64/flag_mfpmath_387_fast.c)
- crates/slate-parser/tests/fixtures/clang/linux/i686/x87_excess_precision.c (NOSSE with gcc knobs ignored, NOSSE2, SSE)

Limits: clang's backend rounds on spill, so `?:` arms and statement-expression results differ between native -O0 and -O2. They are not modeled and were cut from the fixture. clang keeps excess precision on an assignment expression's value, which slate rounds (slate-3amj.62). Per the user, the permissive gaps (_Float16/__bf16 without SSE2, long double without x87) are intentionally not tracked.

See: slate-3amj.8, wiki/concepts/ir/operations.md#x87-excess-precision
