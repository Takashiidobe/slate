# Alignment from the entity at every declaration site

_2026-09-19 20:37:03_

Phase 2 of slate-parser-8lv. Closes lh7.2.31 and lh7.2.32.

Alignment is now a property of ir::Variable rather than ir::Global, so a let
prints [align=N] exactly as a global does, and there is one field and one
print site instead of a per-site assignment. Automatic locals previously hit a
blanket 'automatic variable attributes or asm label' rejection; that guard now
only rejects attributes that are neither vector nor alignment attributes.

__alignof__ of a declared object reads the object's request from the entity.
This needed a second flavor rule, not the existing one. Measured against
clang 22.1.8, gcc 16.2.1 and MSVC 14.51:

  what the object GETS   clang = requested, gcc/MSVC = max(requested, natural)
  what __alignof__ SAYS  clang/gcc = requested, MSVC = max(requested, natural)

They differ only for gcc below natural: gcc lays an aligned(1) int out at 4
but reports 1. lh7.2.31 said to reuse resolve_object_requests' rule, which
would have reported 4 for gcc. Hence declared_alignment beside
effective_alignment.

One false alarm worth recording: clang's assembly shows .p2align 2 for
aligned(1), which looks like the request being dropped. The LLVM IR carries
align 1; the .p2align is a later section-level decision. 9ve.5's rule and the
existing [align=1] expectation were right.

Fixture churn is positional only: [align=N] moved from after [linkage=...]
into the variable production, with every value unchanged. ir-grammar.md
follows; the let production already reused 'variable'.

Filed slate-parser-kmq: parameter attributes are still blanket-rejected, but
MSVC accepts _Alignas on a parameter and clang accepts aligned, so by the
three-compiler rule neither may be an error.
