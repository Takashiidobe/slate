# Wire up sys/auxv.h HWCAP_* probes; fix bare ARM HWCAP names leaking on glibc

_2026-09-08 09:13:44_

(slate-b66b.13.9) libc-shim/include/sys/auxv.h declared getauxval() but never
included bits/hwcap.h, so none of the HWCAP_*/HWCAP2_* constants already
sitting in libc-shim/bits/{arm,aarch64}/hwcap.h were ever reachable from
<sys/auxv.h> -- both real glibc and musl sys/auxv.h include bits/hwcap.h.
Fixed by adding the include.

Comparing against real headers found libc-shim/bits/arm/hwcap.h defines
BOTH the bare (HWCAP_SWP..HWCAP_EVTSTRM) and ARM_-prefixed
(HWCAP_ARM_SWP..) spellings of the base 22 bits unconditionally. musl does
that (both spellings genuinely coexist), but real glibc only defines the
ARM_-prefixed set for the base bits -- code using bare HWCAP_NEON etc.
would compile against the shim but fail against real glibc headers. Gated
the bare spellings to __SLATE_LIBC_MUSL; HWCAP2_* (AES/PMULL/SHA1/SHA2/
CRC32) are unprefixed on both libcs already and stayed ungated.

Added emit_hwcap() to tools/probes/linux-libc-abi.c: MACRO probes for a
representative subset of HWCAP/HWCAP2 bits per __SLATE_ARCH_AARCH64/ARM
(plus the musl-only bare ARM names), skipping bits the shim doesn't model
(newer SME/SVE2/etc. additions on aarch64, and the newer unprefixed
FPHP/ASIMDHP/ASIMDDP/etc. additions on arm) per the bead's instruction not
to fabricate coverage. x86/x86_64 have no HWCAP bits in either real libc,
matching the shim's empty branch.

Verified: tools/libc-abi-matrix.py green on aarch64 and arm (x glibc/musl),
x86_64/i386 unaffected and still green, cargo nextest --profile libc 37/37.
