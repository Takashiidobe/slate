# Accept cl.exe single-byte code pages for /source-charset and /execution-charset

_2026-10-25 23:58:56_

slate-3amj.5.21: only utf-8 and windows-1252 were accepted. Charset is now Utf8 | CodePage(&'static CodePage) (src/charset.rs); Charset::WINDOWS_1252 replaces the Windows1252 variant. src/code_pages.rs holds 40 single-byte pages (437 737 775 850 852 855 857 860-866 869 874 1250-1258 10000 20127 20866 21866 28591-28599 28603 28605), each a 128-entry high table plus the names wine accepts for it.
The tables come from cl.exe, not Python codecs: tools/generate_code_pages.py decodes every byte under /source-charset:.N /execution-charset:utf-8, encodes a candidate set (every decoded char, U+0080-U+024F, U+2000-U+21FF) the other way, and checks each name and .N against _MSVC_EXECUTION_CHARACTER_SET. It exits if encoding is not the exact inverse of decoding (it is for all 40: no best fit, '?' otherwise).
Wine facts: undefined bytes decode to private-use chars in some pages (857, 864, 874, 1253, 1255, 1257, 28593, 28596-28598) and to U+00XX in others (1252's 81 8D 8F 90 9D); us-ascii decodes a high byte to byte & 0x7F (0x8A is a newline), so the generator hardcodes it. Name aliases are wine's (cp866 but not ibm866, ibm437, dos-862, macintosh, ascii; not latin1, cp1252, windows-874).
Unknown names now fail with cl's C3435 text "character set 'X' is not supported"; so do DBCS pages (filed slate-3amj.5.28) and numbers cl takes unchecked (.99999).
Fixtures: msvc/windows/x86_64/code_page_execution.c (1251 with C4566 (1251), .437, US-ASCII, koi8-r) and code_page_source.c (raw bytes under .1251, us-ascii masking, iso-8859-5 round trip), byte-checked against cl /FAs listings; error/msvc/windows/x86_64/charset_double_byte_unsupported.c. Wiki: compiler-flags charset bullet, generated-sources table. Also filed slate-3amj.5.29 for /wd /we and warning levels.
