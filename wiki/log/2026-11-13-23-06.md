# slate-dghn.58.5 lower_extern: __slate_vabi_ alias parsed as long-double C shim name, conflicting __slate_extern_vabi_ trampolines (renamed __vector_abi_)

_2026-11-13 23:06:05_

- bead: slate-dghn.58.5
- kind: bug
- area: crates/slate/src/frontend/lowerer/functions.rs
- area: crates/slate/src/frontend/c_shim.rs

Outcome: vector-ABI extern aliases are named `__vector_abi_<name>`; the `__slate_vabi_<name>` names from 09fd5a5c7 made the long-double C shim emit conflicting trampolines and broke NumPy's cargo check.

Symptom: NumPy translate-project, cargo check of the build script:

```
src/slate_long_double.c:1465:12: error: conflicting types for '__slate_extern_vabi_'; have 'int(void *, void *)'
```

Reproducer: an extern vector function whose C name contains `__` (SVML: `__svml_acosh8_ha`), in a unit that also needs the long-double shim (any extern taking `long double`).

Cause: every `__slate_*` extern is parsed as a C shim name `__slate_<callee>__<tags>` (`c_shim::render_trampoline`; the test harness's `extract_long_double_shim_names` text-scans every `__slate_` token). `__slate_vabi___svml_acosh8_ha` decoded as callee `vabi_` with tags `svml_acosh8_ha`, so each SVML function got an `int __slate_extern_vabi_(void *...)` with a different arity. No `__slate_` prefix can be excluded safely: skipping `__slate_vabi_` also swallowed the real shim `__slate_vabi_ld_double__rf80_f80` for a C function named `vabi_ld_double`.

Fix: `lower_extern` names the alias `__vector_abi_<name>`, outside the shim namespace.

Regression test: `crates/slate/tests/fixtures/x86_64/extern_vector_abi.c` now has SVML-style `__vabi_sum8` / `__vabi_scale_by16` and an asm `long double` extern `vabi_ld_double`; it failed with the conflicting-types error before the rename.
