# Recover head-tested loops to while on rewrite-engine-v2

_2026-09-04 09:06:50_

Added LoopToWhile (src/backend/engine/rules/loop_to_while.rs), a NodeRule on NodeKindTag::Loop that recognizes the lowerer's raw `loop { if !cond { break } body }` shape (guard_break in frontend/lowerer/control_flow.rs) and rewrites it to idiomatic `while cond { body }`, negating the stored `!cond` back to `cond`. Registered at priority 20 in engine/rules/mod.rs, after ForRangeRecover (13) and ForArrayIterRecover (14) so those get first claim on the raw Loop shape before it's converted away.

The old salsa-era equivalent (structure_dispatch/simplify.rs's loops_to_while) was deleted same-day in the goto/switch restart (52f14481) before ever landing on the new engine; slate-04q.85.2 asked for its reimplementation. Confirmed via git archaeology that currently *nothing* converts any Loop to While post-restart, for either lowerer-emitted or structure_dispatch-built loops — the bead's premise ("only works for structure_dispatch loops") described a transient intermediate state 15 minutes before the restart commit, not current HEAD.

Only handles unlabeled loops: rust_ast::Stmt::While has no label field, so a loop kept alive by a genuine continue/labeled break (continue_while.c) can't convert without a bigger, separate change to add labeled-while support. Regenerated loop_sum.c's REWRITES FileCheck block; continue_while.c's regenerates identically (no label, no change). Confirmed the whole rewrites FileCheck path is currently an unconditional no-op (tests/support/filecheck.rs:52 returns Ok(()) whenever profile == Rewrites, not just for -DAG/-NOT lines as previously recorded) -- so the regen was for documentation accuracy, not test-passing.

Full `rewrites` profile: 93/93 (including generated_differential across the whole corpus), cargo clippy and fmt clean. Documented the rule in wiki/concepts/passes.md.
