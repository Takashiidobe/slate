# Atomic fetch uinc/udec lower to compare-and-select counters

_2026-09-20 14:22:41_

`__atomic_fetch_uinc`/`__atomic_fetch_udec` (the builtin names carry no
`_wrap`, unlike the `atomicrmw uinc_wrap`/`udec_wrap` they emit) now lower.
They need no new `ArithOp`: expanding clang's output with
`opt -passes=atomic-expand` gives exactly the compare-and-select form the IR
already has, and being integer-only there is no NaN problem to make it
inexact, as there was for floating min/max (lh7.2.33).

  uinc: ge(old, v) ? 0 : add(old, 1, overflow=wrap)
  udec: logical_or(eq(old, 0), gt(old, v)) ? v : sub(old, 1, overflow=wrap)

Both compares are unsigned whatever the object's signedness -- verified that
clang emits `icmp uge` even for an `int` object -- so a signed object
reinterprets both operands. That is the same reinterpret the
`__sync_fetch_and_umin/umax` path already does, including the redundant
round trip when the operand was converted to a signed place type first.

Factored the reinterpret out of the min/max arm into `compared_as`, and the
compare-node construction into `compare`; both arms now share them.

Spelled only as `__atomic_fetch_<op>`, which the `FetchSpelling` gate added
in the previous change already enforces.

Found while auditing: `_Atomic _Bool` fetch arithmetic is unsupported for
every operation, not just these two (slate-parser-lh7.2.41).

Covered by a new `wrapping` function in
`tests/fixtures/sema/ir_atomic_extensions.c`, including a signed object.
