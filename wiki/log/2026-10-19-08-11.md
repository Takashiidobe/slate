# Add fixtures.dylink: dlopen and LoadLibrary hosts against prebuilt shared libraries

_2026-10-19 08:11:13_

tests/fixtures.dylink/<name>/{host,lib} plus a shared dylink.h (dl_open/dl_sym/dl_close map to dlopen or LoadLibraryA). lib/_.c is always built natively (clang -shared -fvisibility=hidden, or cl.exe /LD under wine); host/_.c is built natively as the oracle and translated with translate-project; both run in the dependency's directory and stdout and exit code must match. Fixtures: basic (scalar ABI, missing library/symbol, non-exported symbols), data_structs (exported globals, structs by value and pointer, strings), callbacks (host fn pointers called by the lib, lib fn pointers returned), lifecycle (constructor/DllMain, shared handle state, unload and reload).

tests/dylink.rs: dylink_linux always runs; dylink_windows builds the translated host for x86_64-pc-windows-msvc (cargo with lld-link, LIB from msvc-wine) and runs both hosts under wine; it skips with a message when wine, lld-link, msvc-wine or the rust target is missing, and SLATE_DYLINK_REQUIRE_WINDOWS=1 makes that a failure. support gained build_project_release_for_target and Run::stdout/exit.

Findings: windows.h cannot be used by a translated host yet because FARPROC (return type of GetProcAddress) is an unprototyped function pointer, slate-8x0b; hosts declare LoadLibraryA/GetProcAddress/FreeLibrary themselves. The MSVC-target output inlines the CRT printf, so \r\n matches the cl.exe oracle without normalization. Two fixture bugs found by the oracle: printf args with side effects have unspecified order and MSVC evaluates right to left.

Validation: dylink_linux and dylink_windows pass; full slate profile not rerun (only new test files and a support addition).
