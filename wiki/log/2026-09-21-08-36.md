# Capture VLA bounds in compound literals at the place level

_2026-09-21 08:36:26_

lh7.2.35. `(int (*)[n]){p}` failed with "nonconstant or unknown
identifier" while the cast spelling `(int (*)[n])p` worked.

Cause: the capture protocol from lh7.2.24 is ordering-sensitive in a
non-obvious way. `extents()` (sema/module.rs) records
`types.extents.insert(expr.id, id)` keyed on the bound's AST expr id,
and `ctype/layout.rs` only produces `VariableExtent::Captured(id)` if
that entry already exists. So `type_name_extents` MUST run *before*
`resolve_type_name`, or layout falls back to constant-folding the
bound and fails. Cast and sizeof both did this; the compound literal
arm did not.

The second half is that `with_extents` wraps an `Operand`, but
`ExprKind::CompoundLiteral` lowers to an `Lvalue`, so the value-level
wrapper had nowhere to attach. Fix: split a `captured()` helper that
folds `ValueKind::Capture` over a plain `Value`, and wrap the
literal's initializer with it. `effects.rs::place` already routes
`PlaceKind::CompoundLiteral { initializer }` through `value()`, which
turns each `Capture` into a `Statement::Temporary`, so the bound lands
hoisted ahead of the literal with no new machinery. `with_extents` is
now a thin Operand wrapper over `captured()`.

Fixture: tests/fixtures/sema/variable_length_array_compound_literals.c

Found while testing, filed as lh7.2.43 and NOT fixed here: `sizeof` of
a dereferenced VLA-typed expression drops the capture and emits a read
of an unbound BindingId. It reproduces on the pre-existing cast path
(`sizeof(*(int (*)[n])p)`), so it is independent of this change.
sizeof discards the operand value, taking the `Capture` wrapper with
it, while the result type still names the binding. C11 6.5.3.4p2 says
a variably modified operand *is* evaluated, so the capture should be
kept rather than dropped.
