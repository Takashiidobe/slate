# bitint shifts accept any integer shift amount

_2026-09-02 15:06:27_

`vendor/bitint` implemented `Shl`/`Shr` only for `usize`, but a C shift amount
lowers as its own promoted type (`i32` for a plain literal, `u32`/`i64`/`u64`
for the others, and a `BInt`/`BUint` when the amount is itself a bitint), so
any `_BitInt` shift failed to compile.

Replaced the eight `usize`-typed impls with a `ShiftAmount` trait and eight
generic ones. `ShiftAmount` is implemented for every primitive integer via a
macro (`usize::try_from(self).unwrap_or(usize::MAX)`) and for `BUint`/`BInt` of
any width. Eight impls rather than ~100 monomorphic ones.

Out-of-range and negative amounts are C UB; mapping them to `usize::MAX` lands
them in the existing `shift >= BITS` branch of `shl_bits`/`shr_bits`, which
returns ZERO (or all-ones for a negative arithmetic `>>`). Nothing panics.

Investigating `tests/fixtures.unsupported/bitint_arith.c` (slate-2o6o.16) also
established what is *not* missing:

- Arbitrary widths already work end to end: 3, 129, 256, 512, signed and
  unsigned, `+ - * / % < >`, negation, and decimal literals past `u128::MAX`.
- Mixed-type arithmetic needs no `Mul<i32> for BInt`-style impls. C converts
  both operands to the bitint type first, and CIR hands slate that conversion
  explicitly, so the generated Rust is always `BInt op BInt`. Shifts are the
  sole exception, since C promotes shift operands independently.
- The remaining blocker is upstream, not in slate: `isSupportedType` in
  ClangIR's `CallConvLoweringPass.cpp` caps bitint at 128 bits, so any function
  whose *signature* mentions `_BitInt(>128)` fails at `-emit-cir`. Being fixed
  upstream; `bitint_arith.c` stays in fixtures.unsupported until then.

New fixture `tests/fixtures/bitint_shift.c`.
