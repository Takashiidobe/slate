# slate-f2zu.14.34.20 build_target shared_flags: rustc MergeFunctions emitted .text..Lanon.\* orphan sections in vmlinux; add -Zmerge-functions=disabled

_2026-11-15 15:35:49_

- bead: slate-f2zu.14.34.20
- kind: bug
- area: crates/slate/src/project/build_target.rs
- corpus: linux

Outcome: bare-metal x86 crates (x86_64-unknown-none and the i386 spec) build
with `-Zmerge-functions=disabled`, so rustc's LLVM MergeFunctions no longer
emits anonymous private functions in `.text..Lanon.<hash>.N` sections, the last
unplaced orphan sections in the vmlinux link.

Symptom: vmlinux link with --orphan-handling=error: 23 "unplaced orphan section
`.text..Lanon.<hash>.0' from `vmlinux.o'". The `.gcc_except_table` half of the
bead was already gone after slate-f2zu.14.34.14.

Cause (verified on the init shard): the sections hold code, not constants, for
example `endbr64; cs jmp __x86_return_thunk` (an empty function) in slate*crate
and float-compare bodies in compiler_builtins. rustc runs LLVM MergeFunctions by
default (`-Zmerge-functions=aliases`). When identical functions are merged, the
shared body goes into a new private, unnamed function that is emitted as
`.Lanon.*`. With function sections it lands in `.text..Lanon._`. The kernel linker script matches `.text.[0-9a-zA-Z_]\*`, and the double dot is reserved for special sections, so these were orphans. Rebuilding the init shard with `-Zmerge-functions=disabled`left no`.text..Lanon`
section in any archive member, compiler_builtins included (build-std uses the
same rustflags).

Fix: `shared_flags` (crates/slate/src/project/build_target.rs) always appends
`-Zmerge-functions=disabled`. It is used only for the core-only, SSE-free
bare-metal targets. C has no counterpart: clang and gcc do not merge functions
by default. Hosted crates are unchanged. Spec: wiki/concepts/ir/calls-abi.md
(bare-metal build target).

Regression test: crates/slate/tests/differential.rs
`freestanding_projects_build_for_bare_metal_targets` now requires the flag in
both the kernel and the -m16 config (failed before the fix).

Limits: not yet confirmed by a full kernel relink (planned after this batch). A
small code-size cost from duplicate bodies, which matches C.

See: slate-f2zu.14.34.14, slate-f2zu.14.34.6.
