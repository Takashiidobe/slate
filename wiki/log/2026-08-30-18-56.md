# Fix GNU __label__ collision in ClangIR upstream (slate-clvn)

_2026-08-30 18:56:53_

Root cause: CIRGen (CIRGenStmt.cpp, CIRGenExprScalar.cpp,
CIRGenExprConstant.cpp) emitted cir.goto/cir.label/block_addr attrs using only
LabelDecl::getName(), discarding LabelDecl* identity. GotoSolver.cpp then
resolves labels via a single function-wide StringMap<Block*> keyed on that
spelled name. GNU __label__ locally-scoped labels legally reuse the same
spelled name across separate lexical instances of the same macro expanded
multiple times in one function (e.g. CHECK_VALUE(...) called twice), so the
solver silently collided distinct LabelDecls onto the first one's block,
producing wrong control flow (infinite loop in statement_expr_local_label.c).

Fix (in ~/llvm-project, clang/lib/CIR/CodeGen): added
CIRGenFunction::getOrCreateCIRLabelName(const LabelDecl*), a per-function
DenseMap<LabelDecl*, string> + StringMap<unsigned> counter that appends a
disambiguating ".N" suffix the first time a spelled name repeats. Routed all
5 call sites (emitGotoStmt, emitLabel, VisitAddrLabelExpr x2,
AddrLabelDiff case) through it instead of ->getName(). GotoSolver itself is
unchanged; its text-based lookup is now correct because CIRGen no longer
hands it colliding names.

Rebuilt build-cir clang+cir-opt and the macro-dump plugin against it.
Verified via a minimal standalone reproducer (two statement-expr instances
of the same __label__ name) and via
tests/fixtures/statement_expr_local_label.c (promoted from test-fixtures/,
prints "17 -5 2" matching native C on both lowering and rewrites profiles).
