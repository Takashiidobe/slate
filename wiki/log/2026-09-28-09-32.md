# Model x86-32 calling conventions in function types

_2026-09-28 09:32:52_

slate-parser-v910: __stdcall/__fastcall/__vectorcall/__thiscall (keywords and GNU attributes) are now part of the function type on 32-bit x86 (TargetFamily::X86). CTypeKind::Function and ir::Type::Function carry a CallConv; the IR prints fn stdcall(...), and AbiSignature.calling repeats it so calls keep the convention under --compact-ir, where the call signature is not printed.

Scope decision (with the user): record the convention, don't model its effects. inreg register assignment, stdcall callee cleanup, vectorcall XMM/HVA passing and Windows symbol decoration (_f@8, @f@8, f@@8) are what LLVM derives from x86_stdcallcc etc.; the Rust side gets them for free from extern "stdcall". The argument pass shapes stay the platform cdecl ones. byval/sret/coerce differences between gcc and clang are a separate discussion.

Placement mirrors clang: a decl-spec convention goes to the innermost function declarator (derive's innermost argument, checked with has_function_declarator), or to the base type when the declarator has none (a function typedef); one on a pointer/Attributed declarator applies to the type beneath it; trailing declarator and function-definition attributes apply to the first function reached through pointers/arrays (CTypes::with_convention). Variadic functions drop the convention, as clang does.

Compatibility: conventions must match (compatible_functions, same_or_enum_underlying). A later declaration without a convention inherits it (inherit_convention, run before the type is used for the ABI); adding or changing it is an error, since clang, gcc and cl.exe (x86) all reject both that and cdecl<->stdcall pointer initialization.

Not modelled: __vectorcall on x86_64 (clang honours it; follow-up bead), regparm.
Found in passing: typeof(&f) inside a static assertion fails after f's definition, before this change too (slate-parser-evdx).
