# quad long double (f128) lowering fixes (slate-sdks.3)

_2026-09-05 09:30:42_

Root cause: like the char-signedness bug, c_ast.rs::parse_c_type hardcoded
\"long double\" to CType::Float{bits:80} (x87 extended) unconditionally,
regardless of target. On aarch64-linux, long double is IEEE binary128, but
every AST-only fallback path (record fields, sizeof) kept treating it as the
x87 LongDouble wrapper struct (10 bytes in a 16-byte slot), corrupting values
and producing inconsistent f128-vs-LongDouble types for the same field.

Fix: added toolchain::long_double_bits(target) (128 for aarch64/arm/riscv, 64
for the existing f64-ABI targets, 80 otherwise) and wired it into
parse_c_type, mirroring char_is_signed_default. The already-correct
CIR-driven paths (rust_type_with_aliases, cir_type_to_ctype) needed no
changes - they already special-cased is_quad_long_double() correctly; only
the AST fallback was wrong.

Two further gaps surfaced once the type was correct:
1. _Complex long double division/multiplication has no native Rust equivalent
   bit-identical to libgcc's Smith's-algorithm runtime calls. Extended the
   existing __muldc3/__divdc3 (f64) and __mulsc3/__divsc3 (f32) direct-extern-
   call mechanism to also cover __multc3/__divtc3 (f128/quad), which fixed
   long_double_complex's 1-ULP divergence.
2. Record fields resolving to f128 didn't set the uses_f128 flag that gates
   `#![feature(f128)]` (lower_record wasn't threaded like lower_record_def's
   caller for uses_long_double). Added ctype_uses_f128 alongside the existing
   ctype_uses_long_double and wired it into lower_record.

long_double_f80_arithmetic.c is inherently x87-specific (hardcodes 10-byte
extended-precision bit patterns via memcpy) and was marked x86_64-only via a
dg-do directive rather than "fixed" - it isn't a meaningful test of any other
format.

Verified: aarch64-lowering, aarch64-rewrites, x86 lowering/rewrites/libc all
pass with zero regressions. Closed slate-sdks.3.
