# Gate regex_t layout and regoff_t width by libc

_2026-09-08 09:36:05_

(slate-b66b.13.14) Probed regex_t/regmatch_t in tools/probes/linux-libc-abi.c
(SIZE/ALIGN/OFFSET on re_nsub, rm_so, rm_eo) and ran libc-abi-matrix across
all 4 arches x 2 libcs.

Found two real bugs, both real for glibc only (musl already matched):

1. libc-shim/include/regex.h's single unconditional regex_t placed re_nsub
   as the FIRST field. Real glibc's re_pattern_buffer puts re_nsub 7th,
   after buffer/allocated/used/syntax/fastmap/translate (all pointer- or
   long-sized). re_nsub is POSIX-documented as accessible after regcomp,
   so a caller reading it at offset 0 instead of offset 24/48
   (32-bit/64-bit) reads garbage. Total struct size happened to already
   match by coincidence (same field count, mix of ptr/long fields).
   Fixed by adding a __SLATE_LIBC_GLIBC branch with the real 7-field-plus-
   bitfield-word shape; musl's existing opaque shape kept unchanged.

2. bits/types.h defined __regoff_t as `long` unconditionally for the
   non-Darwin/FreeBSD branch. That's correct for musl (regoff_t is long
   there) but wrong for glibc, which uses plain `int` (regoff_t only
   widens under _REGEX_LARGE_OFFSETS, which glibc doesn't define). Wrong
   width doubled regmatch_t's rm_so/rm_eo size and align. Gated by
   __SLATE_LIBC_GLIBC.

Also had to split libc-shim/include/regex.h's darwin/freebsd early-return
from the musl/glibc common tail (regmatch_t typedef, enums, decls) --
previously they were all one flat #else, which cannot host a further
glibc-vs-musl split without leaking the glibc regex_t branch's scope into
the darwin/freebsd early-return path.

Verified: tools/libc-abi-matrix.py green for regex_t/regmatch_t on all 4
arches x 2 libcs (2821/2821 records), cargo nextest --profile libc 37/37.
