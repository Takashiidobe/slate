# Rule scope tagging for worklist parallelism

_2026-08-27 21:47:01_

Design sketch (not yet built) for scaling the post-salsa NodeRule worklist
engine (src/backend/engine/) to thousands of stdlib-idiomization rules
without regressing to salsa-era slowness.

Add a Scope classification to NodeRule: Expr, Forward, Function,
Interprocedural. Default = Function, so an unclassified rule keeps today's
exact sequential run_worklist behavior — the tag is opt-in, ignorable.

- Expr (matched node's own subtree only): expected to be the majority of
  rules. Run as a separate fast lane before the general worklist — par_iter
  matches() across all live nodes (pure reads), apply serially, iterate to
  local fixpoint. No worklist requeue bookkeeping needed since there's no
  ancestor/sibling effect by construction. Shrinks what the general worklist
  has to process.
- Forward (matched node + forward uses within the function, e.g. return-value
  mutation, ptr-escape-to-index conversions): common enough to matter but
  needs each rule to report a write-set (binding + range) so overlapping
  Forward rules can be detected before running concurrently. Tag now, keep
  execution serial in run_worklist until Expr-lane + cross-function
  parallelism are shipped and profiled.
- Interprocedural: run earlier (as a pre-pass, like existing
  interproc::string_params::run) specifically so everything after it can
  assume stable function boundaries and run in parallel. Not worth
  parallelizing internally — mirrors LLVM CGSCC's own sequential-by-SCC
  design, since these rules mutate call sites broadly.
- Function: unchanged, still the general run_worklist, just against a
  smaller registry once Expr rules are pulled into their own lane.

Not profiling the current untagged engine before building this: already
tried profiling/hacking on the pre-Scope machinery at length and it wasn't
productive — without the Scope abstraction in place first, perf work turned
into ad hoc patching that never reached a satisfying result. Building the
Scope-tagged design directly instead of re-attempting profile-driven
optimization on the current engine.
