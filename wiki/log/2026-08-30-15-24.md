# slate-a28e.15: alloca-frame field cast for idiomized const-ptr params

_2026-08-30 15:24:36_

Root cause: raw lowering makes every pointer alloca-frame field *mut T
unconditionally (const is never tracked at that stage - types.rs
CirType::Pointer always lowers to Type::Ptr{mutable:true}). The REWRITE-stage
pointer_lattice pass separately idiomizes read-only pointer params into
&T based on actual usage, independent of the raw-lowering default. When such
an idiomized &T param gets stored into its (always-mutable) alloca-frame
field, rewrite_stmt's Stmt::Assign handling only computed target mutability
for Expr::Var targets, not Expr::TupleField (frame field) targets - so it fell
through to a path that re-cast the &T back to a raw pointer with the WRONG
constness, producing E0308 (zstd zdict.rs, using ZSTD_parameters* param).

Fix: src/backend/interproc/pointer_lattice.rs rewrite_stmt - Expr::TupleField
targets (alloca-frame fields) are always declared mutable, so map them to
Some(true) in the same target_mutable lookup used for Expr::Var, letting
to_raw_pointer_as apply the correct *const -> *mut two-step cast.

Fixture: tests/fixtures/alloca_frame_const_ptr_param.c. Its FileCheck blocks
are hand-written, not tool-generated: update_filecheck.py's fn-begin markers
can't bracket this function because alloca-frame-group functions are emitted
after all non-grouped functions (including the marker stub functions), so
the markers and the target function end up non-adjacent in the generated
Rust and extract_generated_regions captures an empty region. The bug itself
lives in the function's prologue (parameter-to-frame-field assignment),
which no statement-level marker can reach either. Verified via differential
+ hand-authored FileCheck on both profiles, full rewrites (90/90) and
lowering (10/10) suites, and a real zstd check-zstd run (E0308 gone, only
pre-existing FFI-safety warnings remain).
