# slate-f2zu.14.40.14 __slate_cleanup::Guard: cleanup closure and always_inline handler compiled into the incremental fallback CGU

_2026-11-16 16:24:34_

- bead: slate-f2zu.14.40.14
- kind: bug
- area: crates/slate/src/frontend/support/cleanup.rs
- area: crates/slate/src/frontend/lowerer

Outcome: __attribute__((cleanup)) guards no longer put cleanup handler code (and its inline asm) into rustc's incremental fallback codegen unit; each unit's cleanup code stays in that unit's object.

Symptom: with the link-order build (incremental, one CGU per unit), the <crate>-fallback.cgu object held drop_glue::<Guard<{closure}>> for every unit with a cleanup, with the closure body and its #[inline(always)] destructor inlined, including tracepoint asm-goto __jump_table and .discard.annotate_data entries. Cleanup code left its C TU; a handler naming a file-scope asm local label would fail to link like slate-f2zu.14.40.12.

Reproducer (minimal C):
    static inline __attribute__((always_inline)) void unlock(int *d) { __asm__ volatile("" ::: "memory"); *d = 0; }
    int f(int n) { int held __attribute__((cleanup(unlock))) = n; return held + 1; }

Cause: rustc partitioning (characteristic_def_id_of_mono_item) sends drop glue, and under incremental also Drop::drop, to the fallback CGU. Guard<F: FnMut()> was generic over the closure type, so Drop called the closure directly and LLVM inlined the closure and handler there.

Fix: crates/slate/src/frontend/support/cleanup.rs is now
    pub struct Guard<'a>(pub &'a mut dyn FnMut());
    impl Drop for Guard<'_> { fn drop(&mut self) { (self.0)() } }
and cleanup_guard (statements.rs) / dispatch_cleanup_guard (control_flow.rs) emit Guard(&mut || handler(ptr as *mut _)). The closure is called through its vtable, which is instantiated where the coercion happens (the unit's CGU); drop glue is one vtable load and an indirect tail call. Temporary lifetime extension through the tuple-struct constructor keeps the closure alive for the guard's scope. dead_store still matches "__slate_cleanup::Guard".

Why not the fn-pointer Guard proposed in the bead: storing `unsafe fn(*mut T)` needs the handler's ABI, safety and return type, which the lowerer's FunctionName does not carry (extern "C" handlers, non-void returns). The dyn closure gives the same indirect-call boundary with no signature dependence and keeps the existing `as *mut _` cast.

Verified: arch_x86_kernel + init probe crates (un-hoisted, link-order flags + incremental): fallback object went from 67 functions + __jump_table + .discard.annotate_data to 12 drop glues, each `mov; mov; mov; jmp __x86_indirect_thunk_r11`, no asm sections. vmlinux links, objtool warnings 33 (34 with the old Guard), boots to busybox, loopback ping OK.

Regression test: crates/slate/tests/fixtures/cleanup_always_inline_handler.c (always_inline handler with asm, early return, goto past a cleanup); FileCheck regenerated for cleanup_nested_block, cleanup_scoped_guard_for_goto, gnu_attributes, zero_init_cleanup_guard_order, x86_64/asm_immediate_cleanup_after_inlining.

Limits: one indirect call per scope exit in every build mode (non-link-order builds could previously inline the handler into drop glue). With IBT the closure call_mut is reached by an indirect call; objtool did not warn.

See: slate-f2zu.14.40.13 (one object per C unit), slate-f2zu.14.40.12.
