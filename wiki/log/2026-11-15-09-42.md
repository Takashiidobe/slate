# slate-f2zu.14.34.11 program_entry: freestanding main is an ordinary exported symbol (staticlib accepted) and no_std roots define a weak rust_eh_personality; m16 boot shards build

_2026-11-15 09:42:53_

- bead: slate-f2zu.14.34.11
- kind: bug
- area: crates/slate/src/frontend/lowerer.rs
- area: crates/slate/src/main.rs
- area: crates/slate/src/project/merge.rs
- area: crates/slate/src/frontend/support
- target: x86_64-unknown-none

Outcome: a freestanding (`-ffreestanding`) `main` lowers as an ordinary exported C function, so all-freestanding projects that define it translate with `--crate-type staticlib`, and `no_std` crates no longer leave `rust_eh_personality` undefined; the arch_x86_boot_m16 and _packed_m16 linux shards build.

Symptom: both -m16 shards define `main` (arch/x86/boot/main.c, realmode wakemain.c), so translate-project rejected `--crate-type staticlib` ("applies only to library projects, but main defines main") and built them as no_std bins for i386-unknown-none. rust-lld then failed: undefined `rust_eh_personality`, and `intcall` (bioscall.S), `HEAP`/`heap_end`/`video_cards` (setup.ld). In the kernel these `main`s are ordinary symbols that header.S calls, linked with .S objects under a linker script.

Reproducer (kernel flags, translate-project --crate-type staticlib, then link the archive):
```c
extern int seven(void);
static int (*volatile source)(void) = seven;
static int counter;
static void step(int amount) { counter += amount; }
void main(void) { step(source()); step(-3); }
```
Before: "defines main" error; once accepted, `ld` reported `(.eh_frame+0x13): undefined reference to rust_eh_personality`. After: translates, builds for x86_64-unknown-none, and links with `seven.S` and `-e main`.

Cause:
- `function_rust_name`, `exports_symbol` and both project-root checks (main.rs `write_project` roots, merge.rs `defines_main`) treated every `main` as the program entry. In C a freestanding program's startup is implementation-defined, so `main` is not special there.
- `panic=abort` gives every call through a `C-unwind` function pointer an abort-on-unwind landing pad, whose `.eh_frame` references `rust_eh_personality`. Extern declarations are already `"C"`; slate's C function pointer types are `C-unwind`. Hosted crates get the symbol from std, and nothing provides it in `no_std`.

Fix:
- `lowerer::program_entry(module, function)` = `module.hosted && name == "main"` now gates the `__slate_main` rename, the export exclusion and root detection. A freestanding `main` is always exported (`#[unsafe(no_mangle)] extern "C-unwind" fn main()` with its C signature) so crt or asm can call it. A single-file translation keeps `#![no_main]`, and project mode drops it from non-root unit files. `Tables` now carries the module for the extern `link_name` check.
- `panic_c.rs`/`panic_loop.rs` define `#[linkage = "weak"] #[unsafe(no_mangle)] extern "C" fn rust_eh_personality() {}`; a freestanding root adds `#![feature(linkage)]`. The definition is weak so several shard staticlibs can link together.

Regression test: `freestanding_main_links_as_an_ordinary_symbol` (crates/slate/tests/differential.rs) with fixtures.arch-mode/freestanding_entry.c and seven.S (callee plus `__x86_indirect_thunk_r11` for -mretpoline-external-thunk). It failed first on each of the two causes. FileCheck regenerated for fixtures/freestanding_no_std.c and freestanding_void_main.c (shim gone). Deleted fixtures.unsupported/freestanding_huge_bitint_main.c: its barrier was the std-only 1 GiB-stack main shim, which freestanding main no longer gets (native clang also takes over 9 minutes on it at -O0).

Shards: arch_x86_boot_m16 and _packed_m16 retranslated with `--crate-type staticlib` (no "defines main" fallback) and clean-built, 0 errors.

Limits: a hosted `-nostdinc` main still gets the shim, and a huge _BitInt there is still barriered.
