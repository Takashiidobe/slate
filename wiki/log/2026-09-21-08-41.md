# sizeof of a VM expression must survive the unevaluated-type rollback

_2026-09-21 08:41:53_

lh7.2.43, the sibling of lh7.2.35.

`sizeof(*(int (*)[n])p)` emitted `mul<u64>(read<u64>(%12), const<u64>(4))`
with `%12` never bound. `unevaluated_type` (sema/expression.rs) lowers
the operand only to read its type, then rolls back `next_id`,
`entities` and `globals` so sizeof stays code-free. That rollback threw
away the extent captures while the resulting `Type::VariableArray`
still named their `BindingId`, and `runtime_size` read it. The rolled
back id counter is also why every affected function printed the same
`%N` -- the id was recycled per call site, not shared.

Fix: `unevaluated_type` returns `(QualType, Option<Value>)` and skips
the rollback exactly when the operand allocated new bindings AND its
type is a top-level `VariableArray`. It hands back the lowered operand
(`AddressOf` for the place case) so the `Capture` chain survives;
`SizeOfExpr` sequences it ahead of `runtime_size`, and `effects.rs`
turns each `Capture` into a hoisted `Temporary`. The error path still
rolls back.

Both halves of the gate are load-bearing, and each was found by a
fixture case rather than by reading:

- Without the `next_id` check, `sizeof(*q)` on an already-captured VLA
  parameter gains a noise statement. `discard()` only suppresses a
  value that HAD effects and lost them to hoisting; a pure operand is
  pushed.
- Without the `VariableArray` check, `sizeof((int (*)[next()])p)`
  would call `next()`. clang returns a flat 8 there, but does call
  `next()` for `sizeof(*(int (*)[next()])p)` -- the deref is what makes
  the operand's own type variably modified. Verified against clang
  22.1.8 `-emit-llvm`.
