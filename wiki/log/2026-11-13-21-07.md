# slate-dghn.58.2 long double bridge: f80 variadic argument to unknown-header extern variadic (PyOS_snprintf) barriered

_2026-11-13 21:07:40_

- bead: slate-dghn.58.2
- kind: bug
- area: crates/slate/src/frontend/lowerer
- target: x86_64

Outcome: a long double passed in the `...` of a body-less variadic function with no known header (NumPy's `PyOS_snprintf`) now lowers through the native-ABI `__slate_icall__` trampoline instead of the `long double: call to <callee>` barrier.

Symptom: numpyos.c `NumPyOS_ascii_formatl` failed with `long double: call to PyOS_snprintf`.

Reproducer:

    int my_snprintf(char *buf, size_t n, const char *fmt, ...);
    int main(void) { char b[64]; long double x = 1.5L; my_snprintf(b, sizeof b, "%Lg", x); }

Cause: in `lower_value_node` (frontend/lowerer/values.rs) the arm that routes variadic direct calls through `lower_long_double_variadic_direct_call` only fired when the fixed signature held f80. With f80 only among the variadic arguments the call fell to `lower_long_double_bridge`, which barriers for variadic callees missing from `function_identity::Known` because the name-based bridge needs a header prototype to forward `...`.

Fix: that arm now also fires for an extern variadic callee not in `Known` when any variadic argument bridges long double. The call becomes `__slate_icall__r<ret>_<fixed>__<variadic>(__slate_ldfp_<unit>_<callee> as *const (), ...)`, with the `__slate_ldfp_` entry `link_name`d to the callee, so the C trampoline calls it as `<ret> (*)(<fixed>, ...)` and loads each f80 argument into a real x87 value. Calls to known-header variadics (printf family) still use the header bridges.

Regression test: crates/slate/tests/fixtures.release/long_double_variadic_extern (two units; mixes int, double and long double variadic arguments).
