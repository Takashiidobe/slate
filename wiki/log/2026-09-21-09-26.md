# Win64 classifies records by size ahead of the flat gate

_2026-09-21 09:26:23_

slate-parser-57a. The bead asked whether MSVC passes a lock-prefixed atomic
aggregate by its atomic size. It does -- but measuring it turned up a bigger
pre-existing defect, and that is the actual fix.

record_abi checked the flat gate (all fields Numeric/Bool/Pointer,
non-recursive) before looking at the convention. flat is not an ABI concept;
it is a confidence proxy for "can I name the register pieces", and native_c
is an abstention, not a passing shape. The proxy is right for sysv64, whose
eightbyte classification needs a field walk, and wrong for win64, which
classifies on size alone. Against clang -target x86_64-pc-windows-msvc we
were abstaining on struct { char a[3]; } (clang: indirect), struct { struct
three t; } (indirect) and struct { char a[8]; } (i64) -- all plain records,
no atomics involved. The win64 arm now runs ahead of the gate; all 13 shapes
in the new fixture match clang, including float-only records, which size-only
gets right too.

With that, the atomic half needs no special rule at all: layout() is already
atomic-aware, so deleting the win64 half of the rejection gives the measured
answer. cl.exe 19.51 /experimental:c11atomics confirms argument and return:
_Atomic struct { char a,b,c; } is 8 bytes and goes in rcx where the plain
3-byte record goes by reference; the 5- and 24-byte records copy exactly 12
and 32 bytes, which is what pins the parameter object as the lock-prefixed
one rather than the value.

WinArm64 held back as slate-parser-o9q: it has the same gate problem, but its
HFA check genuinely needs a field walk and ours is non-recursive, so moving
the size rule ahead of the gate would classify struct { struct hfa h; } as a
non-HFA and coerce it to [2 x i64] where clang gives [4 x float] -- turning a
safe abstention into a wrong answer. The arm64 cl.exe measurement is already
done and recorded on that bead.

Two other measurements worth keeping: MSVC rejects _Atomic struct pair as a
return type (C2024, 'alignas' attribute applies to variables...), which
confirms the lock-free-branch over-alignment is implemented as an alignas on
the elaborated specifier and explains the spelling-dependence found in
slate-parser-rol. And passing a lock-prefixed atomic by value needs
<stdatomic.h>, else C2065 on _Atomic_lock_and_load.
