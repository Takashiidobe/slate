# Duplicated in-progress work: search before creating a new epic

_2026-08-27 22:16:43_

Created a new epic (slate-gfyj, "Rewrite-engine throughput redesign") this
session covering rule dispatch, interning, def-use edges, and fact
derivation for src/backend/engine/ -- without first running bd search or
llog search for existing related work. It duplicated slate-y0qs.3

engine"), already in progress, with a full handoff spec at
wiki/concepts/rewrite-engine-v2.md that had already decided: two-tier
dispatch (node-kind, then call-target-name anchor), hand-rolled
node-ID-keyed fact caches with def-use-neighbor requeueing replacing salsa,
and flagged interprocedural rules (string_params, ptr_len) plus a
c2rust-derived pointer capability lattice as a separate SCC-worklist problem
(slate-y0qs.4) -- all ground this session's conversation re-derived from
scratch as if novel, including the c2rust lattice discussion.

No code was lost -- gfyj.1/.2's actual work (Ident interning, tier-1
NodeKindTag dispatch) matched the existing spec and was folded into
slate-y0qs.3 via notes; gfyj.3/.4 were closed as superseded by the same
spec's Facts section; gfyj.5 (parallelism, genuinely not covered by y0qs)
was reparented under slate-y0qs instead of staying a freestanding epic.

Lesson: for "let's build X" asks that smell architectural (not a bug fix),
run bd search + llog search for the subsystem name before creating tracking
structure, not just before writing code. A design conversation covering
dispatch tables, fact invalidation, or interprocedural fixpoints in this
codebase is very likely to already have a decided answer recorded in
wiki/concepts/.
