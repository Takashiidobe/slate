# MS __forceinline, __ptr64 and __unaligned

_2026-09-27 10:14:01_

slate-parser-v74.1.3 (.1 __forceinline, .2 __ptr64, .3 __unaligned).

All three are gated like __int64/__pragma: msvc flavor, or clang on
*-windows-msvc. Outside that they stay identifiers (ms-winnt-keywords-off.c).

- __forceinline: Keyword::ForceInline sets is_inline and pushes an AlwaysInline
  attribute, so it is inline=always with the usual inline definition rules.
- __ptr64: Keyword::Ptr64 is consumed and dropped in parse_pointer_qualifiers.
  clang-cl gives sizeof(int * __ptr64) == 8 and _Generic selects int *, and
  every supported Windows target is 64-bit.
- __unaligned: Qualifiers::is_unaligned in the AST and sema. It takes part in
  type identity, and dropping it warns like const. Alignment
  (TypeResolver::declared_storage) goes to 1 for _Alignof and declared objects
  but not record members. The oracles differ: clang applies it to any type,
  cl.exe only to pointer types (_Alignof(__unaligned int) == 4 but
  _Alignof(int *__unaligned) == 1). Both keep
  struct { char c; __unaligned int x; } at 8/4. Rendered as __unaligned and
  c_unaligned metadata.

The bead was split at the user's request. __ptr32/__sptr/__uptr need a real
32-bit pointer in the type and IR, so they moved to slate-parser-v74.1.6.
windows.h and winsock2.h now parse in both flavors with only
-D__ptr32= -D__sptr= -D__uptr=.

Fixtures: ms-winnt-keywords-{clang-cl,msvc,off}.c. clang-cl, cl.exe and
Linux clang/gcc accept their respective files. Docs: ast-spec, ast-grammar,
ir-spec.
