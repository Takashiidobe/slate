# slate-dghn.56 translate-project --export-dynamic: -Wl,-E executables kept Py* API lifted to Rust fns, cpython extension modules failed undefined symbol PyList_New

_2026-11-14 10:51:09_

- bead: slate-dghn.56
- kind: bug
- area: crates/slate/src/main.rs
- area: crates/slate/tests/differential.rs
- area: tools/corpus/e2e.py

Outcome: translate-project --export-dynamic keeps every exported C definition as a C-ABI #[no_mangle] root, so the translated CPython loads its extension modules and passes 459/462 test files of `python -m test`.

Symptom: the translated `python` (tools/corpus/e2e.py cpython) started, but every extension module failed to import: `_sqlite3...so: undefined symbol: PyList_New`. CPython links `python` with `-Xlinker -export-dynamic` (LINKFORSHARED), and extension .so files resolve the Py* API against the executable.

Reproducer (fixtures.release/export_dynamic_dlsym): api.c defines `int api_sum(const int *, int)` and `int api_scale(int)`; main.c calls them directly, then looks both up with dlsym(RTLD_DEFAULT, ...) and calls them. Linked with -rdynamic, C prints both lines; the translated binary printed "missing export" and exited 1.

Cause: in executable projects translate_slate_project passes the main unit as liftable_root, so merge::translate_units builds Exports::Liftable. Non-root exports then become pointer_lattice candidates and lose their C symbol: api_sum became `pub fn api_sum(values: &[i32]) -> i32`, PyList_New became `pub fn PyList_New(size: i64)`. Nothing records that the final link exports the dynamic symbol table, because compile_commands.json holds only `-c` commands; -Wl,-E is a link-line property, not a per-unit IR fact, so it does not go through slate-parser.

Fix: `translate-project --export-dynamic` (crates/slate/src/main.rs) passes no liftable root, so the project uses Exports::Fixed and every exported definition keeps `#[unsafe(no_mangle)] extern "C-unwind"` with its C params. Rejected with --merge. The flag does not add a linker argument: the caller still links with -Wl,-E/-rdynamic (e2e.py already does via RUSTFLAGS). e2e.py passes the flag when a Make recipe's ldflags contain -rdynamic, -Wl,-E or -Wl,--export-dynamic (cpython, redis, nginx, lua). Dynamic exports of the cpython binary: 2660 -> 5231.

Harness: release_build_differential reads `// translate-args:` (passed to translate-project) and `// link-args:` (added to the C link and to the Rust build as -Clink-arg) from any unit; support::build_project_release_with_link_args.

CPython test stage: recipe test is `{binary} -m test -j0 --timeout=1200 -x test_gdb --ignore '*TestPerfProfilerWithDwarf*'`, run in build-clang with the translated binary copied there as python-slate (a symlink does not work: getpath follows it and misses the build-tree Lib). Unfiltered run: translated 459/462 files OK, 48,414 tests, 100.4s; native 462/462, 94.6s. Failures are debugging tooling only: test_gdb.test_misc and test_gdb.test_pretty_print (python-gdb.py wants C symbols/types such as builtin_id, v, PyObject; still fail with debug=true), and TestPerfProfilerWithDwarf (perf --call-graph=dwarf shows no py:: frames; the fp variant passes). README trophy case lists CPython at 459/462.

Limits: the filtered recipe run was not completed this session (killed for time). Lua's recipe also links with -Wl,-E for testes/libs; its translated binary predates Exports::Liftable, so its test stage was not rerun with the new flag.
Verification: slate profile 39/39 passed.
