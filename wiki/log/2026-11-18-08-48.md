# slate-3f8g.4.42 asm AsmNames: aarch64 :lo12:sym relocation operand kept raw C name, link failed

_2026-11-18 08:48:22_

- bead: slate-3f8g.4.42
- kind: bug
- area: crates/slate/src/frontend/lowerer/asm.rs
- target: aarch64

Outcome: asm template symbol rewriting now turns the name after an AArch64 `:lo12:` relocation specifier into a `sym` operand, so `global_asm!`/`asm!` using `adrp`+`:lo12:` link.

## Symptom

On aarch64, `adrp x9, helper_value` became `adrp x9, {0}` with `sym helper_value`,
but `[x9, :lo12:helper_value]` kept the raw C name. The link failed with
"undefined reference to helper_value" (or "dangerous relocation") because the
Rust static's symbol differs.

## Reproducer

```c
int helper_value = 7;
__asm__(".text\n.globl h\nh:\n\tadrp x9, helper_value\n"
        "\tstr w10, [x9, :lo12:helper_value]\n\tret\n");
int main(void) { return helper_value; }
```

`slate translate --target=aarch64-unknown-linux-gnu`.

## Cause

`AsmNames::text` (crates/slate/src/frontend/lowerer/asm.rs) set
`statement_start` on every `:` to handle labels (`h:`). After `:lo12:` the
next word was treated as a mnemonic and skipped as a symbol candidate.

## Fix

New `AsmNames::label` flag: true only right after the first word of a
statement. A `:` starts a statement only when `label` is set (the colon
directly follows that word). A word between two colons (`:lo12:`) is a
relocation specifier and never a candidate, even if a C object is named
`lo12`. Side effect: names after a segment prefix (`%fs:foo`, `ds:foo`) are
now candidates too, matching what the assembler resolves.

## Regression test

`crates/slate/tests/fixtures/aarch64/asm_aarch64_toplevel_lo12_symbol.c`:
static `helper_value`, static `lo12` (checks the specifier guard), and an
external `stored`, all addressed with `adrp` + `:lo12:` from a top-level asm.
The statics need `__attribute__((used))`, or clang drops them and the native
C build fails to link.
