# slate-f2zu.14.34.35 panic_c: freestanding panic handler loop {} after a noreturn C panic is an objtool unreachable instruction in rust_begin_unwind

_2026-11-16 21:12:53_

- bead: slate-f2zu.14.34.35
- kind: bug
- area: crates/slate/src/main.rs
- area: crates/slate/src/frontend/support
- area: crates/slate/src/backend/rust_ast.rs
- area: crates/slate/src/project/merge.rs
- flavor: clang

Outcome: when a freestanding project's C `panic` is noreturn (the kernel's), the generated `#[panic_handler]` declares it `-> !` and ends on the call, so objtool no longer reports an unreachable `jmp .` in `rust_begin_unwind`.

Symptom: objtool on the translated vmlinux.o, 27 times (one per shard crate root):

    _RNvCs9qCvQWINJaI_7___rustc17rust_begin_unwind+0x20: unreachable instruction

Codegen was `call panic; <nop pad>; 20: jmp 20`. objtool knows the kernel's
panic() never returns, so the `loop {}` after it is unreachable. Native has no
such code.

Cause: crates/slate/src/frontend/support/panic_c.rs declares
`fn panic(fmt: *const c_char, ...);` returning `()`, so the handler needs
`loop {}` to diverge. main.rs could not tell a noreturn `panic` from a
returning one: `rust_ast::ExternFnDecl` and `FnDef` carried no noreturn fact.
A never return type is not an option: noreturn is not part of the C function
type, so `-> !` breaks function pointers and the backend/link signature
comparison between decls and definitions (see slate-f2zu.14.34.34).

Fix:
- `ExternFnDecl.noreturn` and `FnDef.noreturn` (backend/rust_ast.rs), set from
  `FunctionSemantics::noreturn` in lowerer/functions.rs (extern decls, C
  definitions, naked functions, vector-ABI wrappers); generated helpers set
  false.
- main.rs `c_panic` returns `CPanic::{Returns, Noreturn}` from a `panic(ptr,
  ...)` decl or definition; the freestanding root picks
  frontend/support/panic_c_noreturn.rs (`-> !`, no loop) for Noreturn,
  panic_c.rs for Returns (a returning `panic`, as in
  fixtures.library/freestanding_crate_root, keeps the loop: `-> !` would be UB),
  panic_loop.rs otherwise.

- project/merge.rs `entries` clears `noreturn` in the merge comparison key.
  The flag never prints, and MSVC ignores `__attribute__((noreturn))`, so
  without this every noreturn function split into identical `#[cfg(unix)]` /
  `#[cfg(windows)]` copies (fixtures.merge/signature_compatible: 21 items 3
  gated -> 22 items 5 gated). Merged programs therefore lose the flag; only
  freestanding panic-handler selection reads it, and the kernel is not merged.

Verified on the kernel: hand-applied to the security shard, objtool on its
__slate_panic CGU went from 1 warning to 0; the rebuilt assoc_array unit's
__slate_panic CGU is clean.

Regression test: crates/slate/tests/differential.rs
`freestanding_panic_handler_ends_on_a_noreturn_c_panic`, fixtures
tests/fixtures.arch-mode/noreturn_panic_{definition,caller}.c, for a project
with only the noreturn definition and one with definition plus caller: the
root handler declares `-> !`, has no `loop {}`, and builds for
x86_64-unknown-none. Disassembly ends `rust_begin_unwind` on `call panic`.

See: slate-f2zu.14.34.36, slate-f2zu.14.40.13.
