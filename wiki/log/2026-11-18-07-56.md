Outcome: gcc-dg split-2 and pr85388-2 (-pthread -fsplit-stack) now live in the new tests/fixtures.gcc-dg.gcc-only.ignored/ bucket, and the slate-z3tq umbrella ("Rust binary dies without an exit status where C exits 0") is closed.

Of the ~30 gcc-dg/gcc-torture fixtures in the 2026-10-16 triage, all but these two had already moved to passing buckets or .ignored. Both recurse 1000 x 10000-byte frames (~10 MB) on a pthread. gcc's split-stack prologues (__morestack) grow the stack in segments, but rustc has no split stacks, so the translation overflows the 8 MB thread stack and dies by signal (C=Some(0) Rust=None). Translation succeeds.

Decision: -fsplit-stack raises a resource limit (stack depth, like ulimit -s). It does not change C semantics, so it stays a codegen-only flag that is parsed and ignored. Rejected alternatives:
- stacker::maybe_grow at every function entry: real growable stacks, but it adds a check to every call, no corpus project uses the flag, and it would not support libgcc's __splitstack_* API (split-5 uses __splitstack_makecontext).
- pthread_setattr_default_np with a huge stack under the flag: games split-2, but misses explicit attr stack sizes, makecontext stacks and the main thread.

Same precedent as split-5 (slate-2yro, wiki/log/2026-10-16-21-37.md), which lives in fixtures.gcc-dg.ignored/. These two get a gcc-only ignored bucket to match where they came from. Each has a SLATE: comment giving the reason. compiler-flags.md's codegen-only row now says this.

Limits: a translated program built with -fsplit-stack that needs deep recursion still crashes. Slate does not warn.
See: slate-2yro, slate-3amj.
