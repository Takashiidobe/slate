# accept alignment attributes on parameters with a named warning

_2026-09-21 08:57:38_

`module.rs::parameters` rejected any attribute in `specifiers.attributes` with
`Unsupported("parameter attributes")`, and silently dropped the trailing
`ParameterDeclarationKind.attributes` it never looked at.

Re-measured all three compilers (clang 22.1.8, gcc 16.2.1, MSVC 19.51):

| on a parameter | clang | gcc | MSVC |
| --- | --- | --- | --- |
| `_Alignas(N) int p` | error | error | accepts, `__alignof` = N raised to natural |
| `int p __attribute__((aligned(N)))` | accepts, `_Alignof` = N as written | error | `__attribute__` not parsed |

No construct is rejected by all three, so per the consensus rule neither may
be an error. The bead asked for the alignment to have *no effect*; that is
wrong. Every compiler that understands a spelling applies it — clang gives
`_Alignof(q)` 16 and a 16-aligned home slot, MSVC gives `__alignof(p)` 32.
So slate-parser applies it too, reusing 8lv.2's machinery: the request goes
on the parameter's entity and `object_alignment` reads it through
`declared_alignment`, which already encodes the MSVC-raises / clang-as-written
split. The IR has no parameter home slot, so `_Alignof` is the only
observable.

Added `Warning::ParameterAlignment` (`-Wparameter-alignment`, default on, not
pedantic), naming which compilers reject the spelling written. Non-alignment
attributes now go through `attributes::parameter_unsupported`: `Use::Ignored`
passes, everything else is refused rather than dropped.

Fixtures `ir_parameter_alignment.c`, `ir_parameter_alignment_msvc.c`,
`ir_parameter_attribute_diagnostics.c`. Gate green.
