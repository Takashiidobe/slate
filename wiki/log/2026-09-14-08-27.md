# Literals carry suffix/encoding, resolved against target ABI in sema

_2026-09-14 08:26:46_

lh7.3.7 (full spec rewrite, closes lh7.1.13/lh7.1.14 too): ExprKind's
Integer/WideInteger/Float/*StringLit/*CharLit variants are replaced with
IntegerLiteral{value: BigUint, radix, suffix, spelling},
FloatLiteral{spelling, radix, suffix, imaginary} (unevaluated -
resolve_float(&FloatLiteral) is the sema-callable evaluator, old evaluated
struct renamed ResolvedFloat), CharLiteral{encoding, code_units, spelling},
StringLiteral{encoding, code_units, pieces}. Escape decoding moved to
Lexer::decode_escapes (was decode_char_literal, folded per-char before);
Token::CharLit* now carries Vec<u32> code units instead of a folded i64.
Token::StringLit* is untouched (raw String) - too many non-literal
preprocessor consumers (#include, \_Pragma, stringize, asm templates) to
touch safely; decoding happens only where const_expr builds
ExprKind::StringLiteral.

New TargetInfo (src/target_info.rs, defaults to x86_64-linux-gnu LP64)
threaded onto TranslationUnit/Parser. Per user direction, target-aware
literal type resolution (C17 6.4.4.1p5 candidate search, char/wchar_t
range checks) lives in sema.rs, not the lexer or parser - the parser
keeps literals unevaluated, consistent with lh7.3.12's "no evaluation in
the parser" call. check_literals covers function bodies;
check_declaration_literals covers global initializers. Enum values,
bitfield widths, and static_assert conditions are not yet walked -
follow-up filed as lh7.3.13.

Also fixed tools/update_filecheck.py: decoding strings into numeric
code_units broke the existing {{.*}}-redaction trick for **FILE**-derived
content (a temp fixture path's bytes can't be regex-wildcarded, and its
length varies with pid digit count), so redact_code_units now loosens a
tainted code_units block into an unanchored close-bracket check instead of
matching it line-by-line.
