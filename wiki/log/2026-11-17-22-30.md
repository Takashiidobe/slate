# slate-3f8g.4.41 asm: aarch64 sp and i686 esp stack-pointer register variable operands (current_stack_pointer, ASM_CALL_CONSTRAINT) lowered, nostack cleared

_2026-11-17 22:30:28_

- bead: slate-3f8g.4.41
- kind: feature
- area: crates/slate-parser/src/sema/asm.rs
- area: crates/slate/src/frontend/lowerer/asm.rs
- area: crates/slate/src/frontend/lowerer/globals.rs
- target: aarch64
- target: i686

Outcome: a stack-pointer register variable used as an asm operand now lowers on aarch64 (`sp`) as well as x86_64 (`rsp`), and i686 (`esp`) has a runtime fixture. On aarch64 the asm loses `nostack`, so a `bl` inside it is sound.

## Gap and why it mattered

arm64 Linux defines `register unsigned long current_stack_pointer asm("sp")`. slate-f2zu.14.5 handled the x86 kernel `ASM_CALL_CONSTRAINT` only. On aarch64 every asm that used the variable hit `statement asm: explicit register sp`, and the global itself hit `register variable sp`.

The bead said `holds()` rejected `sp` for `r`. That was wrong: `holds()` already accepts `sp` through the x86 `legacy` name list, so the IR operand was already `Explicit(sp)`. The real gaps were the x86-only checks in the parser and in slate.

## Before

    register unsigned long current_stack_pointer __asm__("sp");
    __asm__("mov %w0, %w1" : "=r"(c) : "r"(current_stack_pointer));

This gave the barrier `explicit register sp`. The IR had `[options=pure,nomem,nostack,...]`.

## After

    core::arch::asm!("mov {0:w}, wsp", lateout(reg) __t0, options(pure, nomem, preserves_flags));

A plain C read of `current_stack_pointer` lowers to `mov {}, sp`.

## Implementation

- Parser `options()` (crates/slate-parser/src/sema/asm.rs): the rule that turns `nostack` off for an `Explicit(sp)` operand now covers AArch64 as well as x86.
- Slate (crates/slate/src/frontend/lowerer/asm.rs):
  - The operand loop's stack-pointer rule (no Rust operand; a referenced output stays a barrier) now covers AArch64.
  - `aarch64_register_modifier` treats `sp` as a general register.
  - The template printer writes `sp` or `wsp` (with `%w`) instead of prefix + `canonical[1..]`, which would have produced `xp`.
- `register_global` (globals.rs): AArch64 `sp` reads through `mov {}, sp`.

clang prints `sp` in the template. gcc copies sp into a GPR and writes it back for `+r`. Both produce the same value.

## Fixture

- crates/slate/tests/fixtures/aarch64/asm_stack_pointer_operand.c: a `bl` into a global_asm helper that pushes and pops x30, `%0`/`%w0` reads of sp, and a plain C read.
- crates/slate/tests/fixtures/i686/asm_stack_pointer_operand.c: the x86_64 fixture with `esp`. It passed without any code change.
- crates/slate-parser/tests/fixtures/{clang,gcc}/linux/aarch64/ir_asm_stack_pointer_operand.c: no `nostack` on the asm that has the sp operand.

Limits: a template that uses `sp` where only a GPR encoding is valid would fail to assemble (gcc would accept it because it uses a copy).
