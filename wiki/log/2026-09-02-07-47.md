# Recover range-for and array-iterator loops

_2026-09-02 07:47:34_

Two new rewrite rules, plus a real engine bug fix uncovered while building the
first one.

ForRangeRecover (src/backend/engine/rules/for_range.rs, new module):
recognizes the canonical desugared C for-loop shape --
`let mut i; i = start; loop { [let bound=N;] if !(i<bound){break} body; i=i+1; }`
-- and rewrites it to `for i in start..end { body }`. Requires: increment is
exactly `i = i + 1`; guard is `i < end` with end either inlined or a
single-use adjacent temp; body never reassigns i; i has no reads anywhere
outside the recognized region (checked via arena.def_use_neighbors, since
own_reads counts an assignment's target as a "read" too -- see the allowed-ids
set built from subtree_ids). Declines when the loop is labeled (NodeKind::For
has no label field to preserve one).

ForArrayIterRecover (src/backend/engine/rules/array_iter.rs, new module):
follow-on that fires on an already-recovered `for i in 0..N {...}` and, when
body's only use of i is as `arr[cast-chain(i)]` for a single Prim-element
array arr of length N, and arr appears nowhere else in body, rewrites to
`for i in arr.iter().copied() { ...i... }` (replacing the whole index
expression with the loop var). .copied() (not into_iter()) because arr is
typically `aligned::Aligned<_, [T;N]>`, not a bare array -- method-call
autoderef through Aligned's Deref only ever yields &[T;N], so into_iter()
would resolve to the same &T-yielding path as iter(), not owned elements.
Restricted to Prim element types so .copied() is always valid (Copy).

Engine bug found + fixed (src/backend/engine/mod.rs run_worklist): the
post-edit "requeue structural parent" step called `arena.parent(id)` *after*
`rule.apply()` ran. When a rule deletes the node it was dispatched on (e.g.
LateInlineTemps inlining a temp Let), `Arena::take` resets that node's stored
parent to None before returning -- so the parent-requeue silently became a
no-op for every deletion-based rule, not just this one. Fixed by capturing
`prior_parent = arena.parent(id)` before the candidate loop (alongside the
already-pre-captured def_use_targets/prior_reads) and requeuing that instead.
This is what let ForRangeRecover actually observe the fully-inlined
`i = i + 1` increment -- without the fix it only ever saw a still-unresolved
`i = _v12` temp reference, because the Loop node (low arena id, dispatched
before its higher-id children) was never revisited after LateInlineTemps
finished inlining those children.

Verified: array_init.c's @rewrite region now shows
`for i in a.iter().copied() { sum = sum + i; }`. Full rewrites (92/92),
lowering (10/10), and libc (34/34) nextest profiles pass; cargo fmt/clippy
clean.
