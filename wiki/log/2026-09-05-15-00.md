# Fix forward-declared enum dropping its Rust type definition

_2026-09-05 15:00:07_

extract_enum() in src/frontend/c_ast.rs built an Enum{variants: []} for a bare
forward declaration (`enum foo;`) the same as for a complete one, since it
never checked for empty variants. collect_enums() pushed both the forward
and the completing EnumDecl node into c.enums, in file order. The type-
emission loop in lower_module (src/frontend/lowerer.rs) dedupes by first-seen
name via a BTreeSet guard, so it processed the empty forward-decl entry
first, claimed the name, and skipped the real complete definition -- while
enum-constant references (via the separate collect_enum_const_ids/DeclRefExpr
path) still resolved to `EnumName::variant`. Result: valid-looking generated
Rust that failed to compile with E0433 "cannot find type `Foo`" whenever a
tag was forward-declared before its definition (a GNU extension, e.g.
`typedef enum foo E; enum foo { ... };` or `enum foo; enum foo { ... };`).

Fix: extract_enum returns None when variants is empty -- a real C enum can
never have zero enumerators, so an empty EnumDecl node is unambiguously a
forward declaration and should never produce an Enum entry. This lets the
completing declaration's entry be the only one that reaches lower_module.

Fixed gcc_torture_suite (930408-1) and c_testsuite_suite (case_00170)
completely under --profile lowering.
