# Shrink AbiPass to native_c except where rustc diverges

_2026-09-28 12:02:39_

Records and complex values now print `native_c` (trust rustc's `extern "C"`)
unless rustc would pass the `repr(C)` stand-in differently from the C
compiler; only those keep an explicit shape (slate-parser-xjv8).

How the divergence list was found: `rustc --emit=llvm-ir` on a `#![no_core]`
crate (works for every target without std) against `clang -emit-llvm` and gcc
asm, over ~70 record/complex shapes on 11 triples. The table is in
`wiki/concepts/ir-spec.md`. Surprises worth remembering:

- clang passes flexible-array-member records in memory on sysv64 and win64;
  gcc (since 4.4) and rustc use registers, so this is flavor-dependent.
- rustc ignores `[T; 0]` fields for HFA detection; C compilers do not, so a
  zero-length or flexible array in a float record diverges on AArch64/armhf.
- rustc never uses VFP HFA passing on thumbv7a-pc-windows-msvc (its triple
  lacks `hf`), while clang does.
- rustc passes HFAs to variadic calls on win-arm64 in FP registers; clang uses
  GPRs (and byref above 16 bytes, which slate previously got wrong).
- i686 `_Complex char/short/int` results come back in registers (gcc agrees);
  slate previously gave them `sret`.
- slate's sysv64 `_Complex __float128` (memory) and `_Complex _Float16`
  (`pair<f16>`) shapes were wrong and are fixed.

The divergence check runs one classifier twice (over the C types and over the
Rust stand-ins) and compares. For sysv64 that classifier is now a proper
eightbyte classifier; `AbiChunk::FloatQuad` (`quad<f16>`) was added for
clang's `<4 x half>`. `win32_returns_in_register` no longer fails on
flexible array members and treats `_BitInt` fields as disqualifying.

Fixtures: `abi_rust_divergence.c` in 9 target dirs; 338 fixtures regenerated.
