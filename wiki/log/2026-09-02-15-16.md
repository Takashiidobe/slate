# split CType::Char out of CType::Int

_2026-09-02 15:16:56_

CType::Int carried a dead is_char flag added in 6531e13f (never read
anywhere). Replaced it with a proper CType::Char { signed: bool } variant,
sibling to Int rather than a field on it.

Only non-mechanical spot: adopt_cir_int_signedness in
lowerer/record_analysis.rs (the aarch64 plain-char-signedness fix from
2026-08-31) matched CType::Int{..} and relied on is_char being ignored via
`..` to reconcile plain char the same as signed/unsigned char against
CIR-derived signedness. Splitting Char out would have silently dropped that
reconciliation for record fields, so added a matching (Char, Int{bits:8})
arm.

Every other exhaustive CType match (ctype_abi_sig, c_type_to_type, c_layout,
normalize_record_shape) got a Char arm mirroring the prior bits:8 behavior
(i8/u8, size 1/align 1). No behavior change elsewhere - CIR-derived
conversion (cir_type_to_ctype) still never produces Char, only
parse_c_type's bare "char" string case does.

Verified: cargo check/clippy clean, `lowering` profile 10/10 including
struct_char_ptr_field_signedness (the aarch64 fixture this touches).
