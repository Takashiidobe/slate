# slate-parser-dyd.59 parser FP pragma: STDC/float_control pragma as an if/loop body was hoisted to compound start and accepted

_2026-11-18 18:00:13_

- bead: slate-parser-dyd.59
- kind: parser
- area: crates/slate-parser/src/parser/stmt.rs
- flavor: clang

Outcome: a floating-point pragma used as an if/loop body (`if (c) #pragma STDC FENV_ACCESS ON`) is now rejected like clang does, instead of being hoisted and applied to the rest of the block.

## Diagnostic or IR fact that was wrong
`parse_stmts_from_tokens` (crates/slate-parser/src/parser/stmt.rs) emitted every pragma found inside a statement's tokens before that statement. For `if (c)` followed by the pragma, the pragma landed at the start of the enclosing compound, so sema saw `PragmaPlacement::CompoundStart` and applied it to the whole block.

## Before and After
```c
double misplaced(double a, double b, int c) {
  if (c)
#pragma STDC FENV_ACCESS ON
  a = 1;
  return a / b;
}
```
Before: accepted. After (--flavor=clang): `floating-point pragma can only appear at file scope or at the start of a` compound statement, at the pragma.

## Fix
Pragmas inside a statement that are `PragmaKind::Stdc` or `PragmaKind::FloatControl` are emitted after the statement instead of before. Sema then sees them past `compound_start` and reports `PragmaPlacement::Misplaced` (the existing diagnostic, as for `fp_pragma_misplaced_after_statement_expression.c`). Other pragmas (pack, omp, ...) are still hoisted before the statement. gcc flavor ignores these pragmas in `FloatingPragmas::apply`, so it is unchanged.

Limits: msvc flavor now also rejects the same placement, as it already rejects other misplaced FP pragmas through the same sema path; not checked against cl.exe.
