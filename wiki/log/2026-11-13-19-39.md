# slate-dghn.58.3 asm_template: x86 memory operand with %w/%b/%h/%k/%q size modifier (fstcw %w0) was a barrier

_2026-11-13 19:39:26_

- bead: slate-dghn.58.3
- kind: bug
- area: crates/slate/src/frontend/lowerer/asm.rs
- target: x86_64

Outcome: x86 inline asm memory operands accept the size modifiers b/h/w/k/q and print the plain address, as clang and gcc do; NumPy's `fstcw %w0` translates.

Symptom: NumPy multiarraymodule.c `__asm__("fstcw %w0" : "=m"(cw))` stopped at `statement asm: memory modifier Some('w')`.

Reproducer:
```c
unsigned short cw;
__asm__("fstcw %w0" : "=m"(cw));
```

Cause: asm_template (crates/slate/src/frontend/lowerer/asm.rs) accepted only no modifier or x86 'H' (+8 displacement) on Memory operands. LLVM's X86AsmPrinter::PrintAsmMemoryOperand ignores b/h/w/k/q on memory, in both AT&T and Intel syntax (clang -S prints `(%rdi)` / `[rdi]` for all five).

Fix: `Some('b' | 'h' | 'w' | 'k' | 'q') if x86 => None` in the memory-modifier match.

Target survey (clang 23):
- x86/x86_64: %w on a register is the 16-bit name; on memory it is ignored.
- aarch64: %w on a register is the 32-bit w name; on memory clang errors (invalid operand), so slate keeps the barrier.
- arm32: %w is not a GPR modifier (clang errors for registers and memory); barrier kept.

Regression test: crates/slate/tests/fixtures/x86_64/asm_memory_size_modifiers.c (fstcw/fldcw round trip, notb/notl/negq/incw through %b/%k/%q/%h on +m operands).

Limits: NumPy translate still stops at long double to PyOS_snprintf (slate-dghn.58.2) and SVML vector-ABI externs (slate-dghn.58.5).

See: slate-dghn.58, slate-dghn.58.1
