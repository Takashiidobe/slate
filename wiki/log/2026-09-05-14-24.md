# extend imaginary_promotion_consts to +, both operand orders

_2026-09-05 14:24:40_

Follow-up to slate-7jv4.13 (see 2026-09-05-14-15.md). Asked why the
collector in c_ast.rs only matched `FloatingLiteral - ImaginaryLiteral`.

Verified against fresh CIR dumps for all four combos: real+imag, imag+real,
real-imag, imag-real. Corrected an assumption drawn from memory of classic
LLVM CGComplexExpr.cpp (expected the unnegated component to keep its own
literal's location, since that source reuses it as-is). CIRGen actually
re-materializes BOTH components of the imaginary operand's pair (synthesized
real=0, and the imaginary value) as fresh `cir.const`s at the
BinaryOperator's own location regardless of add/sub or operand order. So
every combo needs two synthesized facts: [zero, value] -- only
`real - imaginary` (opcode "-", real on the LHS) negates the second one.

Fixed `collect_imaginary_promotion_consts_at` to always push both facts,
negating conditionally, matching both operand orders for `+`/`-`. Confirmed
via `emit-cir` on scratch fixtures for all four combos; no regression on
the promoted `complex__pr47473` fixture under `lowering`/`rewrites`.

`*`/`/` excluded: this fixture's own `(0.0F + 1.0iF) * 0.9L` shows CIRGen
never folds complex multiply/divide this way -- both components always
come from real `cir.fmul` on resolvable SSA operands, so there's no known
instance of this failure mode for those operators.
