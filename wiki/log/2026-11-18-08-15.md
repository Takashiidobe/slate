# slate-3amj.10 gcc -fexec-charset/-fwide-exec-charset: EBCDIC and byte-swapped wide literals encoded like gcc

Outcome: gcc flavor accepts -fexec-charset= (40 single-byte iconv charsets incl. EBCDIC IBM037/IBM1047) and -fwide-exec-charset= (UTF-32/UCS-4/UTF-16 LE/BE), encoding literals and #if character constants as gcc does; clang accepts -fexec-charset=utf-8 only.

Gap and why it mattered: slate-parser warned "unsupported compiler flag -fexec-charset=IBM1047 ignored", so literals kept UTF-8 bytes and the translation printed different bytes than gcc. Fixtures crates/slate/tests/fixtures.unsupported/gcc/flag_{,wide_}exec_charset.c failed.

Before (-fexec-charset=IBM1047, `const char text[] = "Az09 !";`): text = [65, 122, 48, 57, 32, 33, 0].
After: text = [-63, -87, -16, -7, 64, 90, 0] (c1 a9 f0 f9 40 5a), '\n' = 0x25, 'ab' = 0x8182.
-fwide-exec-charset=UTF-32BE on x86_64: L"Azé" = 41000000 7a000000 e9000000 00000000.

gcc facts probed (gcc 16.2.1), all now matched:
- Unknown names fail ("conversion from UTF-8 to X not supported by iconv"), even with -E. Slate rejects them as invalid arguments.
- \x and octal escapes are raw code units, not converted or swapped; simple escapes (\n) and UCNs are converted.
- #if 'A' == -63 under IBM1047: the preprocessor uses the execution charset and signed char.
- __GNUC_{,WIDE_}EXECUTION_CHARSET_NAME is the name as written, and the macro's own string is then encoded (EBCDIC).
- A wide charset narrower than wchar_t (UTF-16 on 32-bit wchar_t) gives junk in gcc; slate rejects it. Bare UTF-32 emits BOMs per piece in gcc; slate rejects it. Bare UCS-4 is big-endian.
- An unencodable character is an error: "converting to execution character set: Invalid or incomplete multibyte or wide character" (gcc says "converting UCN to ..." for a UCN; slate uses the one text for both).

Implementation:
- `Charset::Table(&ByteTable)` with a full 256-entry `[Option<char>; 256]` table (EBCDIC remaps ASCII, so the MSVC `CodePage` high-half table did not fit); `Charset::parse_gnu`.
- src/gnu_charsets.rs is generated by crates/slate-parser/tools/generate_gnu_charsets.py from glibc iconv (ctypes), checking decode/encode consistency and that gcc -fexec-charset=<each alias> produces the same bytes. CP1255/CP1258 left out: glibc treats them as stateful (combining sequences).
- `WideCharset { width, endian }`, `CompilerOptions::gnu_charsets`, `TargetInfo::wide_execution_swapped` set in `Dialect::new` for gcc; `const_expr::execution_units` swaps Character units of wide literals.
- Macros in pp/mod.rs next to the wchar predefines; gcc-flavor error in sema/validate.rs `push_literal_diagnostics` (msvc keeps its `?` + warning).

Fixtures: crates/slate/tests/fixtures/gcc/flag_{,wide_}exec_charset.c (promoted); parser crates/slate-parser/tests/fixtures/gcc/linux/x86_64/exec_charset.c, error/gcc/linux/x86_64/{exec_charset_unknown,wide_exec_charset_width,exec_charset_unrepresentable}.c, error/clang/linux/x86_64/exec_charset_not_utf8.c.

Limits: -finput-charset= still UTF-8 only. Multibyte/stateful execution charsets (Shift-JIS, CP1255/1258, UTF-16 narrow) are rejected.
See: slate-3amj, wiki/concepts/compiler-flags.md.
