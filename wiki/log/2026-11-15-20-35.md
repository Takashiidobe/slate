# slate-f2zu.14.34.29 e2e.py shard_units: arch/x86/boot and realmode/rm in one unlinked_m16 crate, static adapter defined twice

_2026-11-15 20:35:20_

- bead: slate-f2zu.14.34.29
- kind: bug
- area: tools/corpus/e2e.py

Outcome: e2e.py shards kernel units outside vmlinux.a one shard per source directory (one kbuild image each), so arch/x86/boot and arch/x86/realmode/rm no longer share a crate and the duplicate static `adapter` is gone.

Symptom: unlinked_m16 shard build: "symbol `adapter` is already defined" (rm_video_mode.rs vs boot_video_mode.rs).

Reproducer: arch/x86/realmode/rm/video-mode.c `#include`s ../../boot/video-mode.c, so both units define the global `adapter`. They link into different images (setup.elf vs realmode.elf).

Cause: shard_units ran split((), unlinked) over all 67 non-vmlinux units. That is under the 120-unit limit, so they formed one `unlinked` group, and only the codegen-key split separated images. boot and realmode/rm share -m16 flags, so they stayed together in unlinked_m16.

Fix: unlinked units are grouped by their project-relative parent directory before the codegen split. Shards are now named unlinked_<dir>[_<mode>][_cgN], e.g. unlinked_arch_x86_boot_m16, unlinked_arch_x86_realmode_rm_m16, unlinked_drivers_firmware_efi_libstub. 80 -> 83 shards. kernel_link.swap still skips them (no vmlinux.a members). sharded_stages deletes the old unlinked* shard dirs as stale.

Regression test: none (harness). Verified by computing the shard listing from target/corpus/linux/clang/compile_commands.json, then translating and cargo-building both m16 shards: realmode_rm builds clean, and boot no longer reports the duplicate symbol.

Limits: unlinked_arch_x86_boot_m16 now gets through rustc and fails in LLVM MC with 94 "value of N is too large for field of 2 bytes" (16-bit rel16 jumps over 32K; the C is -Os, the crate is opt-level 3). Filed as slate-f2zu.14.34.32.

See: slate-f2zu.14.34.24 (introduced the unlinked split), slate-f2zu.14.34.32.
