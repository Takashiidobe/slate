# slate-f2zu.14.34.10 SymbolOwners: weak default plus strong override in one shard crate (symbol already defined); weak fns get linkage weak; kernel modules get own shards

_2026-11-15 10:23:37_

- bead: slate-f2zu.14.34.10
- kind: bug
- area: crates/slate/src/project/merge.rs
- area: crates/slate/src/frontend/lowerer.rs
- area: tools/corpus/e2e.py
- corpus: linux

Outcome: translate-project keeps one definition per external symbol when several units of one crate define it (strong over weak, first weak otherwise), weak function definitions carry `#[linkage = "weak"]`, and e2e.py puts each kernel module (.mod.c plus its .mod objects) in its own `mod_*` shard.

Symptom: 5 linux shards failed `cargo build` with `symbol X is already defined`: `__ia32_compat_sys_kexec_load` (kernel/sys_ni.c COND_SYSCALL weak stub vs kexec.c), `cpufreq_fallback_governor` (cpufreq.c weak vs cpufreq_performance.c), `init_uts_ns` (init/version.c weak vs version-timestamp.c), `enable_debug_cgroup` (cgroup.c weak vs debug.c), and `__this_module` (one per module .mod.c, all in `_packed`).

Reproducer (two units, one crate):
```c
// a.c
__attribute__((weak)) long f(void) { return 0; }
long use_f(void) { return f(); }
// b.c
long f(void) { return 7; }
```
Before: both a.rs and b.rs emit `#[unsafe(no_mangle)] extern "C-unwind" fn f()`; a.rs has no `#[linkage = "weak"]` either.
After: a.rs declares `unsafe extern "C" { fn f() -> i64; }`, b.rs keeps the body.

Cause:
- rustc rejects two items with one symbol in a crate regardless of linkage, so the linker's weak/strong resolution never gets a chance.
- `lower_module`'s function export path never added `Attr::WeakLinkage` (globals got it in slate-f2zu.14.7), so a weak function definition was strong.
- `__this_module`: module objects are never linked into vmlinux, but sharding grouped them with vmlinux units.

Fix:
- `ComdatOwners` renamed `SymbolOwners` (`symbol_owners`, project/merge.rs). `external_definitions` classifies every external function body and non-common global definition as `Definition::{Strong, Weak, Comdat}`. With two or more definers and at most one strong one, the owner is the first `preferred` (strong or non-discardable comdat) definer, else the first. All-discardable comdats still get `__slate_odr_` names. Two strong definitions are left alone (a real C link error).
- `without_definitions` (was `without_bodies`) drops the body or the global definition and initializer in non-owner units and clears `symbol.weak`, so the reference is a plain extern resolved by the existing cross-unit import path.
- frontend/lowerer.rs: exported weak function definitions (and runtime-symbol wrappers) get `#[linkage = "weak"]`; `Item::Fn` with it requests `#![feature(linkage)]`. Needed for the vmlinux relink (slate-f2zu.14.34.6), where the strong override is in another shard or a C object.
- tools/corpus/e2e.py `kernel_modules`: each `*.mod.c` unit plus the units its `<module>.mod` lists form shard `mod_<path>`; 12 modules; the linux run now has 83 shards (was 75), translate 83/83.

Regression test: crates/slate/tests/fixtures.release/weak_strong_override/ (weak+strong function and global, weak+weak in two units, unreferenced weak).

Limits: units are ordered by the compile database, which may not be the C link order, so a weak+weak pair can pick a different body than ld would. Symbols are keyed by C name, not asm label.

See: slate-f2zu.14.34.6, slate-j3by.1 (comdat owners), slate-f2zu.14.7 (weak globals).
