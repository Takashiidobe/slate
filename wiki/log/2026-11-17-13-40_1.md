# slate-3amj.59 crate_sanitizer: hosted crates whose units agree on -fsanitize=address|thread build with -Zsanitizer; MachineCodegen carries sanitize

_2026-11-17 13:40:29_

- bead: slate-3amj.59
- kind: feature
- area: crates/slate-parser/src/sanitizers.rs
- area: crates/slate-parser/src/ir/module.rs
- area: crates/slate/src/main.rs
- area: crates/slate/src/backend/rust_ast.rs

Outcome: a translate-project crate whose hosted units all set -fsanitize=address (or thread) builds with -Zsanitizer=address|thread, so the translated binary reports the heap overflow or data race the native -fsanitize build reports.

Gap and why it mattered: slate-3amj.58 only emulated predefines; the generated crate was uninstrumented, so out-of-bounds and races inside translated code went undetected where the native build trapped.

Reproducer (crates/slate/tests/fixtures.release/sanitize_address_heap_overflow.c, dg-options -fsanitize=address): a noinline store one past a 16-byte malloc reached through a volatile global (clang -O2 elides a local malloc/free pair, so the global keeps the allocation alive).

Before: C exits 1 with "AddressSanitizer: heap-buffer-overflow"; Rust wrote out of bounds and exited 65.
After: the generated Cargo.toml has

```toml
[profile.release.package.sanitize_address_heap_overflow]
rustflags = ["-Zsanitizer=address", "-Cunsafe-allow-abi-mismatch=sanitizer"]
```

and the Rust binary exits 1 with the same report. sanitize_thread_race.c: both exit 66 with a ThreadSanitizer data race report.

Implementation:
- slate-parser: `sanitizers::Instrumentation` (Address, KernelAddress, Thread; the conflict tables make them exclusive), `Sanitizers::instrumentation`, `ir::MachineCodegen::sanitize`, printed `machine [sanitize=...]` (ir-grammar, ir/calls-abi updated).
- slate: `rust_ast::Program.sanitize`; `crate_sanitizer` (main.rs) returns the name when every unit agrees and every unit has std; disagreement, freestanding/-nostdinc units, and kernel-address warn and return none.
- `crate_manifest`/`write_crate_manifest` now take `codegen_rustflags: &[String]` instead of the stack protector level; the caller builds -Zstack-protector and -Zsanitizer flags.

Settled questions from the bead:
- Runtime: rustc links its own compiler-rt runtime into executables. A rustc -Zsanitizer=address staticlib linked by `clang -fsanitize=address` traps correctly (rustc and clang are both LLVM 23 here).
- -Zbuild-std: not needed to detect bugs in translated code. -Zsanitizer=thread rejects uninstrumented std/core without -Cunsafe-allow-abi-mismatch=sanitizer, so it is always passed.
- -fsanitize=undefined: not mirrored; Rust has no equivalent (wiki/concepts/compiler-flags.md#sanitizers).

Fixtures: crates/slate/tests/fixtures.release/sanitize_address_heap_overflow.c, sanitize_thread_race.c; parser clang and gcc linux/x86_64/sanitize_macros.c now show the machine fact.

Limits: kernel-address is not carried over (the kernel provides the KASAN runtime). memory, leak, hwaddress are not mapped. --merge crates rebuild with defaults (as slate-yar4.51 for the stack protector). std and the support crates stay uninstrumented, so accesses inside them are not checked (libc calls are still intercepted by the runtime).

See: slate-yar4.48 (same mechanism for -Zstack-protector), slate-3amj.58, slate-3amj.60.
