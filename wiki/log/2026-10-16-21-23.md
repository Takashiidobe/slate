# Recover for ranges when sibling loops reuse the counter name

_2026-10-16 21:23:48_

slate-5vj0.5.10: the arena keys def/use and definitions by name, so with several 'for (int i = 0; ...)' loops in one function (memcpy.c, memmove.c), def_use_neighbors(i) spanned every loop and arena.definition(i) named only one let (or, after the first conversion, a For node). for_range's all-uses-in-the-loop check and invariant_within both failed for every loop but one.

- rules/for_range.rs: the counter's let is looked up among the while's earlier siblings first (falling back to arena.definition). When found locally, def/use neighbors outside that let's scope (the let and its later siblings, with subtrees) are ignored, since they can only belong to another binding. Body invariance uses the local let's type.
- rules/remove_mut.rs: invariant_within delegates to a new binding_invariant_within(arena, name, ty, region) that takes the binding's type explicitly.
- Baselines regenerated: memcpy.c, memmove.c, mem_safe_slice_idioms.c (every counted loop is now a for range).

The general name-keyed defs problem is filed as slate-5vj0.5.13 (e.g. remove_mut keeps 'mut' on an outer binding shadowed by an inner one). Leftover '{ for ... }' singleton scopes are slate-5vj0.5.14.
