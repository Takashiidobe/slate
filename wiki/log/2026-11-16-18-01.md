# slate-f2zu.14.40.15 cleanup Guard: per-unit Drop::drop and drop glue landed in incremental fallback CGU, moved to ::slate_support::Guard

_2026-11-16 18:01:27_

- bead: slate-f2zu.14.40.15
- kind: bug
- area: crates/slate/src/frontend/lowerer
- area: crates/slate/vendor/slate-support
- area: crates/slate/src/backend/engine/rules/dead_store.rs
- target: x86_64

Outcome: cleanup guards lower to a single non-generic `::slate_support::Guard`,
so no unit-named Drop impl or drop glue lands in the incremental fallback CGU
and kernel_link check_groups accepts the linux lib shard.

Symptom: `e2e.py linux --from build` (after slate-f2zu.14.40.13) stopped in
kernel_link:

    lib: slate_crate-...-fallback.cgu.0zkirml.rcgu.o (crate root) defines items of
    ['__slate_unit_bug', '__slate_unit_dynamic_queue_limits', '__slate_unit_maple_tree',
     '__slate_unit_sbitmap', '__slate_unit_sys_info']

The fallback CGU held, per unit,
`drop_glue::<__slate_unit_X::__slate_cleanup::Guard>` and
`<__slate_unit_X::__slate_cleanup::Guard as Drop>::drop`.

Reproducer: any C unit with `__attribute__((cleanup(f)))` in a link-order crate
built with CARGO_INCREMENTAL=1 and per-unit CGUs.

Cause: under incremental, rustc's partitioner deliberately places every
`Drop::drop` impl with `drop_in_place`, and drop glue has no characteristic def
id, so both go to the fallback CGU wherever the type is defined.
slate-f2zu.14.40.14 moved the handler closures into their unit by switching to
`Guard(&mut dyn FnMut())`, but `support/cleanup.rs` still emitted a per-unit
`mod __slate_cleanup { struct Guard; impl Drop }`, so each unit's Guard symbols
carried the unit name into root.

Fix: `Guard<'a>(pub &'a mut dyn FnMut())` and its Drop impl live in
`vendor/slate-support/src/lib.rs`. The lowerer (`cleanup_guard` in
lowerer/statements.rs and the armed guard in lowerer/control_flow.rs) emits
`::slate_support::Guard(&mut || ...)`; the `__slate_cleanup` support module,
`support/cleanup.rs` and `Dependencies.cleanup` are gone, and
`dead_store::is_drop_guard` matches the new path. slate-support is a dependency
of every generated crate (CLI and test harness), so no fallback path is needed.

Why not `Guard<F: FnMut()>`: each closure type would monomorphize its own
`Drop::drop`, named after the unit, and the partitioner would put all of them
back in the fallback CGU. The lifetime-only Guard has one `Drop::drop` (in
slate-support's object, merged across shards by kernel_link.runtime_object) and
one drop glue per crate, whose name has no unit in it.

Name conflicts: the leading `::` resolves through the extern prelude, so a C
`struct Guard` or a C global named `slate_support` in the unit cannot shadow it.

Regression test: crates/slate/tests/fixtures/cleanup_guard_name_shadowing.c (C
`Guard` type and `slate_support` global next to two cleanup guards); 6 cleanup
fixtures regenerated.

Kernel relink: `e2e.py linux --from build --jobs 2` passes check_groups for lib;
build ok (84 shards, 0 errors), link ok (vmlinux linked, 57 shards swapped, 0
errors, 60 objtool warnings: 58 redundant UACCESS disable, 1 unsupported
instruction in callable function, 1 call with UACCESS enabled). Not booted.

Limits: the relink ran on shards translated by the old binary and hand-patched
to `mod __slate_cleanup { pub use ::slate_support::Guard; }`, not on fresh
`--from translate` output. The full slate profile was not run; the 7 cleanup
fixtures pass on x86_64.

See: slate-f2zu.14.40.14, slate-f2zu.14.40.13
