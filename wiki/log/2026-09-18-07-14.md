# Character constants in #if follow the target's char signedness

_2026-09-18 07:14:24_

`#if '\xff' < 0` took the false branch where clang and gcc take the true one,
because the preprocessor's expression evaluator folded a character constant to
its raw code unit with no target in hand. The libc-shim's `limits.h` selects
CHAR_MIN/CHAR_MAX with exactly that idiom, so slate-parser was defining
CHAR_MIN 0 / CHAR_MAX 255 on a signed-char target.

`const_expr::Parser`'s evaluator now threads an `EvalContext` (the `is_defined`
callback plus an optional `&TargetInfo`) instead of the bare callback, and
`Preprocessor` keeps the target it is configured with so `#if` evaluation can
pass it. The two target-less callers -- the `__BIGGEST_ALIGNMENT__` probe and
`_BitInt` width folding -- keep the old code-unit fold; neither can see a
character constant in practice.

The value itself moved to `CharLiteral::value`, so the preprocessor and
`sema::types::character_constant` now share one definition instead of two that
disagreed. Its errors are `ConstExprError`, which `ResolveError` already
absorbs, so sema no longer carries its own wording for them.

Signedness matters as much as the value: clang evaluates `u8`/`u16`/`u32`
constants as unsigned in `#if`, wide constants per wchar_t, and plain constants
per char -- `'\0' - 1 > 0` is true on aarch64-linux (unsigned char) and false on
x86_64. `evaluate_wide` gained a `CharLiteral` arm carrying
`char_type_is_signed` into `WideInt`, and all five spellings now agree with
clang -E on both targets.

Note `char_type_is_signed` is the signedness of the character type, not of the
constant's C type: a plain constant is `int`, but preprocessor arithmetic
follows `char`. sema keeps typing plain constants `int` explicitly.

Fixtures: `sema/preprocessor_character_constants.c` and
`sema/preprocessor_character_constants_unsigned_char.c` (aarch64).
