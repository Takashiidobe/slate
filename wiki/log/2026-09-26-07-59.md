# FileCheck fixtures run as one nextest test per configuration

_2026-09-26 07:59:05_

tests/filecheck.rs is now a harness=false libtest-mimic binary: one trial per fixture x prefix, named <path relative to tests/fixtures>::<PREFIX> (e.g. sema/ir_add.c::IR).

Why: the old single #[test] split jobs over 6 threads, each panicking on its first failure, and resume_unwind rethrew one - a run reported at most ~6 failing fixtures, so wide changes needed a regenerate-and-rerun loop. Now 'cargo nextest run --release --no-fail-fast' lists every failing fixture, and '-E test(/name/)' filters.

Gotcha: nextest spawns one process per test, and each process runs main(). Building the trial list scans every fixture, so doing that per process was O(n^2) (~2 min). When invoked with --exact <name> (what nextest does per test), main builds jobs only for that fixture. Full suite: ~5-6s, down from ~10s.

Fixture collection skips dot-files: a killed run leaves .<stem>.filecheck.XXXX.c scratch copies beside the fixture.
