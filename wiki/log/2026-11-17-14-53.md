# slate-yar4.53 NeonOp: AArch64 dotprod/rdm/crypto/sha3/vcmla/frint32 builtins, __crc32*, float16x8_t vectors and scalar __builtin_bit_cast int<->float

_2026-11-17 14:53:29_

- bead: slate-yar4.53
- kind: feature
- area: crates/slate-parser/src/sema/neon_builtins.rs
- area: crates/slate/src/frontend/lowerer
- target: aarch64

Outcome: the AArch64 feature-gated NEON/ACLE builtins (dotprod, rdm, aes/sha1/sha256/sha512/sha3/sm4, vcmla, frint32/64, __crc32*) and float16x8_t/float16x4_t vectors now translate, run and match clang. Scalar int<->float `__builtin_bit_cast` is a bit reinterpretation instead of a value conversion.

Gap and why it mattered: with slate-3amj.55 the unit features reached `#[target_feature]`, but the arm_neon.h/arm_acle.h calls still stopped at "builtin without a lowering". f16 vectors were rejected ("return type vector<f16, 8>"), which blocked NumPy's ASIMDHP paths.

Before (`-march=armv8.5-a+crypto+dotprod`):

```
help: function __builtin_neon_vdotq_u32: builtin without a lowering
help: function __builtin_arm_crc32b: builtin without a lowering
cannot lower a function returning `float16x8_t`
```

After: `vdotq_s32` calls `llvm.aarch64.neon.sdot.v4i32.v16i8`, `vaeseq_u8` calls `llvm.aarch64.crypto.aese`, `__crc32d` calls `llvm.aarch64.crc32x`. `vaddq_f16` is `Simd<f16, 8> + Simd<f16, 8>`.

Implementation:
- sema/neon_builtins.rs:
  - `NeonOp::Direct(signed, unsigned)` covers fixed-name builtins whose operands all share the type-code vector: vqrdmlah/vqrdmlsh, vaes*, vsha1su0/su1, vsha256*, vsha512*, veor3q/vbcaxq (s/u forms), vrax1q, vsm4e/vsm4ekey, vcmla rot0..270 (f16/f32/f64), vrnd32x/z and vrnd64x/z.
  - `NeonOp::Dot`, with `NeonShape::Quarter`: the accumulator keeps the code type and the operands are i8 with 4x the lanes. sdot or udot is chosen by signedness.
  - `NeonOp::Crc` handles the `__builtin_arm_crc32{b,h,w,d,cb,ch,cw,cd}` records (d/cd become crc32x/cx with an i64 data operand).
  - Type code 8 decodes as f16; `*_f16` lanewise builtins (abs, max, min, maxnm, minnm, fma, sqrt, rnd*) reuse their `_v` ops.
  - `NeonOp::FloatResize` handles vcvt_f32_f16/vcvt_f16_f32 (here the code describes the operand).
  - `NeonOp::LaneWrite` lowers vset_lane/vsetq_lane as a splat plus shuffle. This was missing for every element type.
- crates/slate:
  - `simd_type` and `slate_vector_type` accept f16 lanes.
  - The intrinsic catalog maps half/f16, mangles v8f16 and treats f16 as a float overload.
  - values.rs: a scalar `ConversionKind::BitCast` between an integer and f16/f32/f64 is lowered as transmute. Before, it fell through to `as`, so `__builtin_bit_cast(float, 0x3f800000u)` gave 1.06535e+09. The arm_neon.h `vget_lane_f16` macro goes through this path.

Fixtures:
- crates/slate/tests/fixtures/aarch64/neon_feature_gated_builtins.c
- crates/slate/tests/fixtures/aarch64/neon_f16_vectors.c (NaN lanes, ±0, subnormal, 65504, f32->f16 overflow and rounding)
- crates/slate/tests/fixtures/builtin_bit_cast_scalar.c (all targets)

Limits:
- Lane forms (`vdotq_lane_s32`, `vcmlaq_lane_f32`), scalar vqrdmlahh/vqrdmlahs, vsha1c/m/p/h (scalar hash_e operand), vxarq_u64, sm3 and f16 across-vector reductions (vmaxvq_f16) still have no lowering.
- `__builtin_arm_crc32*` always maps to the llvm.aarch64 names, so on Arm32 it produces an intrinsic rustc rejects instead of a barrier.
