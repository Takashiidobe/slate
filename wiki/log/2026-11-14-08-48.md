# slate-5q63.14 foldhash: std SipHash HashMap/HashSet replaced with foldhash in slate and slate-parser (cpython translate 17.7s -> 16.8s)

_2026-11-14 08:48:34_

- bead: slate-5q63.14
- kind: feature
- area: crates/slate/src
- area: crates/slate-parser/src

Outcome: slate and slate-parser use foldhash::{HashMap, HashSet} instead of std's SipHash-backed maps; cpython translate-project drops from ~17.7s to ~16.8s wall with byte-identical output.

Gap: after slate-5q63.13, the ceval.c profile still showed SipHash (hash_one::<&Ident>, Sip13Rounds::write) among the top symbols.

Before (SLATE_NO_FORMAT=1 translate-project on cpython, 3 runs): 17.92s, 17.65s, 17.61s.
After: 16.81s, 16.75s, 16.75s. CPU 72.6s. Per-TU parallel wall 12.2s; ceval.c alone 7.0s (unformatted).
Output: identical to the SipHash build except the __TIME__ string in getbuildinfo.rs.

Implementation:
- crates/slate/Cargo.toml gains foldhash.workspace (slate-parser already had it for pp macros).
- Every `use std::collections::{HashMap, HashSet}` in crates/slate/src and crates/slate-parser/src now imports foldhash::{HashMap, HashSet}, plus HashMapExt/HashSetExt where ::new()/with_capacity() are called. ir/names.rs and parser/declarator.rs fully qualified paths switched to foldhash::.
- foldhash::HashMap is std HashMap with foldhash::fast::RandomState, so API differences are only constructors: Metadata::new() -> ::default() (ir/module_print.rs), HashMap::from([..]) -> ::from_iter (pp/trace.rs).
- Iteration order was already random under std RandomState, so no output depends on it.

Verification: slate profile 39/39, parser profile 9150/9150; all targets build without warnings.

Limits: the gain is small because wall time is bound by ceval.c and ~4s of project-level (non per-TU) phases; profile those next.
See: slate-5q63.13 (shadow restore single walk, SLATE_NO_FORMAT).
