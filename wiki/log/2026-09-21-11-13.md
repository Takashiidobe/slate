# lex the bf16/BF16 floating literal suffix

_2026-09-21 11:13:00_

Follow-up to [[2026-09-21-11-07]]. `__bf16` lowered but had no literal spelling,
so a bf16 value could only arise from a conversion.

gcc accepts `1.5bf16` and `1.5BF16` with type `__bf16`; clang rejects the suffix
entirely. Accepted unconditionally rather than gated on `--flavor`, matching how
the gcc-only `df`/`dd`/`dl`/`q` suffixes were already handled — `const_expr.rs`
has no flavor gating, and input is assumed to already compile.

The bug this actually fixes: gcc spells its own limit macros with the suffix
(`__BFLT16_MAX__` is `3.389…e+38BF16`), so the reference predefine sets in
`src/predefines/gcc-16.*.h` were unusable. Worse, `FLOAT_SUFFIXES` is scanned by
first `ends_with` match over an ordered list, so `…e+38BF16` matched `f16` and
left a trailing `b` in the digits. The new entry therefore has to precede
`f16`, which is now commented at the array.

Chain: `FloatSuffix::BF16`, `FloatValue::BFloat16(u16)` resolved through
`Token::float_value_bf16` (`rustc_apfloat::ieee::BFloat`), the `FloatValue` arm
in `sema/numeric.rs` mapping to `FloatType::BF16`, and the suffix-to-`FloatKind`
arm in `sema/operand.rs` for metadata.

Verified against gcc 16.2.1: decimal and hex spellings, both cases, the
imaginary combination (`1.5bf16i` is a `complex<bf16>`, `sizeof` 4, as in gcc),
`_Generic` selecting `__bf16`, and `(int)3.7bf16` now folding — which makes the
`BF16` arm of `fold.rs float_to_integer` reachable rather than dead. Malformed
spellings (`1.5bf16l`, `1.5bf1`, `0x1.8bf16`) are rejected as gcc rejects them.
`_Complex __bf16` is a parse error in gcc too, at the same point, so our
rejection matches gcc rather than merely coinciding with clang's.

One divergence found and filed separately: `split_float_spelling` lowercases the
spelling, so we accept mixed-case suffixes (`1.5bF16`, `1.5Df`) that gcc
rejects. Pre-existing and uniform across every suffix.
